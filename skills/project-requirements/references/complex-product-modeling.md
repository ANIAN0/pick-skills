# 复杂产品理解

用产品流程图防止复杂需求中的主体、触发和流程关系被理解错。这里描述产品怎样运行，不提前设计类、接口、表结构、工具参数或调度算法。

## 何时使用

出现任一情况时使用本文件：

- 两个以上彼此独立的触发源；
- 后台、定时、异步、持续同步、恢复或长连接；
- 用户、应用、Agent、Skill、调度器或外部工具中的多类参与者协作；
- 多条流程共享同一份数据；
- 多个参考实现分别提供局部能力。

## 建立最小产品图

复杂需求至少形成一张能够解释核心关系的流程图；一张图难以阅读时再按独立流程拆分。图中表达：

1. 谁或什么事件触发流程；
2. 谁执行主要动作；
3. 用户或外部系统提供什么；
4. 系统产生什么用户可见结果；
5. 多条流程之间存在控制调用，还是只读取、写入同一数据。

节点尽量使用“参与者 + 动作”，连线在关系容易误解时标明含义。不要为了满足格式而给每条边分类，也不要把内部组件、接口字段、数据库表或具体轮询参数画进需求图。

用户故事解释为什么需要，用户旅程解释用户怎样完成目标，流程图解释产品各方怎样协作。正文能够清楚回答这些问题即可，不要求三类材料机械重复同一内容。

## 校正语义

检查：

- 同步、定时、手动操作等不同触发是否被错误串成一条链；
- 共享同一数据是否被误写成一个流程触发另一个流程；
- 应用、调度器、Agent 和 Skill 是否互相替代了职责；
- 参考实现事实是否未经产品决定就变成目标行为；
- 图与正文是否对“谁执行、何时发生、用户看到什么”给出同一答案。

如果这些关系存在彼此排斥的产品方向，并且不先决定就无法形成一套自洽方案，回到主 Skill 执行设计阻塞型产品分叉测试。不要为每个节点和连线构造理论上的其他解释。只有技术实现、Agent 内部判断或数据投影存在多种方案时，交给设计，不阻止需求进入设计。

## 状态与生命周期

当等待、运行、成功、失败、中断或恢复会改变用户能做什么、看到什么或得到什么结果时，在正文中写清这些用户可见规则。流程复杂且文字容易混淆时画状态图；文字已经清楚时不强制额外图表。

每个用户可见状态或结果都要标明它属于哪个产品对象。任务是否启用、一次运行是否成功、Agent 会话是否等待以及领域判断是否“无新增内容”可以相关，但不能塞进同一个状态集合。一个对象的结果不能冒充另一个对象的生命周期状态。

需求只确定用户能区分哪些对象、看到什么状态或结果以及能够怎样继续；锁、队列、目录冲突算法、持久化枚举和跨对象事务进入设计。发现技术风险时，不要直接把 agent 选择的防护机制写成产品规则。

不要求需求阶段定义内部状态枚举、持久化字段、重试算法或完整技术状态机。

## 失效与修复

如果新证据证明执行主体、触发关系、独立流程划分或控制关系错误，撤回由错误理解派生的产品结论，重新调查并重画受影响部分。

修复完成后重新执行设计阻塞型产品分叉测试。图形符号、箭头标注或技术细节不足不能单独使产品理解失效。
