# 需求细则

## 路线图维护

`ROADMAP.md` 只保留里程碑节点，不承载需求正文、任务、负责人、日期或验收标准。

```markdown
# ROADMAP

- [discussing] M-001：让用户能用账号登录并进入自己的工作台。
- [confirmed] M-002：让管理员能配置团队成员的访问权限。
```

维护规则：

- 每个 `M-*` 只写一句核心内容；需要解释原因、范围或证据时，写入需求入口或支撑材料。
- 新需求必须先归属到一个 `M-*`；无法归属时先新增或调整里程碑。
- 一个请求跨多个里程碑时，先拆分路线图节点，再一次只推进一个节点的需求入口。
- 需求入口确认后，对应里程碑可改为 `confirmed`；后续实现、验收或发布状态由下游阶段更新为 `in_progress` / `done` / `blocked`。

## 草稿和支撑材料

需求入口在 `discussing` 阶段就是给人阅读的草稿，在 `confirmed` 后就是正式正文。讨论期只维护这一份主文档，不额外维护状态、日志或待办同步文件。支撑材料放在入口旁的同名目录中，按需创建，不预建空目录或空文件。

```text
workplace/3/requirements/2026-06-21-order-import.md
workplace/3/requirements/2026-06-21-order-import/
├── research/RT-001-duplicate-handling.md
├── evidence/EVD-001-current-flow.md
├── decisions/DEC-001-duplicate-strategy.md
└── review/REV-001-requirements-review.md
```

编号使用类型加递增数字：`RT-*` 调研、`EVD-*` 证据汇总、`DEC-*` 需求决策、`REV-*` 审查。项目证据能直接链接真实代码或已有文档时，不复制证据文件；只有多个来源需要汇总结论时才创建 `EVD-*`。

只有需求决策同时满足以下条件才创建 `DEC-*`：以后改变代价明显；只看最终结论无法理解原因；讨论中存在真实取舍。普通结论直接压缩进正文对应位置；未定决策只允许临时放在草稿文末 `## 待确认`，不得在正文创建“待定决策”章节；架构或实现取舍留给 `project-design`。

讨论期确有未解决问题时，在草稿文末临时追加：

```markdown
## 待确认

- [ ] <问题、影响、推荐选项>
```

`## 待确认` 只服务当前讨论，不是正式正文结构。进入 `confirmed` 前必须删除该节：已确认的问题合并回对应正文位置，仍未解决的问题阻止确认。

## 推导深度

简单改动只做足以排除歧义和遗漏的分析。中大型需求先用业务语言说清核心机制：关键对象如何流转，谁触发谁，哪些规则决定结果，哪些失败影响主流程。

以下任一情况视为中大型需求：新模块或子系统、跨模块协作、事实源变化、持久化数据或权限变化、AI/Agent、异步流程、兼容或迁移、三条以上用户路径。

功能点推导时检查：

- 是否直接服务当前里程碑和用户故事，是否遗漏完成目标所需能力。
- 功能之间是否重复、互相依赖或边界冲突。
- 用户可见功能是否同时考虑界面和后台行为。
- 本期做和明确不做是否已达成一致。
- AI/Agent 的任务、角色边界、上下文、工具、自主范围和错误后果是否清楚。
- 用户强调的限制、风险和偏好是否进入功能点或验收要求。

## 正文第一性原则

需求正文不是流程账本、讨论纪要或审查入口。它只服务一个目标：让读者用最短时间理解“为什么要做、给谁做、要做到什么、怎么判断做对”。写正文前先确定目标读者，通常是产品、设计、技术方案负责人、测试和业务确认人；正文必须让这些读者不翻支撑材料也能理解需求结论。

正文组织遵守四条原则：

- 阅读路径优先：内容按读者理解顺序展开，而不是按产出时间、讨论顺序、审查顺序或模板栏目堆叠。推荐顺序是摘要、路线图节点、背景与目标、用户与场景、功能需求、必要 UI 要求、少量补充说明。
- 就近完整：一个功能点下写完它的能力、关键规则、异常、权限/数据影响和验收要求；不要把验收、异常、限制拆到远处，让读者上下跳读。
- 单点表达：同一结论只放在最能解释它的位置。其他章节如果需要提到，只用一句引用式提示，不能换一种说法重复一遍。
- 正文只收最终结论：调研过程、审查意见、变更原因、执行待办和流程元数据不进入正文；待确认问题只允许在讨论期临时放在文末 `## 待确认`。只有它们转化成已确认的需求结论后，才写回正文对应位置。

每一节都必须通过这个判定：读者现在看到它，是否能更快理解需求内容。答案不是明确的“是”，就删除、合并或下沉。

正式正文禁止出现；讨论期只有 `## 待确认` 这一种临时例外，且只能放在文末：

- 顶部字段表、front matter、文档编号、负责人、状态、确认日期、审查链接等流程元信息。
- 独立的“本期边界”章节；范围限制只有在帮助理解某个功能或场景时，写入对应功能小节或补充说明。
- 独立的“验收要求”总章；验收要求必须紧跟对应功能点，避免读者上下切换。
- “待定决策”“待确认问题”“变更记录”“讨论记录”“角色问题集合定义”等过程性章节。
- 为了凑结构而写的空节、占位节或与前文重复的摘要。

如果某段内容属于重要背景、用户画像、业务规则或术语定义，可以留在正文；如果它只是推导过程、审查发现、历史变更或执行待办，必须下沉到支撑目录；如果它是未确认问题，只能在讨论期临时放入文末 `## 待确认`，不能进入正式正文。

## 定稿清理

定稿清理不是重新生成正文，而是在用户已经看过的草稿上做最小编辑。允许的动作只有：

- 删除 `## 待确认`，或把已确认结论合并回对应功能、场景或补充说明。
- 删除过程性话语、重复表达、占位句和只服务讨论的说明。
- 调整章节顺序或小标题，使阅读路径更顺，但不得改变需求含义。

定稿清理后必须对照清理前草稿检查：用户故事、功能点、关键规则、异常、验收要求和 UI 要求没有丢失；任何语义变化都必须回到 `discussing` 继续确认，而不能借“清理”名义直接定稿。

## 用户故事、功能点和验收

用户故事使用四段式，逐项分行列出：作为 `[谁]`，当 `[场景]` 时，我需要 `[功能]`，以便 `[目的]`。

- 谁：具体角色，包含关键属性。
- 场景：触发条件或上下文。
- 功能：动词驱动，不写实现细节。
- 目的：业务价值或用户可见结果。

功能点只写用户可理解的能力和结果，不写模块设计、API、数据库、文件路径或实现步骤。每个功能点内部必须包含对应验收要求，优先使用最高层可观察行为，只有最高层证据不足以证明关键风险时才补充较低层要求。

## UI 需求

需求阶段不生成原型，不创建 `ui/UI-*` 或其他 UI 文件。涉及 UI 时，只在需求正文写清页面、状态、交互、数据、失败反馈、可访问性和用户确认结论的必要摘要；能归入功能点的 UI 要求写在对应功能小节，跨功能的 UI 要求才单独成节；无 UI 时写明“不涉及 UI”。

## 按需调研

缺少事实会导致路线图里程碑、用户故事、功能点或验收要求无法确定时，在草稿文末 `## 待确认` 登记 `RT-*`，写清调研问题、范围和完成条件，然后调用 `project-research`。调研报告链接回 `RT-*`，正文只在最终结论需要溯源时链接调研报告；结论未回写或仍 `blocked` 时不得确认需求。

## 回退

下游证明已确认需求需要改变时，对应 `ROADMAP.md` 里程碑改回 `discussing`，原正文重新作为可读草稿维护，并在对用户的回复中说明哪些方案、计划、执行和验收确认失效。修改后重新自检、审查和用户确认，不能复用原确认。
