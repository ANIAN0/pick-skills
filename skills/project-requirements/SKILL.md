# 项目需求

把用户真正需要解决的问题聊清楚，并形成一份有明确阅读顺序、可以独立理解的需求正文。

正文只保留当前需求结论。把讨论、调研、问题、决策依据、审查记录和变更历史放入正文旁的同名二级目录；正文不能依赖这些材料才能读懂。

## 成功标准

让不了解本次会话的读者仅凭正文就能回答：

- 为什么要做，主要给谁使用；
- 用户在什么场景下怎样使用，系统应产生什么可观察结果；
- 本次包含和不包含什么，哪些规则会改变结果；
- 产品能判断价值与范围，开发能理解行为边界，测试能据此设计主要场景。

不要用篇幅、章节数量或问题数量代替清晰度。

## 先形成需求地图

先阅读用户表达和与需求直接相关的项目材料，再区分以下信息：

- **已确认事实**：用户已经明确表达，或可以从现有业务与项目材料中查证；
- **当前理解**：根据上下文作出的解释，仍可能有别的含义；
- **待决定事项**：不同答案会改变功能、使用方式、范围或预期结果；
- **实现问题**：只影响技术做法，不应让用户在需求阶段决定。

当用户已经提出一个方案时，先判断它是否真正解决原问题、是否与现有事实相符、是否引入不必要范围。把方案当作重要输入，不直接当作已经确认的需求结论。

能从代码、配置、现有文档或业务事实查清的内容自行查清。不要把项目调查题、术语题或实现选型题转交给用户。

改造已有能力或要求与现有功能保持一致时，必须先走查最接近的现有用户流程，至少核对入口、列表展示粒度、详情内容、可执行动作、操作对象和结果反馈。用户点名某项现有能力作为参照时，以该能力为比较基线，不能用当前待改造目标或未完成实现替代；分别记录参照基线、目标当前状态和期望状态。现状不自动等于最优方案，但任何偏离参照基线的用户可见行为都先列为待决定事项，明确询问并得到用户确认，不能静默替换。

在需求地图中明确业务对象和操作粒度：每个列表行、详情页、状态和操作分别针对整个对象、某个版本、草稿、当前运行项或其他具体层级。同一动作名称作用于不同层级时分开记录；对象或操作粒度无法从项目事实查清时，必须让用户决定。

## 高效澄清

在提问前先用已有证据尽量自答，只询问用户必须决定且会改变需求含义的事项。

默认把互不依赖的高价值问题合并为一轮 **2–5 个编号问题**。只有当前答案会决定后续所有问题、事项风险很高，或确实只有一个未决点时，才单独问一个问题。不要机械地每轮只问一个问题，也不要一次抛出长清单。

每个问题都要：

1. 指向一个明确的需求分歧，而不是泛泛收集更多信息；
2. 先写当前理解或已知事实，再指出不同答案会改变什么；
3. 在确有可选方向时给出少量具体选项、影响和基于证据的建议，同时允许用户直接修正前提；
4. 使用产品和业务语言，让用户可以直接回答；
5. 能明确映射回正文中的目标、场景、规则、范围或验收结果。

不要询问：

- 答案不会改变当前需求的问题；
- 为满足固定数量而拆出的同义问题；
- 参数、表结构、接口字段、异常恢复等实现细节；
- 没有项目证据支撑的防御性场景；
- “是否还有其他要求”之类没有边界的收尾问题。

收到回答后，先合并已确认结论并更新正文，再统一处理下一批真正受影响的问题。不要把同一主题拆成多轮零散确认。

## 编写正文

尽早创建或更新正文，随讨论持续合入结论，不在结束时凭记忆重新生成全文。

第一次创建正文时按项目规范标记状态；项目没有约定时标为“草稿”。草稿中区分已确认结论和待决定事项，可以随讨论持续更新，但不能作为已确认需求交给方案、规划或实现阶段。

根据需求复杂度调整篇幅，但复杂需求至少建立以下阅读顺序；可以合并或改名，不要为了形式保留空章节：

1. **开篇概览**：用几段短文讲清问题、用户、期望改变和本次范围；
2. **用户与场景**：说明谁在什么情况下使用，以及想完成什么；
3. **现状基线与行为差异**：说明本次沿用哪些现有行为，明确新增、改变和移除什么；
4. **核心使用过程**：按用户实际发生顺序描述主流程，覆盖入口、列表或选择、详情、操作反馈和操作后的可见状态；
5. **功能与规则**：按用户目标或业务场景组织能力、对象与操作粒度、状态和重要边界；
6. **范围边界**：明确容易误解的包含项、不包含项和外部依赖；
7. **可观察结果**：用主要成功场景和关键差异场景表达验收口径。

先给全貌，再展开细节。每个章节只回答一类读者问题；每段只表达一个中心意思。流程使用有序列表，平行规则使用项目符号，比较或精确映射才使用表格。避免连续大段文字、同一结论在多处重复，以及用链接或术语替代解释。

正文使用一致的业务术语；第一次出现时用自然语言解释，必要时再附项目中的技术名称。把当前状态、目标状态、需求结论、原因和未决问题分开写，不在同一段混杂。

只写用户可感知的行为和业务规则，不提前设计技术架构。不要为了“完整”穷举所有异常、参数和实现默认值。对正文理解非必要的证据、调研过程和长清单移入二级目录，并在正文需要时用链接指向。

## 文件与变更记录

为每个独立改动使用稳定的工作名称。文件名优先使用简短、明确的中文功能名；已有 Issue、Ticket 或事项编号时使用“编号-中文功能名”。路径优先遵循用户指定；否则沿用项目规范，默认写入 `workplace/<版本>/requirements/<工作名称>.md`。文档被下游引用后，不因标题或措辞变化随意改路径。

在正文旁创建同名二级目录，并维护独立的 `变更记录.md`。正文含义变化后追加一条简短记录，说明改了什么以及为什么改；纯排版、错字和不改变含义的措辞调整不记录。其他材料按需创建并使用容易理解的中文文件名。

二级材料中的最终需求结论必须提炼回正文。不要让审查记录、会议记录或调研报告成为理解正文的前置条件。

## 收敛式清晰度审查

正文基本稳定后进入审查循环。不要假设一次审查能发现全部问题，也不要预设必须审查多少轮；以是否仍存在会改变需求理解的实质问题决定是否继续。

每次全量覆盖审查先做来源与基线对照：逐项检查正文结论是否来自用户明确表达、已查证项目事实或用户已经确认的基线差异。改造已有能力时，将正文与已走查的现有用户流程比较；没有来源的偏离即使内部逻辑自洽，也不能直接保留为需求结论。

第一轮先由主 agent 做全量覆盖审查，同时检查三种读者视角：

- **产品视角**：问题、用户、价值、范围和主要体验是否清楚；
- **开发视角**：可观察行为、输入输出、状态规则和边界是否足以避免不同功能理解；
- **测试视角**：能否从正文推导主流程、关键差异场景和预期结果。

在修改正文前先汇总本轮全部发现，去重并逐项验证。对每个发现分类：

- 用户意图不明确：合并进下一轮澄清问题；
- 项目事实缺失：继续调查，不询问用户；
- 正文表达不清：直接重组或改写；
- 实现细节未定义：留给技术设计，不扩写需求；
- 与本次目标无关：记录理由后丢弃。

集中处理本轮全部实质问题，不要发现一个、修改一个、马上再启动审查。审查者提出的假设不能直接写成需求；必须回到用户原话或业务证据验证。

仅在需求复杂、跨领域或主 agent 无法可靠模拟目标读者时，使用独立 subagent 盲读。只提供正文，让其指出可能导致功能理解不同的具体位置并说明影响；不要让其为了凑数生成问题。需要多个读者视角时尽量在同一轮并行审查，汇总后统一处理，避免多个审查者依次修改正文。

每轮修改后按影响范围决定下一步：

- 只改措辞、排版或局部解释：定向复核本节，不启动新一轮全审；
- 改变一个场景、规则或边界：复核该部分及其关联流程、范围和可观察结果；
- 改变核心目标、用户、范围、主流程或多个章节共用的规则：重新进行全量覆盖审查；
- 新发现的问题表明原需求地图失效：暂停补丁式修改，重新梳理需求地图和正文结构后再全审。

普通需求在一轮复核没有发现实质问题后结束。跨领域、高风险或将直接驱动多个下游阶段的需求，可以要求连续两轮没有新的实质问题。实质问题只包括会导致功能、使用方式、范围、业务规则或预期结果被不同理解的差异；措辞偏好、实现选择和不影响当前目标的细节不推动新一轮。

不要规定“至少提出多少个问题”或固定审查轮数。把每轮范围、实质发现、处理结果和下一轮原因放入同名二级目录，不在正文写“审查通过”。

需求阶段完成不表示已经证明不存在未知问题。只有规定的调查与审查已经执行、审查发现的实质问题均已查证、由用户决定或明确排除，并且用户已经审阅和明确认可当前正文，才将正文标记为已确认并允许交给下游。用户确认后若正文的功能、使用方式、范围、业务规则或预期结果发生变化，重新标为草稿并确认受影响内容。

## 边界

- 不强制维护 `ROADMAP.md`、里程碑编号、固定模板、字段编号或需求状态机；项目已有规范或用户明确要求时沿用。
- 不负责技术方案、原型设计、任务规划、编码实现或项目验收。
- 不把需求澄清变成全面审计；调查和提问只覆盖会改变本次需求理解的内容。
- 不以减少提问为由自行决定用户必须决定的事项，也不以追求完整为由无限延长讨论。
