# 项目需求

把用户真正想要的功能聊清楚，并写成一份容易理解的需求正文。

需求正文只讲当前需求结论。正文旁使用同名二级目录保存变更日志，以及确有保留价值的讨论、调研、决策、问题和审查材料。

## 核心原则

- 根据具体事情理解需求，不使用固定模板、问题清单或审核规则代替判断。
- 需求简单就简短表达，需求复杂才展开说明。不要为了显得完整而补充用户并不关心的流程、异常或边界。
- 只追问真正影响用户意图或功能理解的问题。能从现有信息自然理解的内容，不要求用户再次确认或形式化表述。
- 正文独立表达当前已经形成的需求理解。最终结论写入正文；得到结论的过程放入二级目录。
- 优先在现有正文上持续合入新结论，不在结束时凭记忆重新生成全文。
- 使用自然的业务和用户语言，不进入技术方案、任务或实现细节。

## 工作方式

先理解用户已经表达的目标，并按需查看与需求直接相关的项目材料。围绕用户真正想解决的事情自然讨论；哪里已经清楚就直接写，哪里确实可能产生不同理解再继续聊。

尽早创建或更新需求正文，并随讨论持续修改。文档按读者最容易理解的方式组织，可以按场景、功能、使用过程或直接叙述，不预设章节。路径优先遵循用户指定或项目现有约定。

在正文旁创建同名二级目录，并维护其中独立的 `changes.md` 变更日志。每次需求正文的含义发生变化后，追加一条简短记录，说明改了什么以及为什么改。纯排版、错字和不改变含义的措辞调整可以不记。日志只记录变化，不重复保存需求正文。

判断正文是否足够时，把它当作一段给不了解本次对话的人看的说明：如果对方能准确理解用户想做什么、为什么以及大致如何使用，就已经达到目的；如果仍会对核心需求产生明显不同的理解，再补充或询问。不要穷举所有可能情况，也不要把更多细节等同于更完整。

讨论、调研、决策、问题和审查等过程信息不进入正文。除独立的 Markdown 变更日志外，其他二级材料按需创建且格式自由。二级材料中的最终需求结论应提炼回正文，不让正文依赖过程材料才能读懂。

## 清晰度审查

主 agent 认为需求正文已经能表达用户意图后，使用两个新的 subagent 检查正文是否真的能独立传达这份理解：

1. 只把需求正文交给第一个 subagent，不提供用户对话、项目背景或主 agent 的理解。让它从读者角度提出至少 10 个有价值、能够检验需求理解的问题。问题必须基于这份需求，不能为了满足数量加入同义问题或无关细节。
2. 只把需求正文和问题交给第二个 subagent，同样不提供其他上下文。让它完全根据正文逐题回答；正文无法支持答案时明确写“不确定”，不能自行补全需求。
3. 主 agent 根据与用户的完整对话和自己形成的需求理解，独立判断这些问题的答案，再与第二个 subagent 的答案比较。只比较需求含义，不比较措辞。
4. 如果答案存在会导致功能、使用方式或预期结果被不同理解的差异，说明正文还不够清楚。主 agent 继续澄清或修改正文，在变更日志中记录修改，然后重新进行审查。
5. 如果差异只来自表达方式，或者问题触及用户尚未定义且不影响当前需求的细节，不为了让答案完全一致而扩写正文。

把每轮问题、回答和有意义的差异记录在同名二级目录的 Markdown 文件中，文件名和内部格式不限。不要把审查问答或“审查通过”等流程信息写进需求正文，也不要把主 agent 的预期答案提前提供给两个 subagent。

## 边界

- 不强制维护 `ROADMAP.md`、里程碑编号或需求状态机。
- 不强制固定模板、章节、字段、编号、状态或额外确认门槛。
- 不负责技术方案、原型设计、任务计划、编码实现或项目验收。
- 不把需求澄清变成全面审计；需要问到什么程度，由当前需求本身决定。
