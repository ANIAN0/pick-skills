# 项目验收

这是流程型 skill。目标不是复述执行报告，而是从已确认需求、方案、任务和执行结果出发，独立证明交付结果是否满足验收要求。只有真实验收、缺陷闭环、独立审查和用户确认全部完成，标准研发流程才算结束。

## 触发与边界

**触发**：用户要求“最终验收”“交付验收”“真实验收”“验收回归”“验收执行结果”“验收缺陷归因”“确认项目完成”，或其他研发阶段 skill 在执行结果已确认后调用验收时使用。

**不触发**：功能尚未实现或执行结果未确认时，调用 `project-execution`，见其 SKILL.md；用户要求维护上线前完整流程测试方案、测试脚本或测试套件时，调用 `test-suite-maintainer`，见其 SKILL.md；用户要求独立审查阶段入口而不是执行验收时，调用 `project-review`，见其 SKILL.md。

**与其他 skill 的关系**：本 skill 可调用 `project-review` 审查验收入口，见其 SKILL.md。审查 skill 不可用时，按本文件“校验与门槛”和“证据与完成定义”执行一次验收复核，在 `review/REV-*` 记录复核问题、修正结果和结论；不得跳过审查环节或把未复核的入口标为 `confirmed`。

## 存储与路径契约

- 验收入口放在项目目录的 `workplace/<版本>/acceptance/` 下；`<版本>` 必须是整数或两段数字，例如 `3` 或 `3.1`。
- 用户给出验收入口路径时，更新该文件；未给出路径时，优先复用同版本 `acceptance/` 下与当前任务相关的入口；没有可复用入口时创建 `YYYY-MM-DD-功能-slug.md`。
- 新建入口使用 [验收入口模板](assets/acceptance-entry.md)。
- 验收支撑材料放在入口同名目录下：`<入口文件去扩展名>/test/`、`evidence/EVD-*`、`logs/LOG-*`、`defects/DEF-*`、`review/REV-*`。
- 入口只保存验收结论、覆盖矩阵、缺陷摘要、证据链接和剩余风险；原始日志、截图、测试输出和长报告放入支撑目录，并从入口双向链接。
- 禁止在 `workplace/` 之外创建验收入口；禁止把验收内容写进需求、方案、任务或执行入口；禁止在正式路径中使用 `<version>`、`x.x`、`latest` 等占位符。

## 阶段与流转

验收入口 `status` 只使用：

| 状态 | 含义 | 可进入的下一状态 |
|---|---|---|
| `in_progress` | 正在验收、修复回归、补证据或等待审查 | `not_verified` / `blocked` / `confirmed` |
| `not_verified` | 已有验收工作，但缺少必须证据、审查/复核或用户确认 | `in_progress` / `blocked` / `confirmed` |
| `blocked` | 缺少环境、权限、数据、外部依赖或上游修正，当前无法形成验收结论 | `in_progress` / `not_verified` |
| `confirmed` | 必须验收项全部通过、审查/复核通过、用户明确接受最终结果和剩余风险 | `in_progress` |

验收项结果只使用 `passed` / `failed` / `blocked`。缺陷状态只使用 `open` / `resolved`。

切换条件：

- `in_progress` -> `not_verified`：验收执行已经完成一部分，但仍缺少必须证据、审查通过记录或用户确认。
- `in_progress` -> `blocked`：缺少环境、权限、数据或外部依赖，且无法通过项目内可用方式补齐。
- `blocked` -> `in_progress`：阻塞条件已解除，并能重新执行受影响验收项。
- `not_verified` -> `confirmed`：所有必须验收项为 `passed`，无未解决 `DEF-*`，审查/复核通过，用户明确确认最终结果和剩余风险。
- `confirmed` -> `in_progress`：后续发现验收证据无效、新缺陷影响已确认范围，或用户/上游变更推翻验收依据。

## 执行步骤

1. 确认入口和版本：定位 `workplace/<版本>/acceptance/` 中唯一验收入口；新建时使用模板，并把 `status` 设为 `in_progress`。
2. 校验上游状态：读取已确认需求、方案、任务入口、全部 `T-*` 实现契约、执行状态、基础检查证据和 `execution_review`。只有上游执行结论已确认且没有未解释的 `not_verified`、`blocked` 或高风险偏差，才能继续最终验收。
3. 建立追踪矩阵：把每个 `F-*`、验收要求、相关 `C-*`、`T-*`、`V-*`、代码实现、配置变更和既有执行证据连起来；任何无法追踪的必须项先记为验收缺口，不得默认通过。
4. 设计本轮验收范围：按风险选择真实验证方式，必须覆盖成功路径、关键失败路径、边界条件、用户可见路径、共享契约、兼容/迁移影响和回归范围。自动化不可行时写清手工步骤、前置条件、预期结果和证据形式。
5. 执行真实验收：逐项运行或复核验收。后端和服务边界验证真实接口、服务、持久化和副作用；涉及 UI 时验证真实页面、交互反馈、错误提示、布局状态和关键用户路径，必要时保存截图；回归验证必须覆盖受影响模块和共享契约。
6. 记录证据和结论：每个验收项写入 `passed` / `failed` / `blocked`、实际结果和 `EVD-*` / `LOG-*` / 截图 / 报告链接。可以复用执行阶段证据，但必须重新核对适用范围、当前性和覆盖关系。
7. 处理缺陷和回退：验收项未通过时创建或更新 `DEF-*`，记录复现步骤、期望、实际、影响、证据、责任阶段、受影响 `T/F/V` 和恢复条件；按最早错误契约判定回退到需求、方案、规划、执行或验收自身。
8. 复验受影响范围：责任阶段修正并重新确认后，只关闭有修复证据和复验证据的缺陷；重新执行受影响验收项和相关回归，更新入口结论。
9. 审查和用户确认：完成自检后优先调用 `project-review` 审查验收入口；不可用时按本文件门槛创建 `review/REV-*` 复核记录。审查/复核通过后，请用户确认验收结论、功能结果、用户路径、回归结果和剩余风险。用户确认后才能把 `status` 改为 `confirmed`。

## 校验与门槛

验收完成前必须满足：

- [ ] 验收入口路径位于 `workplace/<版本>/acceptance/`，并与支撑目录双向链接。
- [ ] 上游需求、方案、任务和执行结果均为已确认状态；若不是，验收入口保持 `not_verified` 或 `blocked`。
- [ ] 每个 `F-*` 及其验收要求都有验收项、结果、实际观察和可回查证据。
- [ ] 成功路径、关键失败路径、边界条件、UI/用户路径、兼容/迁移影响和回归范围的覆盖与本次风险相称。
- [ ] UI 验收不能只用接口响应、网络请求成功或 DOM 元素存在证明页面正常；必须核对用户实际看到的页面状态，复杂或失败场景要有截图证据。
- [ ] 不把任务状态、执行报告、测试名称、历史结果或“人工检查”空话当作当前真实验收证据。
- [ ] 每个 `failed` 或 `blocked` 必须关联 `DEF-*` 或明确阻塞原因；必须项存在 `failed` / `blocked` 时，总体验收不得通过。
- [ ] 所有 `DEF-*` 均有状态、责任阶段、恢复条件和受影响 `T/F/V`；`resolved` 只能来自修复证据和复验证据。
- [ ] 审查/复核通过，且用户已明确确认最终结果和剩余风险，才允许 `status: confirmed`。

多轮修复后必须比较上一轮和本轮的质量轨迹：若修复一个缺陷后减少了原有 `F-*` 覆盖、丢失关键证据、放宽验收要求、跳过失败路径，或引入同等及以上风险，视为退步；不得关闭缺陷或确认验收。

## 失败与回退

- 输入不是真实任务入口或验收入口路径：停止正式验收，要求提供可追踪入口；不要基于摘要生成 `confirmed` 结论。
- 执行结果未确认、存在未解释 `not_verified` / `blocked` 或缺少 `execution_review`：入口保持 `not_verified`，返回执行阶段补齐。
- 环境、权限、数据或外部依赖缺失：记录 `blocked` 验收项和恢复条件；能按项目已有造数或配置方式补齐时先补齐，不要直接跳过。
- 验收发现实现偏差但需求、方案和任务契约正确：验收保持 `in_progress`，缺陷责任阶段标为执行；执行修复并重新确认后复验。
- 验收发现任务契约错误：回到规划阶段修订任务；修订确认后重新执行、审查并验收受影响范围。
- 验收发现方案或需求错误：继续逐级回退到责任阶段；验收入口记录影响和回退责任，不替责任阶段改结论。
- 验收自身判断或证据记录错误：保持在验收阶段修正入口、证据链接和结果，不把责任推给执行阶段。
- 审查/复核未通过：入口保持 `not_verified`；修正后复审，不得让用户确认替代审查/复核通过。

## 证据与完成定义

`confirmed` 必须同时具备以下证据：

- 每个必须验收项为 `passed`，且证据来自当前真实执行、当前环境复核或仍适用的执行阶段证据再核对。
- 无未解决 `DEF-*`；没有必须项处于 `failed` 或 `blocked`。
- 兼容、迁移、共享契约和回归影响已按风险覆盖。
- 最新审查报告或复核记录结论为通过，入口链接该记录。
- 用户明确接受最终验收结论和具体剩余风险。

用户可以接受剩余风险，但不能直接接受必须验收项的 `failed` 或 `blocked` 作为通过；若要接受，必须先回责任阶段变更范围、需求或验收要求。

## 下沉材料

新建验收入口时使用 [验收入口模板](assets/acceptance-entry.md)。模板只定义入口文档结构；本文件的阶段、门槛、回退和完成定义仍是执行验收的权威规则。

## 边界声明

本 skill **不做**：

- 不修改生产代码，不替执行阶段关闭实现缺陷。
- 不降低已确认需求、方案、任务契约或验收要求。
- 不为每个测试、日志或截图创建一个验收入口。
- 不用 mock、stub、占位数据或历史结果伪装当前真实验收。
- 不把测试套件维护、测试脚本建设或上线前全量测试方案当作本 skill 的主要产出。
- 不替用户接受剩余风险，也不把审查通过等同于用户确认。
