# 项目验收

把已经完成的开发工作整理成可以交付的 Git 提交。先梳理和清理本次修改，再设计合理的分批提交方案；每个批次都要在提交前完成最终验收，发现问题就修复并重新验收，通过后才提交，然后处理下一批。

## 核心原则

- 验收证明的是实际功能和交付结果，不是重复执行阶段的完成说明。
- 正式需求、功能迁移基线、设计和计划文档都是可选输入。存在时沿直接链接读取；不存在时根据用户当前目标、实际采用的方案、受影响既有行为和代码判断。
- 只处理当前工作范围，保留并避开用户已有的无关修改、暂存内容和未跟踪文件。
- 清理临时材料不等于删除所有测试或文档。保留有长期回归价值的正式测试和交付所需文档，只删除确认属于本次工作且不应进入项目的临时产物。
- 一个批次只有在对应修改完成、工作区已清理、最终验收通过后才能提交。
- 提交是本 skill 的正常收口动作；不自动推送、部署、变基、强制更新远端或改写已有提交历史。

## 梳理相关修改

检查 Git 状态、已暂存和未暂存差异、未跟踪文件以及本次工作涉及的需求、方案、任务和审查结论。把工作区内容分成三类：本次应交付修改、本次产生但不应交付的临时材料、与本次无关且必须保持不动的用户修改。

阅读完整差异和必要的相关代码，确认每项修改的用途、相互依赖及其对应的功能目标。不能仅凭文件名判断归属，也不能把工作区里的全部修改默认视为当前任务。

如果无法可靠区分文件归属，先继续调查；删除、覆盖或提交错误文件的风险仍然存在时，请用户确认，不自行猜测。

## 清理工作区

删除本次工作创建且确认不需要交付的临时测试文件、一次性验证脚本、临时数据、日志、截图、缓存、构建产物、草稿和临时文档。清理由验证过程产生的新临时材料，并检查代码中是否遗留调试输出、临时开关、固定数据、注释掉的实现或绕过逻辑。

保留真正属于产品改动的测试、迁移、配置和文档。不要删除或修改其他需求创建的测试文件，不评价它们的质量，也不要清理无法确认来源的用户文件。采取删除操作前先核对准确路径和 Git 状态，避免扩大到当前工作范围之外。

清理可能改变程序行为时，把清理本身纳入后续验收，不能认为“只是删临时文件”而跳过验证。

## 设计分批提交方案

根据功能目的和依赖关系把本次改动划分为一个或多个提交批次。每个批次应表达一个容易理解的完整变更，包含实现该变更必需的代码、测试、配置、迁移和文档；不要为了增加提交数量机械地按文件类型拆分。一个提交已经足够清楚时，不强行分批。

提交方案至少说明每批的目标、包含的文件或差异、与其他批次的依赖、提交前需要完成的验收以及拟使用的提交说明。遵循项目已有的提交信息风格。

安排批次顺序时，确保每次提交后的仓库状态尽量完整、可理解且可验证。如果后续批次的未提交修改会影响当前批次的运行结果，就重新组合批次，或者在不触碰用户无关修改的隔离工作区验证当前批次；不能在混合状态下声称完成了批次级验收。

## 逐批验收、修复和提交

按提交方案一次只处理一个批次：

1. 明确当前批次的代码差异、预期行为和受影响范围，确认不包含其他批次或用户无关修改。
2. 根据该批次的功能和风险设计最终验收，分别检查目标功能是否成立、受影响既有能力是否回归、批次与其余本次修改组合后是否仍可用。选择目标测试、接口调用、界面操作、构建、类型检查、lint 或其他能够观察真实结果的方式，不机械要求固定命令；用户可见改动必须从真实入口操作到结果反馈。
3. 独立核对验收结果。既有测试通过只能作为补充证据，不能单独证明本批次正确；不能为了通过而修改测试去迎合错误实现。
4. 发现实现问题时直接修复，重新检查完整差异并重复受影响的验收，直到本批次真正通过。修复产生的临时材料要再次清理。
5. 如果问题说明迁移双基线、需求、任务范围或技术方案本身错误，先回到对应上游阶段修正，再重新设计受影响的提交批次；不要用局部代码绕过上游问题。
6. 精确暂存当前批次的文件或差异块，避免使用会把整个工作区一起加入的宽泛暂存方式。检查暂存差异，确认没有混入其他批次、用户修改、敏感信息或临时文件。
7. 只有当前批次验收通过且暂存内容与验收对象一致时才创建提交。提交成功后记录提交哈希和说明，再继续下一批。

如果修复改变了批次边界、依赖关系或验收范围，先更新提交方案再继续。后续批次发现已提交批次存在问题时，先修复并创建清晰的后续提交；除非用户明确要求，不通过 amend、rebase 或强制操作改写已有历史。

最后一个批次提交前，使用包含全部本次修改的当前产物再走通代表性完整用户路径，并逐项核对迁移基线中的目标兼容项或其他已确认回归基线。逐批验收通过不能替代整体组合验收；如果完整功能仍不可用，任何批次都不能被包装成“最终验收通过”。

## 完成

所有批次提交后，再检查 Git 状态和提交记录，确认本次应交付修改均已提交，临时材料已清理，未提交内容只剩明确识别的用户无关修改。汇总每个提交的哈希、说明、对应功能和最终验收结果，并如实说明无法验证的内容或剩余风险。

关键验收因环境、权限、设备或外部依赖无法完成时，不提交受影响批次，也不声称验收通过、功能可用或可交付；说明阻塞原因和恢复条件。构建、合同测试和代码审查不能降级替代缺失的真实用户路径。

默认不创建验收文档。项目确实需要保留记录时，把过程材料放到当前工作事项已有正文旁的同名二级目录，并优先使用中文文件名 `验收记录.md`；不要为了验收额外建立复杂的编号、状态和证据目录体系。
