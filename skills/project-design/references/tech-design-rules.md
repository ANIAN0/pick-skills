# 技术方案细则

## 文档和支撑材料

支撑材料放在入口旁的同名目录中，按需创建，不预建空目录或空文件。

```text
workplace/3/tech-design/2026-06-21-order-import.md
workplace/3/tech-design/2026-06-21-order-import/
├── research/RT-001-api-boundary.md
├── evidence/EVD-001-current-flow.md
└── review/REV-001-tech-design-review.md
```

编号使用类型加递增数字：`RT-*` 调研、`EVD-*` 证据汇总、`REV-*` 审查。项目证据能直接链接真实代码或已有文档时，不复制证据文件；只有多个来源需要汇总结论时才创建 `EVD-*`。

入口在相关方案摘要、`D-*`、`C-*` 或 `V-*` 下链接支撑材料；每份 Markdown 支撑材料开头链接回入口的对应标题或编号。

## 调研

证据不足以支撑当前方案时创建 `research/RT-*`，写清单一问题、范围、不调查内容、所需证据、完成条件和受影响条目，然后调用 `project-research`。入口只保留任务和结果链接，格式：

```markdown
#### RT-001 <调研问题短标题>

- 调研任务：[RT-001 <调研问题短标题>](<research/RT-001-slug.md>)
- 调研结果：pending / [completed](<research/RT-001-slug.md>) / [blocked](<research/RT-001-slug.md>)
```

报告回写后，责任阶段必须把结论吸收进方案内容。不能用调研报告替代方案结论；`blocked` 时不得确认方案。

常见触发：新增依赖或外部服务、新模块边界、复用或替换现有能力、数据迁移、兼容性、安全或性能关键假设、无法从代码或文档确认的框架能力。

## 正文第一性原则

技术方案正文只有一个目的：让读者用最短时间理解“为什么选这个顶层设计、系统如何协作、关键取舍是什么、细节如何落地、如何证明方案可行”。与这个目的无关的过程信息禁止进入正文。

禁止进入正文的内容包括：文档编号、负责人、里程碑、审查状态表、讨论过程、变更记录、待定决策清单、为了填模板而写的边界章节、空支撑材料索引。确有未确认技术问题时，只能临时放在文末 `## 待确认`；确认前必须删除该节或把结论合并回对应章节。

正文必须按从全局到细节组织。先讲顶层设计，再讲组件、接口、数据、UI、实施影响和验证；不得以文件修改列表、任务清单或 `C-*` 作为正文主结构。

## 顶层设计

顶层设计是方案的核心，必须在任何文件级修改、字段、接口细节之前明确。至少说明：

- 系统边界：本方案改动哪些系统、模块、页面、服务或数据域，哪些保持不变。
- 核心机制：请求、数据、事件或 Agent 调用如何流转，关键状态如何变化。
- 事实归属：谁是数据、权限、状态或配置的权威来源。
- 失败模型：失败在哪里被发现、隔离、重试、回滚或展示给用户。
- 方案取舍：为什么选择当前方向，主要替代方案为什么不选。

如果这些问题还没有答案，不得直接写 `C-*` 变更清单；应先补项目证据、调研或向用户成组确认会影响顶层设计的问题。

## 内容规则

方案概览用三段以内讲清核心机制：请求或数据如何流转，谁拥有事实，关键状态如何变化，失败在哪里隔离，用户结果如何被观察。

`D-*` 只在存在真实取舍时创建。每条写选择、主要替代、理由和影响；不写通用技术原则。

详细设计按实际命中的领域组织，不为了凑标题强行保留空章节。常见章节包括：模块与组件、API 与交互、数据模型与迁移、权限与安全、UI 实现、异步与任务、AI/Agent 行为、兼容与发布。每个详细设计条目都必须能追溯到顶层设计，而不是孤立描述某个文件要怎么改。

`C-*` 只放在“实施影响”中，用来承接任务规划落点，不能作为方案正文主结构。每条必须包含分类、类型、真实文件或模块、当前状态、目标修改、关联 `F-*`、具体验收要求、对应设计章节和 `V-*`。禁止使用“优化”“完善”“适配”等无落点描述。尚不存在的路径必须明确标注“新增”。

`V-*` 必须包含要证明的行为、真实可执行的验证方式和可观察证据。多模块或前后端协作时，至少一条 `V-*` 覆盖从真实入口到结果的闭环。

## 定稿清理

定稿清理不是重新生成正文，而是在用户已经看过的方案草稿上做最小编辑。允许的动作只有：

- 删除 `## 待确认`，或把已确认结论合并回对应方案概览、顶层设计、详细设计、实施影响或验证策略。
- 删除过程性话语、重复表达、占位句和只服务讨论的说明。
- 调整章节顺序或小标题，使阅读路径更顺，但不得改变方案含义。

清理后必须对照清理前草稿检查：顶层设计、关键决策、用户已确认取舍、约束、不做范围、实施影响和验证策略没有丢失或被改写。发现语义漂移时回到草稿修订，不得进入 `confirmed`。

## 覆盖检查

每轮讨论后检查：

- 每个 `F-*` 和验收要求都有 `C-*` 与 `V-*` 落点。
- 每个 `C-*` 都能追溯到顶层设计和详细设计章节，正文没有被 `C-*` 主导。
- 新增与修改位置都是真实项目路径或显式“新增”。
- 关键取舍有依据，且没有未解释的替代方案。
- API、数据、UI、失败模型互相一致。
- 用户特别关注点和不做范围没有丢失。

## 回退

执行、任务或验收回退并证明方案需要改变时，原方案正文重新作为可读草稿维护，并列出失效的下游计划、执行和验收确认。修订后重新审查和用户确认，不能复用原确认。
