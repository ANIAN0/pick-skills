# 项目设计

把为了解决当前问题或完成改动而采用的技术方案聊清楚，并写成一份新加入项目的开发人员也能快速理解的方案正文。

方案正文只讲当前方案结论。正文旁使用同名二级目录保存变更日志，以及确有保留价值的讨论、调研、决策、问题和审查材料。

## 核心原则

- 根据当前问题或改动目标、现有代码和项目约束选择最合适的方案，不把“最佳”理解为穷举所有可能路线。
- 方案先建立整体实现框架和协作边界，再说明关键改动。不能只罗列文件，也不细化到函数、代码行或具体编码步骤。
- 说明需要新增或修改哪些文件，以及每处为什么要改、在整体方案中承担什么作用。尚不能合理确定到文件时，先查项目；确实受后续实现选择影响时，可以明确到模块或目录并说明原因。
- 正文应让开发人员理解要做什么、总体怎么做、关键部分如何配合，以及方案覆盖到什么程度。具体实现计划和代码细节留给开发人员自行设计。
- 只讨论会影响主要技术方向、文件边界或多人协作理解的问题，不使用固定模板或审核清单代替判断。
- 正文独立表达当前已经形成的技术共识。最终结论写入正文；得到结论的过程放入二级目录。
- 优先在现有正文上持续合入新结论，不在结束时凭记忆重新生成全文。

## 工作方式

先理解用户想解决的问题、期望发生的改变或已有需求，再查看与实现直接相关的代码、配置、接口、数据、测试和项目文档。正式需求文档只是可选输入，不是开始设计的前提。能从项目中确认的事实自行查清；只有不同答案会明显改变方案时，才继续调研或询问用户。

围绕实际约束考虑可行路线，并说明为什么当前选择更适合这次改动。只有存在会影响理解的真实取舍时才讨论替代方案，不为了证明方案完整而罗列无关选项。

尽早创建或更新方案正文，并随讨论持续修改。文档按读者最容易理解的方式组织，可以从系统协作、数据或调用流程、模块关系、关键改动等角度展开，不预设章节。路径优先遵循用户指定或项目现有约定。

正文既要给出整体框架，也要列明预计新增或修改的文件。对每个关键文件说明改动目的和职责变化，但不展开具体代码写法。文件清单服务于解释方案和划分协作边界，不能变成任务清单。

在正文旁创建同名二级目录，并维护其中独立的 `changes.md` 变更日志。每次方案正文的含义发生变化后，追加一条简短记录，说明改了什么以及为什么改。纯排版、错字和不改变含义的措辞调整可以不记。日志只记录变化，不重复保存方案正文。

判断正文是否足够时，把它交给一个了解开发但不了解本次对话、并且刚加入项目的人：如果对方能据此理解实现方向、关键修改、各部分如何配合以及方案边界，并能在此基础上自行规划具体实现，正文就达到目的；如果仍可能形成明显不同的实现理解，再补充、调查或询问。

讨论、调研、决策、问题和审查等过程信息不进入正文。除独立的 Markdown 变更日志外，其他二级材料按需创建且格式自由。二级材料中的最终方案结论应提炼回正文，不让正文依赖过程材料才能读懂。

## 清晰度审查

主 agent 认为方案正文已经能表达技术共识后，使用两个新的 subagent 检查正文是否真的能独立传达这份理解：

1. 只把方案正文交给第一个 subagent，不提供问题或改动的原始描述、用户对话、项目文件或主 agent 的理解。让它以接手实现的开发人员视角，提出至少 10 个有价值、能够检验方案理解的问题。问题必须基于这份方案，不能为了满足数量加入同义问题或无关代码细节。
2. 只把方案正文和问题交给第二个 subagent，同样不提供其他上下文。让它完全根据正文逐题回答；正文无法支持答案时必须明确写“不确定”，不能自行补全方案。
3. 主 agent 根据当前问题或改动目标、项目证据、与用户的完整对话和自己形成的方案理解，独立判断这些问题的答案，再与第二个 subagent 的答案比较。只比较技术含义，不比较措辞。
4. 如果答案存在会导致整体实现方式、关键修改、文件职责、协作边界或方案范围被不同理解的差异，说明正文还不够清楚。主 agent 继续调查、澄清或修改正文，在变更日志中记录修改，然后重新进行审查。
5. 如果差异只来自表达方式，或者问题触及应由开发人员在具体实现时决定且不影响共同方案的细节，不为了让答案完全一致而扩写正文。

把每轮问题、回答和有意义的差异记录在同名二级目录的 Markdown 文件中，文件名和内部格式不限。不要把审查问答或“审查通过”等流程信息写进方案正文，也不要把主 agent 的预期答案提前提供给两个 subagent。

## 边界

- 不强制维护固定路径、模板、章节、编号、状态机或额外确认门槛。
- 不要求先经过需求阶段或补写需求文档；当前问题或改动目标不清楚且会影响方案时，只澄清真正影响技术方向的部分。
- 不把方案细化成开发任务、实施步骤、函数设计、伪代码或逐行修改说明。
- 不修改生产代码、测试、配置或数据，也不负责项目实施与验收。
- 不把技术设计变成全面架构审计；调查和说明到足以建立本次实现共识即可。
