# 项目研发独立审查 v3

这是流程型 skill。目标是判断当前阶段入口是否有足够证据交给用户确认并进入下一阶段。优先发现会造成方向错误、范围遗漏、返工、虚假完成或无法验收的问题；不要重写责任阶段入口。

## 触发与边界

**触发**：用户要求独立审查、复审、检查当前阶段能否确认，或其他研发阶段 skill 调用审查需求、技术方案、任务规划、执行结果或验收入口时使用。

**不触发**：用户要求澄清需求时，调用 `requirements-workshop-v3`，见其 SKILL.md；用户要求设计实现路径时，调用 `tech-design-v3`，见其 SKILL.md；用户要求拆任务时，调用 `implementation-planning-v3`，见其 SKILL.md；用户要求直接实现时，调用 `plan-execution-v3`，见其 SKILL.md。

**与其他 skill 的关系**：本 skill 可由研发阶段 skill 调用，也可单独审查用户给出的真实入口路径。被审查阶段 skill 不可用时，本 skill 仍可基于入口、支撑材料和项目证据完成审查；缺少阶段完成条件时，在报告中记为发现，而不是直接失败。

## 存储与路径契约

- 输入必须是真实阶段入口路径；不接受只有阶段名称、摘要或粘贴片段的审查对象。
- 审查报告放在被审查入口旁的同名支撑目录：`<入口同名目录>/review/REV-编号-阶段英文-slug.md`。
- 首次创建报告使用 [审查报告模板](assets/review-report.md)。
- `REV-*` 编号在同一个 `review/` 目录内递增；阶段英文使用 `requirements` / `tech-design` / `implementation-planning` / `execution` / `acceptance`。
- 普通阶段入口写回 `review` 链接；任务规划审查写回 `plan_review`；执行审查写回 `execution_review`。
- 报告和入口必须双向链接；报告链接被审查入口，入口链接最新审查报告。

## 阶段与流转

审查报告 `status` 只使用：

| 状态 | 含义 | 可进入的下一状态 |
|---|---|---|
| `changes_required` | 存在未解决 `BLOCKER` 或 `HIGH` | `passed` |
| `passed` | 没有未解决 `BLOCKER` 或 `HIGH`，且阶段完成条件有充分证据 | `changes_required` |

发现 `status` 只使用 `open` / `resolved`。

切换条件：

- `changes_required` -> `passed`：所有 `BLOCKER` 和 `HIGH` 均有真实修复证据，复审未发现新的 `BLOCKER` 或 `HIGH`。
- `passed` -> `changes_required`：后续复审发现新的 `BLOCKER` 或 `HIGH`，或原通过依据被项目事实、上游变更、代码差异或运行证据推翻。

`passed` 只表示可以交给用户确认，不表示用户已经确认，也不自动推进责任阶段状态。

## 执行步骤

1. 确认输入：读取真实入口、直接上游入口、入口链接的支撑材料、审查历史和能验证关键声明的项目证据。
2. 确认审查阶段：识别当前是需求、方案、任务规划、执行或验收审查；读取对应阶段的完成条件、用户确认条件和写回字段。
3. 追踪关键声明：从入口结论追踪到支撑材料、上游条目、真实代码、配置、运行结果或验收证据；不能只相信文档自述。
4. 使用怀疑论者视角提出 5-8 个核心问题：优先检查方向、范围、链路、证据、状态、回退、越权修改和虚假完成；不要把格式偏好当作核心问题。
5. 对每个核心问题分级：`BLOCKER` 表示文档无答案、自相矛盾、继续会方向错误、关键范围遗漏、无法执行、虚假完成或无法验收；`HIGH` 表示很可能造成核心返工、用户可见缺陷或重要证据缺失；`MEDIUM` 表示影响局部可靠性或理解但不阻止进入下一阶段；`LOW` 表示整理建议；`PASS` 表示已有明确答案且证据充分。
6. 分类发现：报告严重级别只使用 `BLOCKER` / `HIGH` / `MEDIUM` / `LOW`，`PASS` 不写成发现。默认完整记录 `BLOCKER` 和 `HIGH`；`MEDIUM` / `LOW` 仅在影响用户判断或后续执行时记录。没有问题时明确写“未发现阻塞或高风险问题”，不要为了显得严格制造发现。
7. 写审查报告：每个发现必须包含编号、严重级别、状态、责任位置、问题、影响和可验证修复条件；报告结论与未解决发现保持一致。
8. 写回链接：只更新入口的 `review`、`plan_review` 或 `execution_review` 链接。不要修改阶段正文、阶段状态、任务状态、执行状态、验收状态或用户确认。
9. 复审：责任阶段修正后更新同一报告，保留每轮复审记录；只有修复条件被真实证据满足，才能把发现标记为 `resolved`。

## 校验与门槛

审查完成前必须满足：

- [ ] 审查对象、阶段和范围明确，入口路径真实。
- [ ] 关键声明已查证，不只复述入口自述。
- [ ] 已检查入口、直接上游、支撑材料、真实代码或运行证据之间的链路。
- [ ] 已按阶段读取并应用 [审查清单](references/review-checklists.md)。
- [ ] 所有发现都有具体责任位置、影响和可验证修复条件。
- [ ] 报告 `status` 与未解决 `BLOCKER` / `HIGH` 一致。
- [ ] 入口和报告双向链接。
- [ ] 没有修改责任阶段结论、状态、任务状态或用户确认。

复审时必须比较上一轮报告与本轮证据：若未解决的 `BLOCKER` / `HIGH` 消失但没有修复证据，或修复后引入同等及以上风险，视为质量退步，不得标记 `passed`。

## 失败与回退

- 输入不是真实入口路径：停止审查，要求提供入口路径；不要基于摘要生成正式 `REV-*` 报告。
- 入口缺少阶段完成条件或上游链接：继续审查已有材料，并把缺失项记为发现；不要替责任阶段补写结论。
- 关键证据不存在、命令无法运行或外部系统不可访问：记录证据缺口、影响和恢复条件；缺口影响阶段判断时报告为 `changes_required`。
- 写回入口链接会导致覆盖用户或责任阶段未确认改动时，只创建或更新报告，在最终回复中说明入口链接未写回及原因。
- 复审发现责任阶段需要改变需求、方案、任务契约或执行范围时，只报告回退责任和影响，不替责任阶段执行回退。

## 下沉材料

按需读取 [审查清单](references/review-checklists.md)：

- 需要审查具体阶段的完整检查项时。
- 需要判断跨阶段追踪链路、回退失效、支撑材料或写回边界时。
- 发现可能属于 `MEDIUM` / `LOW`，需要判断是否值得记录时。

## 边界声明

本 skill **不做**：

- 不重写用户故事、技术决策、变更、任务、执行或验收结论。
- 不修改阶段状态、任务状态、调研状态、执行状态或验收状态。
- 不关闭责任阶段的问题，不替用户确认。
- 不为了通过审查降低完成标准。
- 不把审查报告当作需求、方案、任务、执行或验收入口。
