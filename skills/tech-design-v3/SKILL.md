# 技术方案

这是流程型 skill。目标是把已确认需求转成可拆任务的技术契约。方案文档引用需求编号和验收要求，不重写需求正文；方案必须基于真实项目证据，而不是凭空设计。

## 触发与边界

**触发**：用户要求做技术设计、技术方案、实现方案、架构/API/数据/UI 实现设计、验证策略，或需要把已确认需求转成任务阶段可执行契约时使用。

**不触发**：用户还在澄清需求、路线图、用户故事、功能点或验收要求时，调用 `requirements-workshop-v3`，见其 SKILL.md；用户已经要求任务规划、实现、验收或故障排查时，交给对应阶段 skill；用户只要求调研事实且已有 `RT-*` 时，调用 `project-research-v3`，见其 SKILL.md。

**与其他 skill 的关系**：本 skill 可调用 `requirements-workshop-v3`，见其 SKILL.md；可调用 `project-research-v3`，见其 SKILL.md；可调用 `project-development-review-v3`，见其 SKILL.md。调研或审查不可用时，必须记录影响，方案入口不得标记为 `confirmed`。

## 存储与路径契约

- 技术方案入口只在 `workplace/<版本>/tech-design/` 下创建或更新一份；优先使用用户给出的路径，其次复用同一需求或事项已有入口，否则按 `YYYY-MM-DD-功能名.md` 命名。
- 一个已确认需求或事项当前只能有一份方案入口；发现多份时先选择或合并，不继续新增。
- 新建入口使用 [技术方案模板](assets/tech-design.md)。
- 支撑材料放在入口旁的同名目录中，按需创建，不预建空目录或空文件。
- 支撑材料编号使用类型加递增数字：`RT-*` 调研、`EVD-*` 证据汇总、`REV-*` 审查。

## 阶段与流转

| 状态 | 含义 | 可进入的下一状态 |
|---|---|---|
| `discussing` | 方案仍在调查、设计或确认 | `confirmed` / `blocked` |
| `confirmed` | 方案已审查且经用户确认，可进入任务规划或实现 | `discussing` |
| `blocked` | 缺少继续设计或确认的必要条件 | `discussing` |

切换条件：

- `discussing` -> `confirmed`：已确认需求、方案入口、必要支撑材料、独立审查和用户确认全部完成。
- `discussing` -> `blocked`：缺少用户或外部系统才能提供的必要条件，且无法安全假设。
- `confirmed` -> `discussing`：下游证明已确认方案需要改变，或上游需求从 `confirmed` 回退。
- `blocked` -> `discussing`：用户、项目文件或外部系统补齐恢复条件。

## 执行步骤

1. 确认方案入口路径：只在 `workplace/<版本>/tech-design/` 下创建或更新与当前需求或事项对应的一份方案入口。输出完整路径并说明“如需修改请告知，否则继续”，然后继续执行。
2. 校验输入：只接受 `status: confirmed` 的需求入口。读取需求三项核心内容、UI 需求摘要、支撑材料和审查结论；缺少确认需求时返回 `requirements-workshop-v3`。
3. 调查真实项目：检查相关代码、配置、依赖、接口、数据、页面、测试、部署和项目知识，确认当前能力、可复用内容、真实差距和未知项。能查到的事实自己查，不问用户。
4. 写入或更新入口：新建时使用 [技术方案模板](assets/tech-design.md)。入口只保留方案摘要、技术决策、变更清单、验证方案；证据、调研和审查报告放同名支撑目录，并在入口与支撑材料之间双向链接。
5. 讨论缺口：只问会改变主要实现路径、数据归属、兼容、安全、用户体验、范围或验证可行性的问题。相关技术问题一次成组提问，通常 2-5 个；每组都给推荐方案和影响。
6. 形成四项方案内容：方案摘要讲清核心机制和边界；技术决策只记录真实取舍；变更清单给任务阶段明确契约；验证方案写真实可执行方法和可观察证据。
7. 自检、独立审查、用户确认：自检通过后调用 `project-development-review-v3`。审查通过后请用户确认四项方案内容，全部确认后把方案入口 `status` 改为 `confirmed`。

## 校验与门槛

进入下一步或判定完成前必须满足：

- [ ] 入口路径真实，位于 `workplace/`，且一个已确认需求或事项当前只有一份方案入口。
- [ ] 输入需求入口为 `status: confirmed`，方案没有重新定义或复述需求正文。
- [ ] 方案基于真实项目证据，必要调研已完成并回写，支撑材料与入口双向链接。
- [ ] 方案摘要、`D-*`、`C-*`、`V-*` 四项内容互相一致，没有新增第五类核心内容。
- [ ] 每个 `F-*` 和验收要求都有 `C-*` 与 `V-*` 落点。
- [ ] 每个 `C-*` 足以直接拆任务，每个 `V-*` 真实可执行并可观察。
- [ ] 涉及 API、数据、权限、迁移、兼容、异步、AI/Agent、UI 实现或外部依赖时，已读取并应用 [方案细则](references/tech-design-rules.md)。
- [ ] 独立审查通过，用户明确确认方案内容。

审查后修改时，必须比较上一轮入口与本轮入口：若主要实现路径、技术决策、变更落点、验证方案、用户特别关注点或不做范围少了已确认内容且没有明确撤销依据，视为退步，不得进入 `confirmed`。

## 失败与回退

- `discussing` 下发现没有已确认需求：返回 `requirements-workshop-v3`；技术方案入口不得标记为 `confirmed`。
- `discussing` 下证据不足以支撑方案：登记 `RT-*` 并调用 `project-research-v3`；调研结论未回写或为 `blocked` 时，不得确认方案。
- `discussing` 下发现请求跨多个独立需求或事项：先拆分或让用户选择当前事项；未选定前不创建多个方案入口。
- `confirmed` 后上游需求改变或下游证明方案需要改变：把方案入口 `status` 改回 `discussing`、`review` 重置为 `pending`，并说明哪些后续计划、任务、执行或验收确认失效。
- 独立审查不可用或未通过：保持 `discussing`，记录原因和下一步修复条件。

## 提问契约

满足全部条件才问用户：

- 答案会实质改变主要实现路径、数据归属、兼容、安全、用户体验、范围或验证可行性。
- 无法从项目、已有文档、历史对话或调研获得答案。
- 错误假设会导致明显返工、范围错误、用户可见问题、验证失效或风险。

提问时放在回复最后的 `## 需要你确认`，后面不再追加总结。能安全假设时，直接写明假设、依据和影响并继续推进。

## 下沉材料

按需读取 [方案细则](references/tech-design-rules.md)：

- 需要创建支撑材料、调研项或证据汇总时。
- 方案涉及 API、数据归属、权限、迁移、兼容、异步、AI/Agent、UI 实现或外部依赖时。
- 需要判断 `D-*`、`C-*`、`V-*` 写法和覆盖是否合格时。
- 下游回退导致已确认方案需要重开时。

## 边界声明

本 skill **不做**：

- 不修改生产代码、迁移、测试或项目配置。
- 不重新定义已确认需求；方案无法满足需求时返回需求阶段。
- 不把需求正文、调研报告或审查报告复制进方案入口。
- 不创建任务规划、实现计划、验收报告或发布说明。
- 不自动批准调研任务、技术取舍、审查结果或阶段完成。
