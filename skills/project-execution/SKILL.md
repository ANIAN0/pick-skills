# 项目执行

完整理解当前改动目标和已经确定的技术方案，用正确、简洁且符合项目习惯的代码完成改动，并通过与改动相匹配的自测确认功能真正完成。

## 核心原则

- 执行是完成真实改动，不是重新编写需求、技术方案或详细计划。
- 正式需求、方案和任务清单都是可选输入。优先复用已经确认且相互一致的结论；没有文档但当前问题和实现方向已经清楚时，直接执行。
- 当前上下文只有一份明确方案、没有会改变实现的待决项或冲突时，用户要求“开始实施、按此修改、继续开发”就是采用该方案的执行授权，不要求用户重复形式化确认语句。
- 在修改前理解用户想解决的问题、预期结果、方案边界和相关代码。理解到足以正确实现即可，不重复完整的需求或设计流程。
- 实现完整行为和真实调用链，不用 mock、固定返回、临时绕过、空实现或静默降级冒充完成。
- 代码以满足当前改动为限，保持简洁、可读并符合项目现有结构。不顺手重构无关部分，也不为了少改代码而留下明显不完整的实现。
- 自测要在与交付行为匹配的层级证明改动后的真实结果符合预期，不能只因为格式、类型检查或构建通过就宣布功能完成。

## 开始执行

读取当前对话以及已有的问题说明、需求正文、技术方案和任务清单，再检查直接相关的代码、配置、测试和项目约定。已有任务清单时，从清单中的直接链接读取对应需求和方案，不根据相似文件名猜测；链接失效时先确认正确来源，避免混入同一项目的其他并行改动。

如果项目中已经存在与本次改动对应的正式需求、技术方案或任务清单，先检查状态、待决定事项和相互一致性。状态为“已确认”或项目等价状态的正文可直接作为输入；当前方案虽仍标为草稿，但已经没有实质待决项，并且用户在该方案上下文中明确要求开始实施时，可以采用当前方案执行，但执行阶段不修改其确认状态。存在多份可能采用的方案、仍有实质待决项、文档过期或输入冲突时，不能自行选择执行口径，停止并报告需要由哪个阶段处理。

判断来源时使用以下顺序：用户最新明确决定、已确认需求、已确认技术方案、已确认任务清单、当前代码和配置事实。当前实现只能证明现状，不能覆盖已确认的目标行为。用户的新决定与正式正文发生实质冲突时，以用户决定作为当前事实并停止受影响执行；记录需要重新打开的文档，但不在执行阶段改写其内容或状态。

技术方案可以直接进入执行，任务清单从来不是强制中间门禁。已有且仍与当前方案一致的任务清单时，把它作为跨会话进度记忆；旧计划没有链接当前方案或与当前方案不一致时，不再把它作为执行来源，但这不阻止直接按当前方案执行。只有用户需要持久跟踪、多方分工或明确要求规划时，才返回 `project-planning` 更新计划。

开始编码前记录本次采用的用户指令、需求、方案和可选计划，并检查当前工作区差异。当前方案或没有方案时的用户明确目标是范围权威；计划只帮助排序和记忆，不能扩大、缩减或否决方案范围。

存在功能迁移基线时，确认它与当前源、目标工作区和方案实际影响面一致，并读取其中全部源能力迁入项、目标承载面兼容项和契约冲突处置。方案会替换或改变某个页面、主流程、公共组件、协议适配层、状态所有权或数据职责，却没有对应兼容项时，停止编码并报告迁移与设计缺口；不能把迁移账本未写到解释成默认排除，也不能在同一轮切换 skill 修改基线或方案。

## 实现

按已确定的技术方案和项目现有模式完成修改。执行复杂方案时，先从方案中选择一个原子交付单元，不一次铺开整份方案。原子单元以一个可独立观察、独立失败并能在当前工作树中闭环验证的结果为边界；为了打通这个结果可以跨页面、接口和数据层，但不能同时夹带另一个可独立交付的结果。

每个原子单元严格执行同一循环：

1. **界定**：写明它对应的用户结果或系统行为、方案位置、关联的源迁入项或目标兼容项、允许修改的职责范围、明确不包含的相邻工作和完成证据；
2. **实现**：只修改闭合该结果必需的真实调用链；每处生产代码、数据、配置和测试修改都能回指当前单元及其方案来源；
3. **验证**：立即在匹配层级验证该结果，不能把验证推迟到多个单元全部完成之后；
4. **复核**：查看当前完整差异，确认工作树处于可构建或项目等价的一致状态，没有半接入代码和范围外修改；
5. **收口**：记录结果、证据和未解决发现；已有任务清单时更新状态，然后才选择下一个原子单元。

当前单元未通过验证、仍有半成品或无法清楚解释差异来源时，不得开始下一个单元。原子化是执行控制，不要求为每个单元创建文档、分支、提交或向用户逐项确认。

用户可见原子单元必须从真实入口操作到可见结果，证明实际操作对象、权限、状态和结果反馈已经跨层接通。直接渲染组件、调用内部函数或请求单个 API 只能证明对应下层，不足以关闭纵向单元。

跨层集成或高风险公共契约会决定大量后续工作时，第一个原子单元优先选择能验证关键契约的代表性纵向切片。完成聚焦验证、差异复核并恢复到一致状态后，才能展开其余同类单元；不能同时铺开数据库、协议、服务端和页面的大批半成品，最后统一验证。

执行中发现新工作时先分类。只有不改变既定机制、职责和范围，且是闭合当前原子单元不可缺少的接线遗漏，才可纳入当前单元继续；局部实现参数由执行者按项目模式决定。

出现下列任一情况，一律视为方案变化并停止受影响实现：新增方案未定义的数据表或 schema 版本、持久状态、跨进程或跨服务协议、公共 API、权限或安全模型、生命周期状态、后台任务、用户可见行为，改变数据或副作用归属，扩大到当前方案未包含的系统，或实际代码证明方案正在替换未纳入兼容基线的目标承载面。即使执行者认为它“更正确”“是根治方案”或“现有机制有缺陷”，也不能在执行阶段实现。只保存代码证据、受影响原子单元、可能失效的上游位置和建议返回阶段；不修改需求、迁移基线、方案、计划状态，也不在同一轮切换 skill 代替上游拍板。

审查者、测试失败或代码阅读提出的新问题只是一条调查线索。没有已确认上游来源时，记录为范围外发现，不修改代码；不得为了通过审查、消除理论风险或让局部实现更优而引入新机制。

涉及用户界面且已确认方案要求参照或复用现有能力时，修改前查看真实参照页面、组件和交互，按照方案落实页面结构、字段、操作对象、权限表现、结果反馈和视觉状态；修改后再用真实页面比较，不能把“复用”缩减为只复用接口或少量样式。

尊重工作区中已有的用户改动，避免覆盖或改写无关文件。新增代码、测试、配置、迁移或文档，应当确实服务于本次改动。

发生上下文压缩、中断、用户叫停或长时间切换调查方向后，继续前必须重新读取当前方案、可选计划、`git status` 和完整差异，确认正在进行的原子单元、已有半成品和下一步仍在范围内。用户要求停止时立即停止新的修改和命令，只报告当前工作树、已完成验证和安全恢复建议。

## 自测与完成

根据改动性质选择能够证明功能的验证方式。验证层级必须与交付行为匹配：页面功能验证真实运行页面和关键交互；接口功能验证真实路由、鉴权、响应和副作用；迁移、事务或并发要求验证对应数据库行为；纯内部逻辑可以使用聚焦单元测试。低层检查不能替代高层行为，构建通过不能证明页面可用，直接调用函数不能证明 HTTP 接口正确。

当前功能完成的测试证据必须是为本次改动新增或更新的测试，或者由用户、已确认上游文档或项目明确维护规则指定为本次有效基线的既有测试。不能根据测试文件存在、名称相似或历史上曾通过，推断它仍然有效。默认不运行或修改没有上述依据的既有测试，也不把它们的结果作为完成证据；执行阶段不负责全项目回归或评价无关测试质量。

需要时运行专门针对当前改动的目标测试、集成测试、构建、类型检查、lint、真实界面或接口验证，而不是机械要求所有项目执行同一套命令。适合保留的当前改动测试可以作为项目产物；只为临时探查创建的脚本或数据在验证后清理。

测试应覆盖本次改动最重要的成功行为，以及确实可能破坏功能的失败情况或边界。测试失败时查明原因并修复，然后重新验证；不能把由本次代码造成的失败当成环境问题跳过。

使用正在运行的服务、页面或构建产物作为证据前，确认它确实加载了当前工作区的实现。不能用未热更新的旧进程、旧构建或缓存结果证明新代码；未经用户允许不能擅自重启服务，无法确认时将相应行为标记为未验证。

所有原子单元结束后，重新从干净页面、客户端或项目等价初始状态走通本次改动的代表性完整用户路径，并对受影响目标兼容项做回归走查。涉及刷新、恢复、跨轮、取消、审批、权限或并发时，按已确认上游范围走完相应组合路径。这个组合验证检查原子单元接在一起后是否可用，不能由各单元分别通过、合同测试、构建或代码审查推断。

结束前重新查看完整代码差异，并对照当前问题或需求、技术方案和任务清单逐项检查：预期行为是否已经实现，必要修改是否全部完成，代码之间是否真实接通，验证证据是否与交付层级匹配，是否引入无关变化。清单中只有经过实现和相应验证的事项才能标记完成。

如果受权限、外部服务、账号、设备或其他无法控制的条件影响，不能完成关键验证，应明确说明未验证内容、原因和风险，对应任务保持未完成，不能声称功能已经确认完成。

## 独立审查

实现和自测初步完成后，使用两个新的 subagent 检查结果。审查输入同时包含设计符合性来源和受影响目标兼容基线，分别判断“是否按方案实现”和“是否破坏既有能力”；不能让同一份不完整设计同时充当实现、测试和审查的唯一答案。这个审查不能替代实际运行的自测：subagent 只能判断材料是否支持结论，不能凭阅读证明功能已经运行正确。

1. 把当前问题或需求、实际采用的已确认技术方案、任务清单（如有）、完整代码差异、相关项目文件和自测结果交给第一个 subagent，不提供主 agent 的理解或预期答案。让它搜索实现完整性、代码正确性、真实接入和当前改动自测有效性；每个候选问题必须指出相关任务或代码位置、可能违反的行为及影响，不能加入同义问题、无关问题或新的架构建议。候选问题只是调查线索，不是正式缺陷，数量不是完成标准。
2. 把相同输入和候选问题交给第二个 subagent，允许它按需查看直接相关的代码、配置、项目规则和运行证据。要求它逐项记录需求或方案依据、实际代码路径、可复现失败或其他具体证据、影响和分类；分类至少区分“真实实现缺陷”“未有效验证”“上游契约缺口”“已有覆盖”“实现偏好”“前提错误或超出范围”。无法查证时必须明确写“不确定”，不能假设功能正确，也不能凭理论风险要求新增机制。
3. 主 agent 根据完整上下文、代码和实际自测复核分类。只有证据表明当前实现违反已确认行为、没有真实接入或缺少必要验证时才修复并重新自测；没有上游依据、受支持运行路径或具体失败证据的新机制不得写入代码。确认属于上游契约缺口时停止受影响实现，记录证据并等待用户明确要求进入对应阶段，不能由实现审查替设计拍板。
4. 修复影响实现结果或接入链路时，只复审修改区域和受影响路径，不重新强制生成一批全量问题。如果差异只来自措辞或不影响当前功能的实现偏好，不为了让答案完全一致而改代码。

没有正式需求、方案或任务文档时，使用用户的原始改动描述代替，不为了审查补造文档。审查问题和回答不写入生产代码或任务清单；除非用户要求保留，否则不额外创建审查文档。审查只判断当前差异是否满足当前输入，不负责重新设计更完整的架构。

执行完成不表示已经证明不存在未知问题。只有执行输入仍然有效且一致、每个源迁入项和目标兼容项均有实现处置、每个交付结果均已通过原子循环、组合后的真实用户路径和兼容回归取得匹配层级的验证、候选问题已经查证分类、正式缺陷已经修复并重新验证，才能说明“实现完成并可进入验收”。只完成代码或设计内低层检查时，必须使用“代码已实现”“设计内检查通过”或“待真实可用性验证”等准确状态，不能称为功能完成或可交付。除非用户明确要求，不自动提交、推送、部署或修改生产环境。

## 边界

- 不要求先执行 `project-requirements`、`project-design` 或 `project-planning`。
- 不把执行过程变成重复的需求澄清、技术设计或任务细化。
- 不以检查命令通过替代对实际功能的验证，也不要求每次改动都执行成本不相称的完整回归。
- 不自行把未经指定或未随当前需求更新的既有测试认定为有效依据；全项目回归属于后续验收或专门测试阶段。
- 不隐瞒失败、跳过项、方案偏差或无法验证的部分。
- 不擅自扩大修改范围或进行外部发布操作。
