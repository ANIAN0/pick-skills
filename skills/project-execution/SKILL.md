# 项目执行

完整理解当前改动目标和已经确定的技术方案，用正确、简洁且符合项目习惯的代码完成改动，并通过与改动相匹配的自测确认功能真正完成。

## 核心原则

- 执行是完成真实改动，不是重新编写需求、技术方案或详细计划。
- 正式需求、方案和任务清单都是可选输入。优先复用已有结论；没有文档但当前问题和实现方向已经清楚时，直接执行。
- 在修改前理解用户想解决的问题、预期结果、方案边界和相关代码。理解到足以正确实现即可，不重复完整的需求或设计流程。
- 实现完整行为和真实调用链，不用 mock、固定返回、临时绕过、空实现或静默降级冒充完成。
- 代码以满足当前改动为限，保持简洁、可读并符合项目现有结构。不顺手重构无关部分，也不为了少改代码而留下明显不完整的实现。
- 自测要证明改动后的真实行为符合预期，不能只因为格式、类型检查或构建通过就宣布功能完成。

## 开始执行

读取当前对话以及已有的问题说明、需求正文、技术方案和任务清单，再检查直接相关的代码、配置、测试和项目约定。已有任务清单时，从清单中的直接链接读取对应需求和方案，不根据相似文件名猜测；链接失效时先确认正确来源，避免混入同一项目的其他并行改动。不同来源冲突时，根据用户最新表达和真实项目证据判断；冲突会改变功能结果或主要技术方向且无法可靠判断时，再请求澄清。

已有任务清单时直接复用，把它作为范围和进度记忆，不重新展开每项任务的设计。没有清单且改动包含多个容易遗漏的部分时，先维护一份极简工作清单再编码；只有一个明确修改点时直接开始，不额外制造规划阶段。

## 实现

按已确定的技术方案和项目现有模式完成修改。每完成一个连贯部分，就检查其上下游是否真实接通，并及时更新任务清单状态。不要完成第一处修改后就停止；继续处理清单和方案中仍未覆盖的必要工作。

执行中发现实现当前方案不可缺少但清单遗漏的工作时，把它补入清单并继续。如果新发现会改变用户预期、整体实现方向、重要接口、数据归属或兼容方式，暂停相关实现，先更新理解或技术方案，不能静默偏离。

尊重工作区中已有的用户改动，避免覆盖或改写无关文件。新增代码、测试、配置、迁移或文档，应当确实服务于本次改动。

## 自测与完成

根据改动性质选择能够证明功能的验证方式。当前功能完成的自测证据必须专门针对本次改动，例如为当前改动新增或更新的测试、直接接口调用、真实界面操作或其他可观察行为。禁止把项目内并非为当前改动创建或更新的测试文件，作为当前功能正确或已经完成的自测依据。

不要运行或修改项目内未因当前改动而创建或更新的测试文件；执行阶段不负责全项目回归，也不评估既有测试的质量。需要时运行专门针对当前改动的目标测试、集成测试、构建、类型检查、lint、真实界面或接口验证，而不是机械要求所有项目执行同一套命令。适合保留的当前改动测试可以作为项目产物；只为临时探查创建的脚本或数据在验证后清理。

测试应覆盖本次改动最重要的成功行为，以及确实可能破坏功能的失败情况或边界。测试失败时查明原因并修复，然后重新验证；不能把由本次代码造成的失败当成环境问题跳过。

结束前重新查看完整代码差异，并对照当前问题或需求、技术方案和任务清单检查：预期行为是否已经实现，必要修改是否全部完成，代码之间是否真实接通，是否引入无关变化。清单中只有经过实现和相应验证的事项才能标记完成。

如果受权限、外部服务、设备或其他无法控制的条件影响，不能完成关键验证，应明确说明未验证内容、原因和风险，不能声称功能已经确认完成。

## 独立审查

实现和自测初步完成后，使用两个新的 subagent 检查结果。这个审查不能替代实际运行的自测：subagent 只能判断材料是否支持结论，不能凭阅读证明功能已经运行正确。

1. 把当前问题或需求、实际采用的技术方案、任务清单（如有）、完整代码差异、相关项目文件和自测结果交给第一个 subagent，不提供主 agent 的理解或预期答案。让它提出至少 10 个有价值、能够检验实现完整性、代码正确性、真实接入和当前改动自测有效性的问题，不能加入同义或无关问题。
2. 只把相同材料和这些问题交给第二个 subagent。让它依据代码与证据逐题回答；无法从材料判断时必须明确写“不确定”，不能假设功能已经正确。
3. 主 agent 根据完整上下文、代码和实际自测独立判断答案，再与第二个 subagent 的答案比较。如果差异可能意味着漏改、错误实现、未真实接入、无效自测或用户预期没有满足，就继续调查、修复并重新自测，然后重新审查。
4. 如果差异只来自措辞或不影响当前功能的实现偏好，不为了让答案完全一致而改代码。

没有正式需求、方案或任务文档时，使用用户的原始改动描述代替，不为了审查补造文档。审查问题和回答不写入生产代码或任务清单；除非用户要求保留，否则不额外创建审查文档。

独立审查没有发现影响完成结论的问题后，向用户简洁说明完成了什么、做了哪些针对当前改动的自测，以及是否仍有未完成或未验证内容。除非用户明确要求，不自动提交、推送、部署或修改生产环境。

## 边界

- 不要求先执行 `project-requirements`、`project-design` 或 `project-planning`。
- 不把执行过程变成重复的需求澄清、技术设计或任务细化。
- 不以检查命令通过替代对实际功能的验证，也不要求每次改动都执行成本不相称的完整回归。
- 不运行、修改或评价不属于当前改动的既有测试文件；全项目回归属于后续验收或专门测试阶段。
- 不隐瞒失败、跳过项、方案偏差或无法验证的部分。
- 不擅自扩大修改范围或进行外部发布操作。
