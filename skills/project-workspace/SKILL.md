# 项目工作区维护

维护项目当前有效的公共上下文和迭代生命周期：同步项目指令，维护项目规则与路线图，管理 `workplace/` 中的版本目录，并安全归档已完成版本。

## 核心原则

- 本 skill 管理项目级环境，不处理某个具体需求的正文、技术方案、任务清单、代码实现或验收过程。
- `AGENTS.md`、`CLAUDE.md`、`PROJECT_RULES.md` 和 `ROADMAP.md` 表达当前有效的指令、规则与方向；`project-knowledge` 保存系统如何工作等长期可复用事实，两者不要混写。
- 遵循项目已有格式和目录约定。缺少约定时使用本文件给出的最小结构，不为了统一格式重写已有文档。
- 所有移动、覆盖和远程同步都先确认准确来源、目标和差异，保留用户无关修改。
- 不使用状态机、固定编号或复杂的工作区合规清单。

## 项目级文件与目录

默认在项目根目录维护：

```text
项目根目录/
├── AGENTS.md
├── CLAUDE.md
├── PROJECT_RULES.md
├── ROADMAP.md
└── workplace/
    ├── <版本>/
    │   ├── requirements/
    │   ├── tech-design/
    │   └── implementation-planning/
    └── archive/
        └── <已归档版本>/
```

项目已有其他结构时优先沿用，不把缺少某个可选文件或目录直接视为错误。版本名称使用用户明确给出的名称、现有 Roadmap 或项目已有约定，不自行创造版本。项目明确允许多个版本并行时保留多个活动版本，不强制单活跃版本。

需求、设计和计划正文仍按各自 skill 的目录规则创建，工作事项名称优先使用中文。过程调研、审查和变更记录放在相应正文旁的同名二级目录。

## 同步 AGENTS.md 与 CLAUDE.md

使用 `filebrowser-skill` 或项目已有 FileBrowser 工具执行传输，本 skill 负责判断同步对象、方向和冲突。默认远程位置为 `/AGENTS.md` 和 `/CLAUDE.md`；项目已有其他映射时沿用现有配置。

用户要求拉取时，先比较远程文件与本地文件。内容相同则无需覆盖；本地不存在时直接下载；两边内容不同时，说明差异和可能丢失的内容，根据用户明确的权威方向处理，不能静默覆盖本地修改。

用户要求上传时，只上传明确指定且已经核对的本地文件。没有明确上传意图时，不把本地修改自动推送到 FileBrowser。单个文件同步失败不代表其他文件成功或整个同步完成，应分别报告结果。

不要把密钥、令牌或本地私密信息加入指令文件后上传。同步完成后重新读取本地目标文件，确认实际内容与选定来源一致。

## 维护 PROJECT_RULES.md

`PROJECT_RULES.md` 只记录项目级规范：项目出发点、长期原则、明确边界，以及开发者不提前知道就容易做错的重要约定。不要写某个需求的临时偏好、实现步骤、任务进度或通用工程常识。

文件已存在时保留现有结构和表达，只修改用户要求或已经明确确认的规则。新增内容前检查是否重复或与旧规则冲突；修改或删除既有规则时说明影响，不能根据代码习惯自行推断新的强制规则。

文件不存在且用户要求创建时，使用容易理解的简单结构，例如“项目原则与边界”和“开发必须了解的信息”，不添加占位规则，也不限制一次只能修改一条。

## 维护 ROADMAP.md

`ROADMAP.md` 记录项目级方向、版本目标、优先级和当前进展，不展开为具体需求的开发任务清单。沿用项目已有结构；没有文件且用户要求建立 Roadmap 时，用简洁的版本或目标列表开始。

只根据用户明确决定、已经确认的需求变化或真实完成结果更新 Roadmap。存在对应工作文档时使用直接链接，使版本目标能够找到相关需求、设计或计划，但不要复制这些文档的正文。

需求进入、调整优先级、延期、取消或验收完成时，更新对应事项的实际状态和必要说明。无法确定 Roadmap 中哪个事项对应当前工作时先调查或询问，不按相似名称猜测。不要自动规划用户没有决定的项目方向。

## 创建和检查版本工作区

创建版本时先确认项目根目录和版本名称，再建立 `workplace/<版本>/` 以及当前体系需要的 `requirements/`、`tech-design/` 和 `implementation-planning/`。已有目录和文件原样保留，不覆盖或重建。

检查结构时只关注本 skill 管辖的项目级文件、`workplace/` 和 `archive/`，不把普通源码、产品文档、依赖或构建目录当作违规项。发现放错位置、重复版本或链接失效时，先列出准确路径和拟调整动作；会移动、覆盖或删除现有内容且用户没有明确授权时，取得确认后再执行。

不同阶段的正文已经能够通过直接链接找到时，不为追求整齐而搬动。结构服务于查找和协作，不以目录形式本身作为完成目标。

## 归档版本

只在用户明确要求归档某个版本，并且能够准确定位源目录和目标目录时执行。归档前检查：对应开发是否已经验收并提交、Roadmap 是否反映真实结果、源目录是否存在、`workplace/archive/<版本>/` 是否冲突，以及源目录中是否仍有明显未处理的工作。

归档默认把整个 `workplace/<版本>/` 原样移动到 `workplace/archive/<版本>/`。不要在归档过程中批量删除测试、审查、问题、日志、零字节文件或其他材料；临时产物应在项目验收时根据真实归属清理，无法确认价值的文件宁可保留。

目标目录已存在、版本仍在开发、相关改动尚未提交或移动会覆盖用户内容时停止，说明具体问题，不合并目录、不覆盖、不部分归档。移动完成后重新检查源路径、目标路径、Roadmap 链接和 Git 状态，如实报告仍需提交的归档变更。

## 边界

- 不修改具体需求、技术方案、任务清单、生产代码或验收结论。
- 不替 `project-knowledge` 判断或摄入长期知识，归档也不强制触发知识抽取。
- 不自动推送 FileBrowser、Git 远端或部署环境。
- 不删除归档版本，不在归档时进行推测性的批量清理。
- 不为了满足固定目录形式覆盖项目已有约定或用户文件。
