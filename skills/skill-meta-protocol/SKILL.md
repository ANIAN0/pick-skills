# Skill 元协议

本协议只在新建、重构、审查 skill，或排查"改动为什么产生了意外副作用"时使用；不参与任何具体任务的执行。它的唯一目的：让仓库里所有 skill 共享同一套结构假设，使"改一个模块"的影响范围可预测，而不必每次重读全文确认会不会牵连别处。

## 触发与边界

**触发**：新建 skill；重构或审查已有 skill 的 SKILL.md 结构；判断一次改动的影响范围；判断某个具体 skill 属于流程型/工具型/知识型中的哪一种；给某组 skill 设计路由文档。

**不触发**：执行某个具体 skill 的实际任务——具体 skill 的 SKILL.md 已经包含它运行所需的全部规则引用，不需要在任务执行时临时加载本协议。

**本协议不是三种形态之一**：它不套用自己给"流程型/工具型/知识型"定义的标准模块清单；正文只留每次使用都要看的内容，参考类内容下沉到 `references/`。

## 自包含契约

本协议是一个可以独立分发的 skill 包：`skills/skill-meta-protocol/` 目录本身包含运行它所需的全部文件，不依赖仓库根目录的任何文件。`references/SKILL_template.md`、`references/glossary.md`、`references/optional_modules.md`、`references/CHANGE_CHECKLIST.md`、`references/MIGRATION_GUIDE.md` 均在本目录内，改动或分发本 skill 时一并携带。

新建或重构的具体 skill 同样必须满足这条契约：一个 skill 声明自己"能做 X"，就必须在自己的目录内带齐完成 X 所需的全部说明、模板、脚本和参考文件；可以在 SKILL.md 里*引用*另一个 skill 的入口作为协作项（见"跨 skill 引用规则"），但不能把自己完成任务的必经步骤指向仓库级或另一个 skill 目录内部的文件。判断标准：把这个 skill 的目录整个复制到另一个仓库，它是否还能按自己 SKILL.md 写的步骤走完全程。走不完，就是自包含契约的违反。

## 表达规范（判断原则；完整定义与例子见 glossary）

结构对了（内容放对模块）不等于表达对了（模块内怎么写）。改动 SKILL.md 后，用以下判据自查；每条的完整定义、正反例见 [references/glossary.md](references/glossary.md)，此处只留判断本身：

- **可预测性**：同一类任务跑两次，agent 是否走同一条处理路径？读起来完整但每次细节漂移，不合格；读起来简略但每次精确复现，合格。
- **渐进展示**：内容分步骤类（每次执行都要看，留在 SKILL.md）和参考类（按需查阅，超过几条就下沉到 `references/*.md`，主文件只留一句指向它的话）。判断测试：这部分内容是不是只在某个分支场景才会被用到？
- **引用深度不超过一层**：SKILL.md 可以指向 `references/*.md`，但 `references/*.md` 之间不应再相互链接形成第二层——每多一层，agent 判断"要不要继续往下读"的路由成本和出错概率都会上升。
- **单一权威来源**：一条规则只能有一处权威定义，其余提到它的地方只能引用、不能复述。发现同一条规则有两种措辞时，保留更精确的一个，删除另一个，原位置改成引用句。
- **主导词**：反复出现的复合描述收敛成一个词，只在首次出现时定义，之后全篇统一使用。
- **规则可执行性测试**：写完一条规则，问"没有它 agent 大概率会怎么做"和"加了它这个行为真的会不一样吗"。两个答案都指向"没变化"，说明规则要么冗余要么不够具体。
- **借口对照表**：记录 agent 实际用来软化执行硬规则的说法和对应反驳；仓库级通用借口收在 glossary，某个 skill 特有的借口下沉到该 skill 自己的 `references/excuses.md`。

## 适用范围与 skill 三种形态

仓库内的具体 skill 分三种形态，共享同一套槽位定义和命名规则：

- **流程型（process）**：有明确阶段顺序、入口文档、状态机和阶段间确认。必须使用"阶段与流转"和"失败与回退"模块。
- **工具型（tool）**：封装一个外部工具或 CLI 的调用方式，没有跨会话状态机。不需要"阶段与流转"，仍需要"触发与边界""执行步骤""边界声明"。
- **知识型（knowledge）**：维护一份随时间积累的结构化知识库。需要"存储结构""写入门槛""读取与查询""校验"，通常不需要"阶段与流转"。

判断依据：是否存在"用户确认才能进入下一步"的阶段切换（→流程型）；还是只封装单次可重复调用的能力（→工具型）；还是主要任务是积累和检索长期有效的结构化内容（→知识型）。一个 skill 可以同时具备多种形态特征，按主要职责选骨架，次要部分作为该骨架下的一个模块出现，不另起一套结构。

## 标准模块清单

每个模块对应 SKILL.md 中的一个二级标题，职责互斥。括号内标注哪些形态需要它：必选标注为"必"，按需标注为"选"。

| 模块 | 职责（只回答这一个问题） | 流程型 | 工具型 | 知识型 |
|---|---|---|---|---|
| 触发与边界 | 什么情况下使用本 skill，什么情况下明确不使用 | 必 | 必 | 必 |
| 环境配置契约 | 本 skill（或本 skill 所属的一组 skill）依赖哪些项目级外部配置，配置从哪里读；机制见 [references/optional_modules.md](references/optional_modules.md) | 选 | 选 | 选 |
| 存储与路径契约 | 文件/数据放在哪里，路径怎么生成，命名规则是什么 | 必 | 选 | 必 |
| 阶段与流转 | 有哪些阶段/状态，什么条件下能从一个状态切到另一个 | 必 | 不适用 | 选 |
| 执行步骤 | 拿到一个具体任务后，按什么顺序做 | 必 | 必 | 必 |
| 校验与门槛 | 进入下一步或判定完成前必须满足的检查项 | 必 | 选 | 必 |
| 失败与回退 | 出错、受阻或需要撤销已确认结论时怎么处理 | 必 | 选 | 选 |
| 提问契约 | 什么情况下才允许向用户提问，问题怎么呈现 | 必 | 选 | 选 |
| 证据与完成定义 | 什么样的结果才能标记为"完成"，证据要求是什么 | 必 | 选 | 必 |
| 边界声明 | 本 skill 明确不做的事 | 必 | 必 | 必 |

"不适用"表示该形态原则上不会用到这个模块；"选"表示视具体 skill 的复杂度决定，模块过于单薄时可以并入相邻模块，但不能反向把一个模块拆成两个标题表达同一职责。

## 模块内容互斥规则

- "存储与路径契约"只定义路径和命名，不描述什么时候该读写哪个路径——那是"执行步骤"或"阶段与流转"的职责。
- "环境配置契约"定义本 skill 依赖哪些项目级外部配置、从哪个路径读取、必需字段的含义和最小示例；这些内容必须随本 skill 单独分发，不能把字段权威定义留给外部生成器。它不和"存储与路径契约"混写。
- "阶段与流转"只定义状态值和切换条件，不描述切换时具体做什么操作——那是"执行步骤"的职责。
- "校验与门槛"只列检查项和通过/不通过的判据，不描述不通过时怎么办——那是"失败与回退"的职责。涉及审查-修订多轮迭代循环的 skill，还需追加"相比上一轮是否退步"的质量轨迹判据，机制见 [references/optional_modules.md](references/optional_modules.md)。
- "失败与回退"只描述异常路径处理，不重新定义正常状态机；只能引用已定义的状态值，不能发明新状态。
- "证据与完成定义"只定义"完成"的证据标准，不描述具体怎么生成证据——那是"执行步骤"的职责。

违反信号：同一条规则出现在两个模块里；某个模块标题是"执行与校验"或"流程与异常"这种合并了两个职责的名字。出现时应该拆开，而不是接受它。

## 差量声明

"提问契约""证据与完成定义"这两个模块存在同一种情况：本协议给出的是行为性惯例——一个训练良好的 agent 默认就会做得八九不离十（合理提问、如实举证），协议只是把这些默认行为标准化、统一措辞，让仓库里不同 skill 的表现方式一致，不是补上一个 agent 本来做不到的能力。

这条判断很重要，因为它决定了"能不能只写一句引用"是否违反自包含契约：

- **如果缺了这份说明，agent 大概率也不会做出明显更差的行为**（提问契约、证据与完成定义都属于这类）→ 具体 skill 没有特殊差异时，**整个模块标题直接删除，不留任何占位句**——包括"遵循 skill-meta-protocol"这类引用句，也包括"无特殊要求，按常规判断处理"这类自足但没有信息量的句子。这两种写法对执行任务的 agent 都不提供任何行为指引，留着只是噪音，和"标准模块清单"里对"环境配置契约"早已说明的"不需要为了以后可能用而强行填写占位内容"是同一条规则的延伸。这称为**差量声明**：有差异就只写差异，没有差异就整节不出现。
- **如果缺了对应内容，任务本身做不完或产出会缺失**（比如环境配置契约——不知道项目用什么issue系统，这一步直接卡住）→ 这是功能性依赖，不适用差量声明，必须按"自包含契约"和"跨 skill 引用规则"处理：要么把内容内联/复制进本 skill 自己的目录，要么明确这是用户项目自身要提供的输入（不依赖某个 skill 生成），并写清对方不可用时的退化路径。

判断一个模块该走哪条路的问题只有一个："如果这份说明不存在，agent 会不会给出明显更差、甚至无法完成任务的行为？"答案是"不会，顶多不够统一" → 差量声明（无差异则整节省略）；答案是"会，任务会卡住或产出缺失" → 功能性依赖，走自包含契约。

**"必选"不等于"必须有文字"只适用于行为性惯例模块**：提问契约、证据与完成定义这类模块没有特殊差异时可以整节省略。结构性必选模块（触发与边界、执行步骤、边界声明，以及该形态完成任务必需的存储、流转、校验、失败处理）必须在最终 SKILL.md 中留下可执行内容；缺失时不能用"已判断过无需文字"解释。审查者要在 [references/CHANGE_CHECKLIST.md](references/CHANGE_CHECKLIST.md) 中核实省略是否只发生在允许差量声明的模块上。

## 命名与状态值规则

- 阶段/任务状态优先从这个集合里选，不够用才扩展：`discussing` / `confirmed` / `pending` / `in_progress` / `done`（完成且已验证）/ `not_verified`（完成但验证条件不满足）/ `blocked`（当前无法继续）。
- `done` 只能用于有真实验证证据支撑的完成；"看起来做完了但没验证"必须是 `not_verified`。任何具体 skill 不允许放宽这条。
- 编号前缀按内容类型区分，不按 skill 区分：`F-*` 功能/需求项、`D-*` 决策、`C-*` 变更、`T-*` 任务、`V-*` 验证、`RT-*` 调研、`REV-*` 审查、`DEF-*` 缺陷、`EVD-*` 证据、`LOG-*` 日志。需要新前缀时先确认现有前缀语义是否已覆盖。
- 路径中的日期统一用 `YYYY-MM-DD`，正式产出中不留尖括号占位符。

## 提问契约（通用版）

只有当答案无法从项目文件、对话历史、工具输出或可靠外部来源获得，且错误假设会实质改变范围、结果或用户体验时才提问。能查证的就去查证；能基于明确依据做出合理假设的，直接假设并说明依据。

必须提问时：一次只问当前最关键的一个问题；给出推荐选项和不同选择的影响；问题放在回复最后单独的 `## 需要你确认` 区块，该区块之后不再附加其他内容。

具体 skill 有特殊提问限制时，按"差量声明"处理：只在自己的"提问契约"模块写差异部分。

## 证据与完成规则（通用版）

- 结论必须能追溯到真实来源：项目文件、命令输出、工具返回、可靠外部材料。不得凭空声称。
- 不得用 mock、stub、占位数据、样例返回伪装成真实验证结果。
- 自动化检查（lint、build、typecheck）只能证明它实际覆盖的部分，不能替代它没测试到的行为验证。
- 标记完成前，对照本 skill 自己的"校验与门槛"模块逐项自检；发现问题就地修复后再标完成。

具体 skill 有额外、更严格的证据要求时，按"差量声明"处理：只在自己的"证据与完成定义"模块写额外部分。

## 多入口与领域扩展

多入口路由文档和领域元协议都只在对应复杂度已经出现时创建。具体机制见 [references/optional_modules.md](references/optional_modules.md)；不要为尚未出现多入口或领域共性问题的 skill 组预先创建文件。

## 跨 skill 引用规则

一个 skill 需要复用另一个 skill 的能力时：

- 只引用对方的入口和输出契约（它接受什么、产出什么），不复制对方内部的执行步骤，也不能把自己完成任务的必经步骤建立在"对方目录内部文件必须存在"之上——那会违反上面的自包含契约。协作是可选的增强，不是完成任务的前提；如果对方 skill 不可用，本 skill 应该能明确说明"这一步跳过"或退化处理，而不是直接失败。
- 引用格式统一为："调用 `<skill-name>`，见其 SKILL.md"。不维护一份"谁调用谁"的关系图——应该能从各 skill 的"触发与边界"模块直接读出来。
- 两个 skill 出现双向依赖（A 调用 B，B 也调用 A）是设计信号，应该拆出第三个更小的 skill 或回到本协议讨论边界，而不是接受循环依赖。

## 改动影响自检

修改某个具体 skill 之前，按 [references/CHANGE_CHECKLIST.md](references/CHANGE_CHECKLIST.md) 的影响范围表预判同步检查点；如果一次改动同时命中多处，先重新评估改动方案是否跨越了模块边界。

## 与配套文件的关系

本协议正文只放"判断和决策时要用的原则"，以下文件均在本 skill 目录内，各自承接不同的下沉内容：

- [references/SKILL_template.md](references/SKILL_template.md)：据本协议生成的脚手架，可直接复制改名使用。
- [references/glossary.md](references/glossary.md)：表达规范涉及词汇的完整定义、正反例对照。只在写新 skill 或怀疑用词不一致时查阅。
- [references/optional_modules.md](references/optional_modules.md)：标准模块清单里标注"选"、且展开后篇幅较长的模块（环境配置契约、多轮迭代质量轨迹）的完整机制。只在具体 skill 命中对应场景时查阅。
- [references/CHANGE_CHECKLIST.md](references/CHANGE_CHECKLIST.md)：把本协议的判断原则转成可逐项打钩的操作清单，改动 SKILL.md 前后过一遍。
- [references/MIGRATION_GUIDE.md](references/MIGRATION_GUIDE.md)：把已有 skill 套进标准模板时的迁移步骤，只在批量改造存量 skill 时查阅。

## 边界声明

本协议**不做**：

- 不参与任何具体任务的执行，不替代具体 skill 的 SKILL.md。
- 不维护仓库里"谁调用谁"的关系图（见"跨 skill 引用规则"）。
- 不对具体 skill 的内容正确性背书——本协议只管结构和表达，不管某个 skill 的领域知识是否准确。
- 不提供自动化的合规检测工具；[references/CHANGE_CHECKLIST.md](references/CHANGE_CHECKLIST.md) 是人工/agent 逐项核对清单，不是可执行脚本。
- 不为尚未出现多入口问题的 skill 组预先创建路由文档。
