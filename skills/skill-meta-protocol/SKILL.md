# Skill 工程

把 Skill 当作一组按需加载、改变 Agent 行为的运行指令来维护。Skill 可以约束同一个 Agent 当前阶段的职责，也可以交给独立 Agent 执行；它不等同于函数、固定流水线节点或一份必须套用统一章节的文档。

本 Skill 是创建和演进其他 Skill 的工作入口，不是其他 Skill 执行任务时必须加载的公共协议。外部脚手架、模板和格式校验器可以帮助初始化或检查文件，但不能证明职责边界正确，也不能证明修改后的 Agent 行为更好。

修改本 Skill 自身时也执行本文流程。不能因为一条规则已经写进本文，就把它当作自身正确性的证据。

## 先还原真实使用方式

修改任何 Skill 前，先从当前平台、仓库和调用方回答：

- 谁会触发它：用户直接请求、Agent 自动匹配、编排 Skill，还是另一个阶段 Agent；
- 使用时由同一个 Agent 连续切换职责，还是为它创建新的 Agent 或任务；
- Agent 实际会加载哪些文件和上下文，哪些材料只通过路径、产物或工具结果传递；
- 它允许读取和修改什么，是否包含外部写入、删除、提交、部署或其他副作用；
- 它可以独立使用，还是属于一组由编排者组合的阶段能力；
- 它怎样结束，结果只存在于当前回复，还是需要形成文件、状态或其他可复用材料。

读取目标 Skill 的 `description`、正文、界面元数据、直接调用方、相关脚本和参考文件；修改已有 Skill 时再检查相关 Git 历史、用户反馈、原始输出、测试和运行记录。不能仅根据 Skill 名称、章节结构或预想的流水线推断其实际使用方式。

如果这些事实仍不清楚，并且不同答案会改变 Skill 的职责、权限或拆分方式，先调查调用环境；无法调查时向用户确认最关键的一项，不先按熟悉的 Skill 形态重写。

## 明确本次改动是什么

先把任务归入一个主要类型：

- **创建**：当前没有对应 Skill，需要建立新的按需行为；
- **修复**：已有职责不变，但某个真实场景没有按预期工作；
- **扩展**：在原职责内增加新的适用场景、工具或材料；
- **契约变更**：触发条件、职责、权限、输入、结果或完成边界发生变化；
- **结构重构**：目标行为原则上不变，只调整指令和资源的组织；
- **拆分或合并**：改变 Agent 选择和加载 Skill 的边界；
- **淘汰**：能力已经被取代、合并或不再使用。

一次工作可以涉及多个类型，但必须指出哪个是主要变化。不要把局部行为修复、职责扩张和全文结构重写混在一次改动里；确实不可分时，先说明依赖关系和需要共同验证的行为。

## 从实际问题建立证据

修改已有 Skill 时，先用最短形式记录：

```text
场景：
当时加载的 Skill、上下文和调用方式：
实际行为：
期望行为：
造成的影响：
来源或复现证据：
```

优先使用用户提供的真实任务、原始对话、Agent 输出、文件差异和工具结果。根据文字自行想象的问题只能作为待验证假设，不能直接推动重构。

在安全且成本合理时，用相同调用方式和尽量干净的上下文复现问题。用户已经提供多次一致表现、原始证据充分，或错误包含不可接受的副作用时，不为了满足复现形式重复执行风险动作。

根据根因决定改哪一层：

| 现象 | 优先检查 | 常见处理 |
|---|---|---|
| 应触发但没有触发，或无关请求误触发 | `description`、相邻 Skill 的描述、路由方式 | 修正触发措辞或消除入口重叠 |
| 已触发，但顺序、判断或完成方式持续错误 | `SKILL.md` 中直接控制该行为的内容 | 局部改写、删除冲突规则或补充可判断边界 |
| 缺少项目知识、协议、格式或输入 | 调用方提供的上下文、`references/`、前置条件 | 补真实资料、输入契约或缺失时处理 |
| 同一机械操作反复被临时编写且容易出错 | `scripts/` 或确定性工具 | 下沉为脚本并实际测试 |
| 一部分指令经常不需要、互相干扰或需要不同权限 | Skill 边界、Agent 隔离方式、编排者 | 评估拆分、合并或改由独立 Agent 执行 |
| 错误来自平台、模型、工具权限或外部服务 | Skill 外部运行环境 | 修复外部问题或明确限制，不用提示词伪装修复 |
| 同样输入偶发一次偏离，无法稳定复现 | 上下文差异和模型波动 | 暂不修改或只记录观察，避免为单次波动增加永久规则 |

一次失败不自动等于缺少一条规则。先找现有规则是否冲突、重复、放错加载层级，或问题是否根本不属于 Skill。

## 创建新的 Skill

创建前先确认 Skill 确实是合适载体：

- 通用 Agent 已经能稳定完成、没有项目专属知识、重复流程或特殊风险时，通常不需要 Skill；
- 只需要提供事实和规范时，优先考虑参考资料；
- 只需要稳定执行确定性操作时，优先考虑脚本或工具；
- 需要长期约束某个仓库内所有任务时，先判断项目规则是否比按需 Skill 更合适；
- 需要按用户意图加载一组专门知识、工作方式、工具或权限边界时，才创建 Skill。

至少取得以下使用样例；用户的真实样例优先，Agent 自己生成的样例只能作为候选：

- 一个最常见、应该触发的请求；
- 一个靠近职责边界、仍应触发或需要转交的请求；
- 一个看起来相似但不应触发的请求。

根据样例写清最小运行契约：

- Agent 在什么请求和上下文中加载它；
- 加载后必须改变哪些默认行为；
- 完成任务需要什么输入、工具、知识或权限；
- 什么结果才表示本次调用完成；
- 哪些相邻职责不属于它；
- 无法继续时怎样报告或退化。

先实现通过这些样例所需的最少内容。章节根据 Agent 执行任务时需要回答的问题自然组织，不为了统一外观添加空模块、状态机、固定步骤、确认轮次或附属文档。只有 Agent 执行时确实需要的详细知识、脚本和资产才进入 Skill 包。

## 维护和迭代已有 Skill

先定位问题对应的最小行为和最小指令范围，再修改：

1. 保留仍然成立的职责、结构和措辞；
2. 优先修改直接导致问题的一段，不顺便统一全文风格；
3. 新规则与旧规则表达同一件事时，替换或合并旧规则，不继续叠加；
4. 一条规则必须改变某个可以说明的 Agent 选择；只重复常识、强调态度或要求“合理判断”的内容不保留；
5. 需要补充罕见分支细节时，判断它是否应按需放入参考文件，而不是让所有调用都加载；
6. 可确定、重复且容易写错的操作移入脚本，不依赖 Agent 每次重新生成；
7. 修改 `description` 时同步检查相邻 Skill 和直接调用方，避免修复漏触发后制造误触发；
8. 修改权限、副作用、输入输出或完成定义时，按契约变更处理，不伪装成措辞优化。

如果一个问题只能通过持续增加例外规则勉强压住，停止继续补丁，检查是否误判了职责、调用上下文、工具能力或 Agent 隔离方式。

## 判断是否需要结构重构

以下情况可以推动结构重构：

- 多个有证据的问题共同来自同一组织缺陷，例如关键规则分散冲突，或罕见内容挤占每次加载的上下文；
- Agent 的真实调用方式已经改变，现有正文仍按旧方式组织；
- 职责、权限或输入输出契约已经由用户明确改变；
- 拆分、合并或编排调整要求重新安排加载边界；
- 当前结构让修改无法局部完成，任何小改动都会触碰大量无关内容。

以下理由本身不足以重构：

- 出现了新的模板或最佳实践；
- 其他 Skill 使用不同章节；
- 文档看起来不够整齐；
- 审查者偏好另一种表达方式；
- 单个问题可以通过局部修改解决；
- 希望一次性预防尚未发生的所有问题。

重构前先列出必须保持的行为、允许改变的行为和已知故障案例。尽量把“移动和整理内容”与“改变行为契约”分开；无法分开时明确说明。重构后不能只验证格式和链接，必须重新检查这些行为。

## 判断拆分与合并

Skill 的边界取决于哪些指令应该在同一个 Agent 上下文中一起生效，不取决于一个流程有多少步骤。

出现以下信号时考虑拆分：

- 用户或编排者会独立选择其中一部分；
- 不同部分需要不同 Agent、上下文隔离、权限或副作用授权；
- 大量调用只需要其中一部分，其他内容持续占用上下文或干扰判断；
- 某部分被多个不相关工作流独立复用；
- 两部分的触发条件、完成方式或失败处理明显不同；
- 可以明确说明拆分后怎样提供必要原始上下文或结果。

出现以下情况时通常保留在一起：

- 同一个 Agent 完成任务时必须同时理解全部约束；
- 拆分后必须传递无法可靠外化的隐藏推理才能继续；
- 两部分从不独立触发，拆分只增加路由；
- 新名称和描述无法让 Agent 稳定选择；
- 所谓边界只是正文中的先后步骤。

两个 Skill 长期处理相同请求、经常同时加载或依赖互相覆盖对方的遗漏时，优先评估合并或重新划分边界，不继续通过扩大 `description` 竞争触发。

对于编排 Skill 和阶段 Skill：

- 编排 Skill 负责选择阶段、提供上下文、检查产物、处理回退；
- 阶段 Skill 负责被选中后的工作，不复制整套编排逻辑；
- 阶段之间可以传递文件、代码、工具结果或当前对话中的明确输入，不强制每个阶段都创建持久文档；
- 使用新 Agent 隔离阶段时，传递足以重新建立判断的原始材料，不只传上一个 Agent 的结论摘要；
- 下游发现上游问题时，返回证据并由调用方重新进入上游职责，不在当前阶段悄悄改写上游。

## 验证修改

按实际改动选择验证，不把所有检查机械套在每个 Skill 上。

静态检查只能证明对应文件有效：

- frontmatter 能解析，名称与目录满足当前平台要求；
- `description` 与正文职责一致；
- 引用文件和直接路径存在；
- 界面元数据与当前 Skill 一致；
- 新增或修改的脚本能够真实运行，并覆盖其重要失败分支；
- 调用方、安装清单、文档和测试没有继续引用已删除或改名的入口。

行为验证至少覆盖：

1. 本次问题对应的场景；
2. 一个最接近且修改前正常的场景；
3. 一个不应触发或不应越权的邻近场景；
4. 修改了跨 Skill 契约时，一个真实调用方或编排场景。

验证 Agent 行为时，尽量使用新的上下文或独立 Agent，按真实用户和调用方的方式提供 Skill、请求和原始材料。不要把本次诊断、预期修复机制或标准答案提前泄漏给执行者。验证必要行为、禁止行为、文件和副作用，不要求自然语言逐字一致。

无法进行行为验证时，可以完成静态修改，但必须明确标记“仅完成静态校验，行为尚未验证”，不能把格式通过声称为问题已经解决。

## 保留必要的维护记录

默认使用 Git 历史记录改动，不为每个 Skill 创建需求文档、CHANGELOG、决策目录或版本体系。提交说明至少让后来者知道：

```text
问题：什么真实场景失败
原因：问题位于哪一层
修改：为什么选择这次最小变更
验证：实际检查了什么
未确认：还有什么没有证明
```

当同一 Skill 已经反复修改、问题需要跨会话跟踪，或仅靠提交无法还原“什么输入产生了什么错误行为”时，才维护一份案例账本。沿用仓库已有位置；没有约定时放在运行 Skill 包之外的 `maintenance/<skill-name>.md`，避免维护过程材料进入每次执行上下文。

案例账本只追加或更新可复现行为，不写流水账：

```text
案例编号：
请求与必要上下文：
实际错误：
必须发生：
禁止发生：
证据：
当前状态：
关联提交：
```

平台或仓库已经有明确发布和兼容机制时沿用；没有时使用 Git 提交或标签标记已验证基线，不额外引入形式化版本状态。

## 淘汰 Skill

确认目标 Skill 已被替代、合并或不再具有独立触发场景后，先搜索：

- 其他 Skill 和编排者的直接引用；
- 界面元数据、安装清单、锁文件和分发配置；
- 项目文档、示例、测试和自动化；
- 用户项目中可能仍使用的名称、路径和产物。

根据真实使用情况选择直接删除、保留兼容入口或先迁移调用方。删除或重命名时同步处理已确认的直接引用；无法确认外部使用者时明确兼容风险，不声称已经无影响。

## 完成与边界

完成一次 Skill 工程任务时，说明：

- 发现的真实问题或创建依据；
- 为什么选择创建、局部修复、扩展、重构、拆分、合并或淘汰；
- 改变了哪些 Agent 行为和加载边界；
- 做过哪些静态与行为验证；
- 哪些结论仍未验证。

本 Skill 不做：

- 不以统一章节、文件数量或模板符合度代替行为正确性；
- 不保证概率性 Agent 在所有上下文中产生相同文字；
- 不把领域事实错误自动归因于 Skill 结构；
- 不用提示词掩盖缺失的工具能力、权限或外部服务；
- 不因为正在维护 Skill 就自动获得生产写入、外部操作或其他未授权副作用权限；
- 不要求其他 Skill 在正常执行时加载本 Skill。
