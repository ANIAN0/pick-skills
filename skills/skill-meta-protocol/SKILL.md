# Skill 元协议

本协议只在新建、重构、审查或排查"为什么改动产生了意外副作用"时使用。它不参与任何具体任务的执行——具体 skill 在自己的 SKILL.md 中直接写明需要的规则，不要求运行时额外加载本协议，以避免不必要的 token 成本。

本协议的唯一目的：让仓库里所有 skill 共享同一套结构假设，使得"改一个模块"这件事的影响范围可以被预测，而不必每次重新阅读整份文件去确认会不会牵连别处。

## 为什么需要这份协议

一个 skill 的 SKILL.md 一旦变大，最常见的失控模式是：同一条规则在文件里出现了两次轻微不同的措辞；一个章节悄悄承担了另一个章节的职责；改动一处描述时，另一处依赖它的描述忘了同步。这些问题的根源都是"模块边界没有显式声明"。

本协议要求每个具体 skill 把内容拆分到固定的章节槽位中（见下文"标准模块清单"），每个槽位只回答一个问题，槽位之间不重复信息、不交叉引用对方的细节（只能引用结论或路径）。这样，当你只想改"失败时怎么办"，你能确定只需要改"失败处理"这一节，而不必通读全文确认有没有别处也写了类似的话。

## 表达规范：不只是分对模块，还要写得对

前面几节解决"内容该放进哪个模块"（结构层）。这一节解决"放进模块之后，这段话该怎么写"（表达层）。两层互相独立，结构对了表达可能仍然差，表达好了结构也可能仍然乱——改动时两层都要过一遍。

**唯一判据：可预测性。** 判断一段 SKILL.md 写得好不好，不是看它读起来是否专业、是否详尽，而是看同一类任务跑两次，agent 是否走了同一条路径。读起来很完整但每次执行细节都在漂移，是没有用的；读起来很简略但每次都精确复现同一行为，是合格的。改动后自问："这段改动让 agent 下次遇到同类情况，会不会做出和这次不一样的选择？"如果会，说明描述还不够具体，不是篇幅不够，而是判据不够可检验。

**渐进展示：按"多久用一次"分层，不按主题分层。** 一个模块内部的内容还要再分两类：

- **步骤类**：有顺序、有完成判据的动作，agent 每次执行都要看。这类内容留在 SKILL.md 主文件里，且必须能回答"做到什么程度算完成"——判据要可检验（比如"每个被修改的状态值都已在改动影响自检表里核对过"），不能是模糊的"产出一份清单"。
- **参考类**：定义、规则、术语表、配置示例，按需查阅，不是每次都要重新读一遍。这类内容超过几条就应该下沉到同目录下的 `references/*.md`，主文件里只留一句指向它的话（就像本文件用 `references/glossary.md` 承载详细词汇定义）。

判断该不该下沉的简单测试：如果这部分内容只在某个分支场景才会被用到（比如"迁移旧版本数据时才需要看的字段对照表"），说明它是少数分支才走到的参考材料，应该下沉，不要让所有调用路径都背着它的 token 成本。

**single source of truth（单一权威来源）。** 一条行为规则只能有一处是它的权威定义；其余提到它的地方只能引用，不能复述。这是"模块内容互斥规则"在表达层的延伸——互斥规则保证规则不会被拆到两个模块里同时定义，single source of truth 保证哪怕只在一个模块里，也不会被写两遍措辞略有差异的版本。改动时如果发现同一条规则有两种说法，以更精确、更新的那个为准，删除另一个，在原位置改成引用。

**主导词：把反复出现的复合描述收敛成一个词。** 如果某个概念在文件里反复用一句话或一个短语描述（比如反复写"先写一个会失败的测试，确认失败原因正确，再写最小实现让它通过"），应该把它收敛成一个词并只在第一次出现时定义清楚，之后全篇统一只用这个词（例如 `RED → GREEN → REFACTOR`，本协议和 `plan-execution-v3` 已经在这样做）。好的主导词能借用模型预训练里已有的理解，减少每次都要重新解释的篇幅，同时让同一个词在所有 skill 里指向同一件事——这也是为什么"命名与状态值规则"一节要求状态值和编号前缀全仓库统一，不允许各 skill 自造同义词。

详细的词汇定义、命名示例和反模式对照表见 [references/glossary.md](references/glossary.md)，不在本节展开。

**规则可执行性测试：写完一条规则，先想清楚它的对照场景。** 可预测性判据容易停留在"读起来很有道理"的层面，真正检验一条规则有没有用的方法，是问："如果没有这条规则，agent 大概率会怎么做？"和"加了这条规则之后，那个大概率行为会不会真的改变？"如果想不出"没有这条规则时 agent 会做什么不一样的事"，说明这条规则要么是在重复 agent 本来就会做的事（可以删掉，没有信息量），要么写得不够具体（改了等于没改）。这不要求你真的去跑测试验证（本仓库没有这类评测基础设施），但下笔前先在脑子里过一遍这个对照，能筛掉大量"正确的废话"。

**借口对照表：把 agent 实际用过的绕过理由记下来，而不是只猜测。** 写规则时容易假设"说清楚了 agent 就会照做"，但实践中 agent 经常用看似合理的理由把一条硬规则软化执行，比如把"必须找到根因"执行成"这次先这样改，应该能绕过去"。遇到这种情况，不要只是在原规则上加重语气，而是把这次实际出现的借口和对应的反驳记下来，积累成一张表。这张表属于参考类内容，具体 skill 如果积累了自己的借口对照表，下沉到该 skill 自己的 `references/excuses.md`，不需要全仓库共享一份，因为不同 skill 遇到的借口往往是该 skill 特有的。仓库级、跨 skill 通用的借口模式见 [references/glossary.md](references/glossary.md) 的对应小节。

## 适用范围与 skill 三种形态

仓库内的 skill 分三种形态，模块取用规则不同，但共享同一套槽位定义和命名规则：

- **流程型（process）**：有明确的阶段顺序、入口文档、状态机和阶段间确认，例如研发流程套件。必须使用"阶段与流转"和"回退与重新确认"模块。
- **工具型（tool）**：封装一个外部工具或 CLI 的调用方式，没有跨会话状态机，例如 filebrowser-skill。不需要"阶段与流转"模块，但仍需要"触发条件""执行步骤""排错""边界"。
- **知识型（knowledge）**：维护一份随时间积累的结构化知识库，例如 personal-kb。需要"存储结构""写入门槛""读取与查询""校验"模块，通常不需要"阶段与流转"。

判断一个具体 skill 属于哪种形态，看它是否存在"用户确认才能进入下一步"的阶段切换（→流程型），还是只封装单次可重复调用的能力（→工具型），还是主要任务是积累和检索长期有效的结构化内容（→知识型）。一个 skill 可以同时具备多种形态特征，这时按主要职责选择骨架，次要部分作为该骨架下的一个模块出现，不另起一套结构。

## 标准模块清单

每个模块对应 SKILL.md 中的一个二级标题，职责互斥。括号内标注哪些形态需要它：必选标注为"必"，按需标注为"选"。

| 模块 | 职责（只回答这一个问题） | 流程型 | 工具型 | 知识型 |
|---|---|---|---|---|
| 触发与边界 | 什么情况下使用本 skill，什么情况下明确不使用 | 必 | 必 | 必 |
| 环境配置契约 | 本 skill（或本 skill 所属的一组 skill）依赖哪些项目级外部配置，配置从哪里读 | 选 | 选 | 选 |
| 存储与路径契约 | 文件/数据放在哪里，路径怎么生成，命名规则是什么 | 必 | 选 | 必 |
| 阶段与流转 | 有哪些阶段/状态，什么条件下能从一个状态切到另一个 | 必 | 不适用 | 选 |
| 执行步骤 | 拿到一个具体任务后，按什么顺序做 | 必 | 必 | 必 |
| 校验与门槛 | 进入下一步或判定完成前必须满足的检查项 | 必 | 选 | 必 |
| 失败与回退 | 出错、受阻或需要撤销已确认结论时怎么处理 | 必 | 选 | 选 |
| 提问契约 | 什么情况下才允许向用户提问，问题怎么呈现 | 必 | 选 | 选 |
| 证据与完成定义 | 什么样的结果才能标记为"完成"，证据要求是什么 | 必 | 选 | 必 |
| 边界声明 | 本 skill 明确不做的事 | 必 | 必 | 必 |

"不适用"表示该形态原则上不会用到这个模块；"选"表示视具体 skill 的复杂度决定，模块过于单薄时可以并入相邻模块，但不能反向把一个模块拆成两个标题表达同一职责。

**"环境配置契约"和"存储与路径契约"的区别**：前者管"这个项目用的是什么外部系统"这类因项目而异、但多个 skill 共享的设置；后者管"本 skill 自己的文件放哪"。只有当一组 skill 反复依赖同一份项目级设置时才需要这个模块，没有这类需求直接删除标题。具体机制和实例见 [references/optional_modules.md](references/optional_modules.md)。

## 模块内容互斥规则

为了保证"改一个模块只影响一处"，约定以下互斥边界：

- "存储与路径契约"只定义路径和命名，不描述什么时候该读写哪个路径——那是"执行步骤"或"阶段与流转"的职责。
- "环境配置契约"只定义本 skill 依赖哪些项目级外部配置、从哪个路径读取——不重复定义配置文件内部各字段的含义，字段含义的权威定义留在生成该配置的 setup skill 里；也不和"存储与路径契约"混写，前者管"外部系统是什么"，后者管"本 skill 自己的文件放哪"。
- "阶段与流转"只定义状态值和切换条件，不描述切换时具体要做什么操作——那是"执行步骤"的职责。
- "校验与门槛"只列检查项和通过/不通过的判据，不描述检查不通过时怎么办——那是"失败与回退"的职责。涉及审查-修订这类多轮迭代循环的 skill，这个模块还需要追加"相比上一轮是否退步"的判据（质量轨迹），不能只看单轮是否达标；具体机制见 [references/optional_modules.md](references/optional_modules.md)。
- "失败与回退"只描述异常路径的处理方式，不重新定义正常状态机——正常状态机的定义留在"阶段与流转"里，失败处理只能引用已定义的状态值，不能发明新状态。
- "证据与完成定义"只定义什么算"完成"的证据标准，不描述具体怎么生成证据——那是"执行步骤"的职责。

违反这条规则的典型信号：同一句规则出现在两个模块里；某个模块的标题是"执行与校验"或"流程与异常"这种合并了两个职责的名字。出现这种信号时应该拆开，而不是接受它。

## 命名与状态值规则

为了让不同 skill 之间的状态值可以被统一理解，而不是每个 skill 各发明一套：

- 阶段/任务状态优先从这个集合里选，不够用才扩展：`discussing`（讨论中）/ `confirmed`（已确认）/ `pending`（待开始）/ `in_progress`（进行中）/ `done`（完成且已验证）/ `not_verified`（完成但验证条件不满足）/ `blocked`（当前无法继续）。
- `done` 只能用于"有真实验证证据支撑"的完成，不能用于"看起来做完了但没验证"——后者必须是 `not_verified`。这条规则不允许任何具体 skill 放宽。
- 编号前缀按内容类型区分，不按 skill 区分，跨 skill 复用同一套含义：`F-*` 功能/需求项、`D-*` 决策、`C-*` 变更、`T-*` 任务、`V-*` 验证、`RT-*` 调研、`REV-*` 审查、`DEF-*` 缺陷、`EVD-*` 证据、`LOG-*` 日志。具体 skill 需要新前缀时，先确认现有前缀语义是否已经覆盖，避免同义重复造前缀。
- 路径中的日期统一用 `YYYY-MM-DD`，版本号不使用尖括号占位符遗留在正式产出中。

## 提问契约（通用版）

所有具体 skill 的"提问契约"模块，如果需要详细规则，默认引用本节，不需要重新措辞：

只有当答案无法从项目文件、对话历史、工具输出或可靠外部来源获得，且错误假设会实质改变范围、结果或用户体验时才提问。能查证的就去查证；能基于明确依据做出合理假设的，直接假设并说明依据，不为了"保险"而提问。

必须提问时：一次只问当前最关键的一个问题；给出推荐选项和不同选择的影响；问题放在回复最后单独的 `## 需要你确认` 区块，该区块之后不再附加其他内容。

具体 skill 如果有特殊的提问限制（例如某个阶段绝对不能提问、必须批量收集问题），在自己的"提问契约"模块里只写"特殊于通用规则的差异部分"，通用部分直接说"其余遵循 skill-meta-protocol 的提问契约"。

## 证据与完成规则（通用版）

- 结论必须能追溯到真实来源：项目文件、命令输出、工具返回、可靠外部材料。不允许凭空声称。
- 不得用 mock、stub、占位数据、样例返回伪装成真实验证结果。
- 自动化检查（如 lint、build、typecheck）只能证明它实际覆盖的部分，不能替代它没有测试到的行为验证。
- 标记完成前，对照本 skill 自己的"校验与门槛"模块逐项自检；发现问题就地修复后再标完成，不把已知缺陷留给下一步或用户。

具体 skill 如果有额外的、更严格的证据要求（比如必须保留命令行原始输出），写在自己的"证据与完成定义"模块里，只写**额外**部分，不重复以上通用部分。

## 多入口场景的路由文档

当一组相关 skill（或一个 skill 内部的多种模式）存在多个相近但不同的入口时——比如同样是"研究"，有快速模式、系统性综述模式、引导式模式等好几种选择——"该选哪一个"这件事不应该由用户或 agent 在每个 skill 内部各自摸索判断标准，也不应该在每个 skill 的"触发与边界"模块里各自重复一遍完整的选择逻辑（那样任何一个模式新增或调整时，所有其他 skill 的"触发与边界"都要跟着改，违反单一权威来源）。

正确做法：为这一组 skill 单独写一份路由文档，放在这组 skill 共同的上级目录下（例如 `references/mode_selection_guide.md` 或类似命名），用一棵简单的判断树或对照表回答"用户的描述符合什么特征时，该进入哪个模式/哪个 skill"。每个具体 skill 的"触发与边界"模块只需要写自己的触发条件本身，不需要写"和其他模式的对比"；真正纠结该选哪个时，由 agent 主动去读这份路由文档，而不是临场比较各 skill 的描述。

路由文档本身只回答"选哪个"，不回答"选中之后怎么做"——后者仍然是被选中那个 skill 自己的"执行步骤"职责。如果发现路由文档里开始详细描述某个模式的执行细节，说明职责越界了，应该把那部分挪回对应 skill 自己的文件。

## 跨 skill 引用规则

一个 skill 在自己的 SKILL.md 里需要复用另一个 skill 的能力时：

- 只引用对方的入口和输出契约（它接受什么、产出什么），不复制对方内部的执行步骤。
- 引用格式统一为："调用 `<skill-name>`，见其 SKILL.md"。不在本协议或具体 skill 里维护一份"谁调用谁"的关系图——那应该能从各 skill 的"触发与边界"模块直接读出来。
- 如果两个 skill 之间出现了双向依赖（A 调用 B，B 也调用 A），这是设计信号，应该拆出第三个更小的 skill 或回到本协议讨论边界，而不是接受循环依赖。

## 改动影响自检表

修改某个具体 skill 之前，按以下表格预判影响范围，而不是改完再去发现连带问题：

| 你要改的内容属于哪个模块 | 预期影响范围 | 需要同步检查的地方 |
|---|---|---|
| 触发与边界 | 谁会调用这个 skill、什么时候不会被调用 | 是否有其他 skill 在自己的"触发与边界"里写了"何时转交给本 skill"，需同步措辞 |
| 环境配置契约 | 依赖哪个外部系统、配置字段含义 | 是否有其他 skill 共享同一份配置，字段改名或废弃时是否需要同步那些 skill 的引用 |
| 存储与路径契约 | 文件落盘位置、已有数据的可发现性 | 是否有脚本或其他 skill 硬编码了旧路径 |
| 阶段与流转 | 状态机本身，可能让已有的"in progress"数据处于未定义状态 | 是否需要为存量数据写迁移说明；"失败与回退"是否引用了被改动的状态值 |
| 执行步骤 | 具体怎么做，通常影响范围最小 | 校验与门槛是否假设了某个执行步骤产出的中间结果 |
| 校验与门槛 | 完成标准变严或变松 | 证据与完成定义是否需要同步；已通过旧门槛的存量结论是否需要重新审视 |
| 失败与回退 | 异常路径处理 | 是否意外引入了"阶段与流转"未定义的新状态值 |
| 提问契约 | 交互体验 | 通常影响范围最小，独立模块 |
| 证据与完成定义 | 完成判定的严格程度 | 校验与门槛、执行步骤是否需要补充对应的产出动作 |
| 边界声明 | 范围收缩或扩张 | 扩张边界时检查是否与另一个 skill 的边界产生重叠 |

如果一次改动同时落在"需要同步检查的地方"列出的多个位置，说明这次改动跨越了模块边界，应该重新评估改动方案本身，而不是继续往下改。

## 与配套文件的关系

本协议正文只放"判断和决策时要用的原则"，配套文件各自承接不同的下沉内容，本身就是"渐进展示"的一次实践：

- `SKILL_template.md`：据本协议生成的、可直接复制改名使用的脚手架，包含每个模块的占位说明和示例措辞。新建 skill 时复制它，按"标准模块清单"里该形态需要的模块保留对应章节，删除不适用的章节标题（不要留空标题等着以后填，空标题本身就是噪音）。
- `references/glossary.md`：本协议"表达规范"一节涉及的词汇的完整定义、正反例对照，以及为现有仓库挑选主导词的建议清单。只在写新 skill 或者怀疑某处用词不一致时查阅，不需要每次都读。
- `references/optional_modules.md`：标准模块清单里标注为"选"、且展开后篇幅较长的模块（目前是"环境配置契约"和多轮迭代场景下的质量轨迹判据）的完整机制和实例。只在具体 skill 命中对应场景时查阅。
- 仓库根目录的 `CHANGE_CHECKLIST.md`：把本协议的判断原则转成可逐项打钩的操作清单，改动前后过一遍。
- 仓库根目录的 `MIGRATION_GUIDE.md`：把已有 skill 套进新模板时的迁移步骤与判断依据，只在批量改造存量 skill 时查阅。

此外，"多入口场景的路由文档"一节描述的路由文档不是本协议自带的固定文件，而是一种按需创建的文件类型：只有当某组 skill 真的出现了多入口选择问题时才创建，放在那组 skill 共同的上级目录下，文件名按场景自定，不强制统一命名。

## 本协议与领域元协议的关系

仓库内已有的 `project-development-v3-common` 是研发流程域的领域元协议——它定义 F/D/C/T/V/RT/REV/DEF 编号语义、入口文档契约、阶段顺序等"v3 套件内部共享"的规则。这是本协议的一个领域实例：遵循本协议的标准模块清单、表达规范、命名规则，但在自己的领域内补充额外的模块（"调研契约""审查契约"等），只要新模块职责单一、不与标准模块重叠即可。

将来如果小说创作三件套、工具集成等其他 skill 群也发展出跨 skill 共享的领域规则，可以照 `project-development-v3-common` 的样子，各建一份域内元协议（如 `novel-suite-common`），同样挂在 `skill-meta-protocol` 之下。不需要把所有领域规则都塞进顶层元协议。
