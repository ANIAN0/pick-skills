# 改动前后自查清单

把 `skill-meta-protocol` 的判断原则转成可逐项打钩的操作清单。任何一个具体 skill 的 SKILL.md 在新建、重构或改动后，改动者（人或 agent）按下表逐项核对，不需要重读整份协议正文。只有大范围重写或迁移旧 skill 时才需要读本文件；日常执行某个具体 skill 的任务不需要读它。

## 结构层

- [ ] 已按"适用范围与 skill 三种形态"判断这个 skill 属于流程型 / 工具型 / 知识型，模块取用符合"标准模块清单"里对应形态的必选项。
- [ ] 每个二级标题只回答"标准模块清单"里那一格定义的问题，没有把两个职责合并进一个标题（比如"执行与校验"这种名字）。
- [ ] 没有任何一条规则同时出现在两个模块里——按"模块内容互斥规则"逐条核对。
- [ ] 涉及审查-修订多轮循环的 skill，"校验与门槛"补充了质量轨迹判据（维度、比较方式、退步阈值）。

## 自包含层

- [ ] 把这个 skill 的目录整个复制到另一个仓库，按它自己 SKILL.md 写的步骤，能不能走完全程（不依赖仓库根目录文件、不依赖另一个 skill 目录内部文件的存在）。
- [ ] 所有引用的 `references/*.md` 都在本 skill 目录内，链接路径是相对路径。
- [ ] 与其他 skill 的协作是可选增强，不是完成任务的必经前提；对方不可用时本 skill 有明确的退化处理或说明，而不是直接失败。
- [ ] 没有和另一个 skill 形成双向依赖（A 调用 B，B 也调用 A）。

## 表达层

- [ ] 步骤类内容（有顺序、有完成判据）留在 SKILL.md 主文件；参考类内容（定义、判据表、配置示例）超过几条就下沉到 `references/*.md`，主文件只留一句指向它的话。
- [ ] 从 SKILL.md 出发，任何一条结论最多跳一次链接就能拿到——`references/*.md` 之间没有相互链接形成第二层。
- [ ] 搜索过仓库里是否已有同一条规则的另一个措辞版本；如果有，只保留更精确的一份,另一处改成引用句。
- [ ] 如果某个模块的规则是"协议/上级已给通用版本，本处只补差异"这种模式，先判断它是行为性惯例还是功能性依赖（"如果这份说明不存在，agent 会不会给出明显更差、甚至无法完成任务的行为"）。行为性惯例才能用"差量声明"只留一句引用；功能性依赖必须按"自包含契约"内联或提供退化路径，不能只留引用——引用一个可能不存在的文件会让这个 skill 单独分发时直接失效。
- [ ] 反复出现三次以上的复合描述，已收敛成一个主导词，且只在首次出现时定义。
- [ ] 每条硬性规则都过了一遍"规则可执行性测试"：删掉它 agent 大概率会不会做出不一样的事；写成了"规则 + 为什么"而不是裸的 ALWAYS/NEVER/MUST。
- [ ] 状态值、编号前缀符合"命名与状态值规则"里的全仓库统一集合，没有为同一件事另造同义词。

## 完成前

- [ ] 对照"改动影响自检表"，确认这次改动落在的模块对应的"需要同步检查的地方"已经逐条检查过；如果同时命中多处，说明改动跨越了模块边界，已重新评估改动方案而不是硬着头皮往下改。
- [ ] `边界声明`（如适用）和实际改动后的范围一致，没有说"不做 X"但正文其他地方又隐含在做 X。
- [ ] 具体 skill 的 description 同时说明"做什么"和"什么时候用"，写成第三人称，包含具体触发关键词（而不是泛泛的功能清单）。
