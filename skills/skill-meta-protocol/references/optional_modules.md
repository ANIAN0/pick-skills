# 可选模块详解

本文件收录"标准模块清单"里标注为"选"、且展开后篇幅较长的模块。SKILL.md 主文件只保留判断"我需不需要这个模块"所需的最小信息；命中对应场景后再来这里查具体机制。没有命中的 skill 完全不需要读本文件。

## 环境配置契约

这是"环境配置契约"这个模块的唯一权威说明；SKILL.md 的标准模块清单表格里只留一句指向本节的话，不重复以下内容。

**和"存储与路径契约"的区别**：前者回答"这个项目用的是 GitHub 还是 Linear、triage 标签叫什么、领域文档放在哪个目录"这类因项目而异、但同一个项目内多个 skill 都要用到的设置；后者回答"本 skill 自己产出的文件放在什么路径"。两者都在回答"路径/配置在哪"，但一个是外部系统坐标，一个是本 skill 的私有存储坐标，不要混写。

**什么时候真的需要这个模块**：只有当一组 skill（不是单个 skill）反复依赖同一份项目级设置时才需要。例如仓库里如果 to-issues、triage、to-prd 这类 skill 都要知道"问题追踪用什么系统"，且目前是每个 skill 各自硬编码或反复询问用户，就是典型场景。

**怎么做**：这是功能性依赖，不适用 SKILL.md 里定义的"差量声明"（那条只覆盖提问契约、证据与完成定义这类行为性惯例）——缺了具体配置内容，任务会真的卡住，必须按"自包含契约"处理。合规写法：

- 把配置本身当成**用户项目自身的输入**（类似 `.env`、项目根目录的一份 YAML），本 skill 只负责读取项目里已经存在的文件。
- 在本 skill 自己的 SKILL.md 或本 skill 自己的 `references/` 文件中写清配置路径、必需字段、字段含义、允许值、最小示例、配置缺失或字段无效时的处理方式。
- 外部生成器可以作为可选增强被提及，但不能成为字段含义或配置 schema 的权威来源；即使生成器不可用，本 skill 仍必须能告诉用户如何手动创建最小可用配置。

**没有这类需求的 skill**：直接删除这个模块标题，不需要为了"以后可能要用"而强行填写占位内容。

## 多轮迭代场景下的质量轨迹

这是"校验与门槛"模块的一个特化情形，只适用于本身带有"审查-修订"循环的流程型 skill（比如审-改-再审的反复打磨流程）。普通单轮通过/不通过的 skill 不需要这一节。

**为什么单轮门槛不够**：单轮门槛只能回答"这一次产出是否达标"，但发现不了另一种情况——某一轮为了修一个问题，引入了新的退步，而单轮检查只看"这一轮要修的问题修了没有"，不会主动比较前后变化。

涉及多轮迭代的 skill，"校验与门槛"模块除了单轮判据外，还应该定义：

- 用什么维度衡量质量（不需要复杂的打分系统，几个关键维度即可，比如"论点连贯性""证据充分性"这类与该 skill 产出物相关的维度）。
- 怎么比较本轮和上一轮在同一维度上的相对变化，而不只是看本轮是否达标。
- 退步达到什么程度需要强制触发一次额外检查点（写一个具体阈值，不要用"明显退步"这种无法判断的措辞）。

这条规则只关心"是否需要补一次检查"，不重新定义检查点本身怎么做——检查点的具体操作仍然属于"执行步骤"或"阶段与流转"的职责，质量轨迹只是触发条件的来源之一。

## 多入口场景的路由文档

当一组相关 skill（或一个 skill 内部多种模式）存在多个相近但不同的入口时，"该选哪一个"不应该由用户或 agent 在每个 skill 内部各自摸索，也不应该在每个 skill 的"触发与边界"模块里各自重复一遍完整选择逻辑。

正确做法：为这组 skill 单独写一份路由文档，放在它们共同的上级目录下，用判断树或对照表回答"用户的描述符合什么特征时该进入哪个模式"。每个具体 skill 的"触发与边界"只写自己的触发条件本身，不写"和其他模式的对比"。

路由文档只回答"选哪个"，不回答"选中之后怎么做"；后者仍是被选中 skill 自己的"执行步骤"职责。

路由文档不是本协议自带的固定文件，而是按需创建的文件类型：只有某组 skill 真的出现多入口选择问题时才创建，放在那组 skill 共同的上级目录下，文件名按场景自定。

## 领域元协议

一组 skill（比如同属一个研发流程套件、或同属一个创作套件）可以在 `skill-meta-protocol` 之下建一份领域元协议：遵循本协议的标准模块清单、表达规范、命名规则，同时补充该领域特有的模块（例如"调研契约""审查契约"）。

新增领域模块必须满足两条：职责单一；不与标准模块重叠。不需要把所有领域规则都塞进本协议。
