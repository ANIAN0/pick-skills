# 存量 skill 迁移指南

把已有的、没有严格遵循本协议的 skill 套进标准模板时使用。只在批量改造存量 skill 时查阅，新建 skill 直接用同目录的 SKILL_template，不需要读本文件。

## 迁移顺序

按以下顺序处理一个存量 skill，每步做完再进入下一步，不要跳步：

1. **定形态**：按 SKILL.md 的"适用范围与 skill 三种形态"判断这个 skill 属于流程型 / 工具型 / 知识型。如果同时具备多种特征，按主要职责选骨架。
2. **列现有内容清单**：把存量 SKILL.md 现有的每个章节标题和它实际承担的职责列一遍，标注它对应"标准模块清单"里的哪一格，或者标注"职责不明/跨越多格"。
3. **拆分越界章节**：对标注"跨越多格"的章节，按"模块内容互斥规则"拆开，每条规则归到唯一一个模块。
4. **补齐结构性必选模块**：对照该形态的"必选"列，逐个检查结构性模块是否存在可执行内容；缺失的模块，先判断是"内容存在但标题不对"还是"内容确实没有"，前者改标题，后者按该模块的职责补写。提问契约、证据与完成定义这类行为性惯例模块只有存在特殊差异时才补写。
5. **下沉参考类内容**：超过几条的定义、判据表、配置示例移到该 skill 自己的 `references/*.md`，主文件只留一句指向它的话。检验：从 SKILL.md 出发拿到任何结论最多跳一次链接。
6. **自包含核对**：检查 SKILL.md 里的每一个文件路径引用，凡是指向仓库根目录或另一个 skill 目录内部文件的，改成以下两种处理之一：
   - 该文件确实是这个 skill 自己需要的资产 → 复制进本 skill 的 `references/`，成为它自己的文件。
   - 该文件属于跨 skill 共享的协作项 → 改成"跨 skill 引用规则"里定义的引用格式，且确保对方不可用时本 skill 有退化路径，而不是硬依赖。
7. **命名对齐**：状态值、编号前缀改成"命名与状态值规则"里的统一集合，删除自造的同义词。
8. **过一遍 CHANGE_CHECKLIST**：迁移完成后，按同目录的 CHANGE_CHECKLIST 逐项核对，不满足的项目继续修，不要标记迁移完成。

## 常见迁移信号

| 存量 skill 里常见的写法 | 说明它需要 | 处理方式 |
|---|---|---|
| 章节标题叫"流程与异常"或"执行与校验" | 违反模块内容互斥规则 | 按上面第 3 步拆开 |
| SKILL.md 里出现大段术语解释、配置示例，混在步骤中间 | 违反渐进展示 | 按第 5 步下沉 |
| 步骤里写"参考 `<其他 skill 目录>/xxx.md` 的做法" | 违反自包含契约 | 按第 6 步处理 |
| 状态值用了"审核中""待处理"这类没有出现在统一集合里的词 | 违反命名规则 | 按第 7 步改名，检查是否已有等价的标准状态值 |
| 完成判据写"看起来没问题就行" | 未通过规则可执行性测试 | 换成具体、可检验的判据 |

## 迁移不做的事

- 不因为"迁移"就删除存量 skill 里已经验证有效、只是章节标题不规范的内容——先归类，再决定要不要精简。
- 不在迁移过程中顺带修改这个 skill 的领域逻辑或功能范围；迁移只处理结构、表达和自包含性，功能变更是另一次改动。
- 不批量迁移多个 skill 后才统一验证；每迁移完一个就过一遍 CHANGE_CHECKLIST，避免问题累积到后面才发现是哪一步引入的。
