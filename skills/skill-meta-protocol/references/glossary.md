# 表达规范词汇表

本文件是 `skill-meta-protocol` 中"表达规范"一节的详细展开，只在写新 skill 或怀疑某处用词不一致时查阅。SKILL.md 正文只放判断原则，这里放定义、例子和可直接套用的清单。这是这些概念在仓库内的唯一权威定义——SKILL.md 正文只保留一句判断原则加指向本文件的链接，不重复这里的例子。

## 可预测性（predictability）

**定义**：同一类输入，agent 在不同会话里走出同一条处理路径，而不是每次都重新即兴决定。这指的是"过程一致"，不是"输出文字一致"——两次执行允许写出不同的具体内容，但发现问题、分级、汇报的**方式**应该一致。

**怎么检验**：把这段描述读给一个完全没见过这个项目的人，问"如果给你两个不同的具体场景，你做出的决策方式会不会因场景而摇摆"。如果答案是"看心情"或"看怎么理解这句话"，这段描述就不合格。

正例（`project-execution` 里的写法）：

> 验证失败时在执行记录链接证据，写明命令、关键错误、根因判断、修复和重试结果。同一问题连续三轮仍不通过且当前无法继续时标记 `blocked`。

"连续三轮"是具体数字，不是"反复尝试后仍失败"这种模糊表述——后者每次执行可能因 agent 当时的"耐心程度"不同而做出不同判断。

反例：

> 遇到问题时合理判断是否继续重试或上报。

"合理判断"没有给出任何可检验的边界，两次运行很可能走向不同结果。

## 渐进展示（progressive disclosure）的三层

| 层级 | 内容性质 | 放在哪 | 加载时机 |
|---|---|---|---|
| 步骤（in-skill step） | 有顺序、有完成判据的动作 | SKILL.md 主文件 | 每次执行都要看 |
| 参考（in-skill reference） | 定义、规则、判据表，本身是扁平的同级集合 | SKILL.md 主文件，独立小节 | 每次执行都要看，但只是查表不是走流程 |
| 外部参考（external reference） | 详细词汇、配置示例、迁移指南、长篇正反例 | 同目录下 `references/*.md` | 只在某个分支场景命中时才加载 |

**步骤和参考的区别不是"长短"，是"有没有顺序和完成判据"。** 一份扁平的规则列表（比如本协议的"命名与状态值规则"）属于参考，不属于步骤，即使它有很多条；一个三步流程属于步骤，即使只有三句话。误把参考写成步骤的样子（编号、要求严格按顺序执行），会让 agent 误以为这些规则之间有依赖关系，产生不必要的顺序约束。

**判断要不要下沉到外部参考文件的测试**：这部分内容是不是只在某个分支场景才会被用到？

正例：`filebrowser-skill` 把"安装"整节下沉到 `references/install.md`，因为只有命令找不到这个分支才会触发，正常调用路径完全不需要加载安装步骤。

反例：把每个状态值的详细解释都堆在主文件里，即使有十几个分支场景各自只用到其中一两个状态值——这种情况应该只在主文件留一张精简的状态表，把详细案例下沉到参考文件。

**引用深度不超过一层。** SKILL.md 可以指向 `references/*.md`，但 `references/*.md` 之间不应再相互链接、形成需要连续跳转两次才能拿到答案的第二层。Anthropic 对 Agent Skills 的公开实践同样建议"引用保持在离 SKILL.md 一层以内"：每多一层链接跳转，agent 判断"要不要继续往下读"的路由成本和读错文件的概率都会上升，读起来越"完整"往往越不可预测。检验方法：从 SKILL.md 出发，任何一条结论最多点开一次链接就能拿到，拿不到就说明分层分错了，应该把中间那一层拍平或直接内联。

## 单一权威来源（single source of truth）

**检测方法**：在同一个 SKILL.md 内，或同一仓库的多个 SKILL.md 之间，搜索同一条规则是否被复述了第二次。常见的复述信号：

- 两处都写了"完成"的定义，但措辞不完全一样——这是同一条规则的两个版本同时存在，改一处时另一处会过时。
- 一个具体 skill 在自己的"提问契约"模块里重新写了一遍通用提问规则的完整措辞，而不是引用 `skill-meta-protocol`——即使写得一字不差，这仍然是重复源，未来协议更新时这份复制会过时却没人记得去同步。
- 两份参考文件（比如"环境配置契约"相关的说明）各自写了一遍同一对术语的区别，例句不同、措辞不同——这不是"互相印证"，是同一条定义的两个漂移版本。修复方式是保留一个权威定义，另一处只保留入口指针；但具体 skill 的功能性配置 schema 仍必须随该 skill 自己分发，不能只指向本协议或另一个 skill。

**修复方式**：保留更精确、更新的版本作为权威定义，另一处改成"遵循 X"的引用句，不是删除引用关系本身。

## 主导词（leading word）

**定义**：一个能唤起读者（包括 agent）已有理解的紧凑词，用来替代反复出现的长句描述。一个好的主导词同时降低两件事的成本：每次复述这个概念的字数，以及 agent 每次重新理解这个概念要花的"心力"。

**怎么挑选**：在仓库里搜索是否有某个三五个词的短语反复出现（允许措辞略有差异但语义相同）。出现三次以上，且语义边界清晰、可以用一个词或短复合词概括，就是收敛成主导词的候选。

| 反复出现的描述 | 候选主导词 | 收敛后的效果 |
|---|---|---|
| "先写一个会失败的测试，确认失败原因正确，再写最小实现让它通过，再整理代码" | `RED → GREEN → REFACTOR`（已在 `project-execution` 使用） | 之后全篇直接说"按 RED/GREEN/REFACTOR 推进"，不需要每次重新解释三个阶段分别做什么 |
| "扮演怀疑论者提出问题，再按 BLOCKER/HIGH/MEDIUM/PASS 分级" | `两轮审查` | 后续 skill 提到审查流程时可以直接说"按两轮审查处理"，不必每次复述两轮各做什么 |
| "把已确认的状态重新打开，允许修改，但要重新走一遍确认" | `回退`（本协议的"失败与回退"模块已经在用） | 统一术语后，"回退"在所有流程型 skill 里都指同一件事，不会有的 skill 叫"重开"、有的叫"撤销确认" |
| "协议已给通用版本，具体 skill 只需补充自己的差异，不重复通用部分的措辞"——但仅限于行为性惯例，不能覆盖功能性依赖 | `差量声明`（本协议的"提问契约""证据与完成定义"两处曾用不同句子重复表达同一件事，收敛后统一引用；"环境配置契约"起初也被套了进去，但那是功能性依赖——缺了它任务真的做不完，套用差量声明会让下游 skill 单独分发时直接失效，后来改回按"自包含契约"处理） | 行为性惯例模块没有差异时整节删除；环境配置契约不使用这个词，必须随具体 skill 提供配置 schema 或最小示例 |

**反模式**：为了显得"专业"硬造一个新词，但这个词在模型的预训练理解里没有对应含义，或者和仓库里已有的另一个词冲突（比如已经用了"回退"表示状态重开，又造一个"回滚"表示同样的事）。主导词的价值来自"借用已有理解"，不是来自"造词本身"。

## 规则可执行性测试

**定义**：写完一条行为规则后，在脑子里（不需要真的跑评测）过一遍这个对照："如果没有这条规则，agent 大概率会怎么做？"和"加了这条规则，那个大概率行为会不会真的不一样？"

**两种失败模式，各自的修法不同**：

- **规则在重复 agent 本来就会做的事**：这种规则没有信息量，留着只会让文件变长，应该删除。判断方法：想象一个完全没读过这条规则、但受过良好训练的 agent，问它会怎么处理这个场景——如果答案和规则要求的一致，这条规则是冗余的。
- **规则写得不够具体，改了等于没改**：比如"出错时合理处理"。即使删掉这条规则，agent 大概率还是会做"看起来合理"的事——规则没有真正约束住任何具体选择。修法是把"合理"换成一个可检验的判据，比如"连续三轮仍不通过且当前无法继续时标记 `blocked`"——这里"三轮"和"无法继续"都是可以对照检查的，不依赖"合理"这种因 agent 当时状态而漂移的词。

同样值得注意的反模式是全篇堆砌 ALWAYS / NEVER / MUST 这类大写祈使句而不解释原因：模型会照字面执行，但遇到规则没预料到的边界情况时容易机械套用或忽略。优先写成"规则 + 为什么"，让"为什么"在未覆盖的场景里充当判断依据，而不是只留一句无法泛化的命令。

**这不是一套强制流程，是下笔前的一次自查**。本仓库目前没有专门的 agent 行为评测基础设施，所以这里只要求"写之前想清楚"，不要求真的跑一遍对照测试再交付。

## 借口对照表

**定义**：记录 agent 在实际使用某个 skill 时，曾经用来软化执行一条硬规则的具体说法，以及对应的反驳或修正方式。

**为什么不是靠"加重语气"解决**：一条规则被绕过，通常不是因为语气不够强硬，而是规则本身留了一个"看起来合理"的缺口。加重语气不会堵住这个缺口，因为 agent 依然可以认为"这次确实简单，这个判断仍然成立"。

**怎么记录**：发现一次绕过时，记两件事：agent 实际说出的理由（尽量原样保留，不要提前概括），以及为什么这个理由不成立、规则应该怎么改才能堵住这个具体缺口。例：

| 出现的说法 | 为什么不成立 | 规则修正方向 |
|---|---|---|
| "这次问题比较简单，直接改应该就行" | "简单"是 agent 自己的主观判断，规则没有给出"什么算简单"的客观标准，任何问题都可以被认为简单 | 把"找根因"换成可检验动作，比如"修改前必须能用一句话说清楚：为什么这个改动能让失败的检查通过，不能是改了之后看看" |
| "这部分逻辑后面会重构，先不管" | 用未来的计划为现在的疏漏开脱，而"后面会重构"本身没有任何强制力保证 | 规则里加一句：不接受"以后处理"作为跳过当前检查的理由，除非已经在"失败与回退"里建了一个对应的待办记录并取得用户确认 |

**这张表归属哪里**：仓库级、跨多个 skill 都可能出现的通用借口模式留在本文件；某个具体 skill 特有的借口下沉到该 skill 自己的 `references/excuses.md`，保持本文件只装真正跨 skill 通用的内容。

## 把这套规范用在审查现有 skill 时的检查问题

- 这一段如果换一个人在不同时间执行，会不会做出不一样的判断？（可预测性）
- 这部分内容是每次执行都用得到，还是只有某个分支场景才用得到？用得到的频率是否匹配它现在所在的层级？（渐进展示）
- 从 SKILL.md 出发，拿到一条结论需要跳几次链接？超过一次说明分层分错了。（引用深度）
- 这条规则在文件里（或仓库里）是不是已经存在另一处稍有不同的版本？（单一权威来源）
- 有没有一句反复出现的长描述，值得收敛成一个词？（主导词）
- 如果没有这条规则，agent 大概率会怎么做？加了规则之后这个行为真的会不一样吗？这条规则是不是只有大写祈使句、没有"为什么"？（规则可执行性测试）
- agent 有没有在实际使用中找过缺口绕过这条规则？如果有，这个具体说法记下来了吗？（借口对照表）

这七个问题就是"表达规范"在审查时的全部用法，不需要额外的打分体系。
