# 项目调研

围绕一个明确问题调查事实，给出足以支持当前决策的可靠结论。调研只负责查清问题，不替需求、设计、计划、执行、审查或验收阶段作决定。

调研是调用阶段的证据提供者，不是并行阶段负责人。被需求、迁移、设计或其他阶段调用时，只形成调研回答或调研材料；不同时修改调用阶段正文、其他阶段正文、代码和完成状态，由调用阶段决定如何使用证据。

调研发现迁移基线、需求或方案存在错误时，只指出具体事实、受影响结论和应返回的产物负责人。不能因为材料位于同一个二级目录，就直接修改 `功能迁移基线.md` 或其他阶段正文；证据提供不包含跨阶段写权限。

## 核心原则

- 先确认真正需要回答的问题，以及答案将支持什么判断，避免无边界地收集资料。
- 正式需求、方案、任务或调研文档都不是前提。当前对话已经把问题说清楚时直接调查。
- 项目事实以真实代码、配置、数据结构、提交历史和运行结果为准；外部事实优先使用当前的一手资料、官方文档或源码。
- 明确区分来源说明的内容、项目中观察到的事实和基于证据作出的推断。
- 结论以解决当前问题为限，不为了显得完整堆积无关背景、来源或过程记录。
- 无法可靠判断时明确写“不确定”，说明缺少什么证据以及它如何影响当前决策。

## 调查问题

从用户当前描述或调用阶段提取一个可以回答的问题，并确认必要的范围。多个问题彼此独立时分别调查，但不为此创建编号、状态机或任务体系。只有缺少用户才能提供的信息，并且不同答案会实质改变调查方向时才提问；其他情况根据已有上下文继续。

先检查项目中已经存在的代码、文档、历史调研和长期知识，复用仍然适用的事实，避免重复调查。已有材料只是线索，关键结论仍要核对其当前性和真实来源。

涉及参考项目时先限定它在当前问题中的角色：行为基线、视觉参考、SDK/框架/平台候选、数据或协议来源、实现证据。只调查支持当前判断所需的角色和能力；不能因为一个项目被称为“参考”就同时调查、比较并迁移其全部能力。

用户问“为什么没参考 X”“是否看过 X 的交互”或用参考项目质疑现有结论时，把问题解释为**证据完整性调查**。这只授权核实 X 与被质疑能力的真实关系，不授权将 X 设为行为基线、把 X 的功能加入目标范围，或替用户组合多个参考。若参考角色会改变目标产品行为，调研只能把角色写成候选并交还需求阶段决定。

调查项目内部行为时，阅读能够证明结论的上下游代码和配置，必要时执行只读检查或运行验证，不能仅凭文件名、注释或单个代码片段推断完整行为。

调用阶段正在建立或复核产品模型时，把待核实的节点或连线作为调查问题。除源码位置外，必须回答：谁触发、谁执行、读取什么、写入什么、产生什么结果，以及它与相邻流程是控制调用、数据读取、数据写入还是仅共享同一数据。共享数据不能推导出执行先后；不同触发源不能因为最终访问同一存储就合并成一条流程。

产品模型调研按“来源流程”和“目标采用”分开输出。先用“执行者 + 动作”还原来源中的独立流程，再说明哪些节点和连线是直接事实、哪些只是证据推断；不能把来源项目的轮询频率、目录结构、CLI 开关、内部任务编排或其他实现参数自动升级为目标产品需求。调研完成标准是调用阶段能够据此保留、撤回或继续调查一条具体模型关系，而不是得到更多可以抄入正文的技术细节。

需求阶段准备提问时，把每个候选问题作为待证伪假设调查。除核实来源行为外，同时检查当前需求正文、变更记录和已确认参考角色能否直接回答它，并返回以下分类之一：

- 已有决定已经回答；
- 已确认且范围匹配的行为或视觉基线可以回答；
- 正文漏写或前后矛盾，需要需求阶段修复；
- 属于设计展开，不是产品决定；
- 仍存在会改变目标行为的真实产品分歧。

只有最后一类才能成为用户问题。用户要求“先看 X”“X 已有现成逻辑”只会消除事实调查题；除非 X 在该能力上已有明确的目标采用决定，否则调查后仍要把“来源做法”和“目标是否采用”分开。调查完成标准是给出分类及证据，不能只汇总“可能的选项”后把本可查清的事项继续交给用户。

调查外部信息时，针对可能变化的事实在线核实。技术问题优先查官方文档、规范、源码或原始研究；搜索结果页和摘要只用于发现来源，不能直接作为结论证据。来源冲突时说明各自适用范围、差异和采用某一结论的理由。

## 形成结论

先直接回答调研问题，再给出支持关键结论的项目位置、命令结果或外部来源。只记录真正影响判断的证据，不要求固定来源数量。

对会影响下游判断的内容明确区分：

- **来源事实**：源码、运行行为、配置或可靠资料直接证明什么；
- **证据推断**：基于哪些事实作出什么解释；
- **候选目标行为**：事实说明某种目标做法可行，但尚未成为用户需求或方案决定；
- **未回答问题**：当前证据没有解决、且会影响调用阶段的事项。

“某 SDK 支持某能力”“某参考项目采用某交互”只能证明来源事实或可行性，不能直接推出目标产品也应采用相同行为。调研结尾明确说明结论交给哪个阶段、能支持哪个判断、不能替该阶段决定什么。

如果用户此前已明确要求在限定范围内 1:1 复刻、完全还原或沿用完整逻辑，目标采用基线已经是需求事实。该范围只取用户语句直接指向的项目和能力，不能因同轮还提到其他参考对象就横向扩张。调研应说明范围内哪些行为被该决定继承、哪些不在范围内或与目标约束冲突；不要把已经存在的采用决定再次降级成候选，也不要代替需求阶段扩大其范围。

调研结论使用事实性语言。可以写“X 实现了……”“X 可作为……的候选参照”“采用该行为会产生……差异”，不能写“目标应采用 X”“应组合 A/B/C”“应以 X 为行为基线”。后者是需求或设计决定，不是调研结论。被调用阶段处于质疑修复态时，不替它重写正文，也不把原错误换成新的确定性建议。

同时说明仍然存在的不确定性、限制、冲突和未能验证的内容，并解释这些内容是否会阻止当前阶段继续。如果证据不足以形成可靠答案，不用猜测填补空白，应说明当前能够确认什么、不能确认什么以及下一步需要的条件。

最后说明调研结论对当前需求、方案、任务或实现意味着什么，但由调用阶段决定是否修改其正文或代码。

## 保存调研材料

简单问题默认直接在对话中回答，不强制创建报告。调研属于某个工作事项且结果值得保留时，把材料放在该事项正文旁的同名二级目录，使用简短、明确的中文文件名，例如 `支付接口限制调研.md`；不要额外建立 `RT-*`、`research/` 或证据编号目录。

同一个问题已有调研材料时优先更新原文件，并保留结论发生变化的原因和新证据。过程日志、临时下载和一次性脚本不写入调研正文，任务结束前按其交付价值清理。

调研结论如果长期稳定且会被多个需求复用，可以交给 `project-knowledge` 判断是否沉淀；本 skill 不依赖知识库，也不自动修改知识库。

## 边界

- 不用固定模板、状态字段、双向链接或完成清单判断调研质量。
- 不把无来源推断、搜索摘要、历史结果或来源数量包装成已确认事实。
- 不自动修改需求、方案、任务、代码、验收结论或用户决定。
- 不因某项能力不可用就伪造结论；说明限制并尽可能寻找可靠替代证据。
