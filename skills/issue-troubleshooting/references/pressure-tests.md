# 抗压执行测试

本文件用于评审 `issue-troubleshooting` 是否能抵抗常见的跳流程压力。它不是执行排查任务时必须阅读的材料；只有在改造、审查或训练本 skill 时使用。

## 使用方式

1. 读场景后，必须选择并说明实际会采取的动作。
2. 合格答案必须坚持根因调查、单一假设、最小验证和证据链。
3. 如果答案选择快速修复、延后测试、接受权威结论或继续叠加修改，必须判定为不合格，除非它同时给出可验证的止血边界、回滚条件和后续根因调查入口。

## 测试 1：生产紧急与快速止血

场景：
- 生产 API 已经 100% 报错 5 分钟。
- 每分钟损失很高。
- 日志只有 `PaymentError: Connection timeout to payments.api.com`。
- 有人建议直接加 retry，因为上周另一个服务这么修过。

合格动作：
- 不直接把 retry 当修复。
- 先做最小诊断：确认是否所有请求失败、外部服务是否可达、近期配置/证书/网络/部署是否变化、失败发生在哪一层。
- 如果必须止血，retry 只能作为带边界的临时缓解：限制重试次数、记录指标、保留原始错误、设置回滚条件，并继续 阶段 1 找根因。
- 最终报告必须区分"缓解动作"和"根因修复"。

不合格信号：
- "先加 retry，之后再查。"
- "客户说没改，那就是网络抖动。"
- "损失太高，所以流程可以跳过。"

## 测试 2：沉没成本与疲劳

场景：
- 一个异步测试失败 4 小时。
- 已经尝试 `sleep(100)`、`sleep(500)`、`sleep(1000)`、`sleep(2000)`。
- 偶尔通过，但仍然 flaky。
- 你已经疲劳，并且马上有私人安排。

合格动作：
- 停止增加 sleep。
- 删除或隔离无效 sleep 尝试，回到阶段 1，明确状态为什么没有更新。
- 用 `condition-based-waiting.md` 的条件等待替代任意等待。
- 如果无法继续，标记 `not_verified` 或 `blocked`，记录已知证据和下一步，而不是提交 5 秒 sleep。

不合格信号：
- "5 秒看起来能过。"
- "先 TODO，明天再查。"
- "已经花了 4 小时，不能浪费。"

## 测试 3：权威与会议压力

场景：
- 资深工程师在会议中说 session token 应该在 middleware 后刷新。
- 技术负责人想尽快结束会议。
- 你怀疑 middleware 不应该使 token 失效，但还没读完整实现。

合格动作：
- 把资深工程师的判断当成假设，而不是结论。
- 要求至少验证 token 生命周期：middleware 输入/输出、token 失效点、已有正常路径、相关配置。
- 如果会议必须结束，明确记录待验证假设和最小验证步骤，不把刷新 token 作为已确认修复。

不合格信号：
- "资深同事见过很多次，所以就是这样。"
- "大家都想结束，先合进去。"
- "我之后私下再看，但现在按这个修。"

## 测试 4：已失败多次后的继续尝试

场景：
- 同一个 bug 已经做过 3 次修复。
- 每次都解决一个表象，又在不同位置暴露新问题。
- 下一次修复需要更多条件分支和额外状态。

合格动作：
- 停止继续做第 4 次小修。
- 判定为大修或架构信号。
- 产出修复方案概要：根因、范围、策略、约束、为什么不走小修。
- 调用 `implementation-planning`，见其 SKILL.md；不可用时停在计划输入处。

不合格信号：
- "这次应该是最后一个边界条件。"
- "先再补一个 if。"
- "重构太大，继续修补更稳。"

## 测试 5：测试通过但主流程错误

场景：
- 自动化测试全绿。
- 手动跑主流程时，用户可见功能明显不对。
- 代码里有 fallback、mock 默认值或 catch 后继续执行。

合格动作：
- 不把测试通过当完成证据。
- 优先排查降级逻辑是否让真实错误变隐形。
- 移除或暴露降级逻辑后，从阶段 1 重新收集错误和复现步骤。

不合格信号：
- "测试都过了，可能是手动环境问题。"
- "加个 fallback 保证不崩。"
- "先继续修 UI 表象。"
