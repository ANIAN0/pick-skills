# 问题排查与修复

这是一个流程型 skill。核心原则：先找到根因，再动手修复；没有根因调查，就不允许提出修复方案。

## 触发与边界

**触发**：测试失败、生产 bug、异常行为、性能问题、构建失败、集成问题、主流程与预期不一致、同一问题多次修复未生效、用户要求"看看报错/问题/功能不对"。

**不触发**：用户只要求设计新功能、规划正常需求开发、编写需求文档、做纯代码审查且没有明确故障现象。此类任务应使用更匹配的 skill；如果排查中发现根因其实是需求或架构方案缺失，本 skill 只记录排查结论，不代写需求或技术方案。

**与其他 skill 的关系**：
- 修复被判定为大修时，调用 `implementation-planning`，见其 SKILL.md；若该 skill 不可用，则把本 skill 产出的修复方案概要作为人工确认清单，不直接实施大修。
- 大修计划确认后，调用 `plan-execution`，见其 SKILL.md；若该 skill 不可用，则停止在已确认计划处，向用户说明无法继续按计划执行。
- 项目已有技术方案时只读引用项目内的 `workplace/<version>/tech-design/` 内容；不得因为 bug 修复而创建新的 tech-design 文档。

## 存储与路径契约

- 排查报告写入用户项目的 `workplace/<version>/troubleshooting/`。
- `<version>` 必须使用项目中已有的具体版本目录，例如 `workplace/1/troubleshooting/`；不能在正式产出中保留 `1.X`、`<version>` 或尖括号占位符。
- 若项目没有 `workplace/<version>/` 结构，则把报告写入项目内最接近的排查/记录目录；如果没有可判断的目标目录，先在最终回复中给出报告内容，不新建仓库级共享目录。
- 报告命名为 `YYYY-MM-DD-{问题关键词}-排查报告.md`，日期使用当前本地日期。
- 参考材料和脚本只引用本 skill 目录内的 `references/` 与 `scripts/`。

## 阶段与流转

| 状态 | 含义 | 可进入的下一状态 |
|---|---|---|
| `pending` | 已识别技术问题，尚未开始系统排查 | `in_progress` |
| `in_progress` | 正在执行五阶段排查或修复 | `blocked` / `not_verified` / `done` |
| `blocked` | 缺少必要信息、环境、权限或用户决策，当前无法继续 | `in_progress` |
| `not_verified` | 已实施修复或形成结论，但验证条件不满足 | `in_progress` / `done` |
| `done` | 根因、修复和验证都有真实证据支撑，报告已归档或已在最终回复中给出 | 无 |

阶段只能按以下顺序推进：阶段 1 根因调查 -> 阶段 2 模式分析 -> 阶段 3 假设验证 -> 阶段 4 修复规模评估 -> 阶段 5 修复实施。

流转条件：
- 阶段 1 -> 阶段 2：已记录错误信息、复现情况、近期变更和关键证据；无法复现时已说明缺口并收集替代证据。
- 阶段 2 -> 阶段 3：已找到正常参照或明确说明没有参照，并列出异常实现与参照/预期之间的关键差异。
- 阶段 3 -> 阶段 4：单一根因假设通过最小验证；未通过时继续提出新假设，不进入规模评估。
- 阶段 4 -> 阶段 5：已按 `references/scale-and-red-flags.md` 判定小修或大修。
- 阶段 5 -> `done`：修复通过自动化或可复现的行为验证，且排查报告已归档或随最终回复交付。

## 执行步骤

1. **根因调查**：完整阅读错误、警告和堆栈；记录文件路径、行号、错误码；稳定复现问题；检查 git diff、近期提交、依赖、配置和环境差异。多组件链路中，在组件边界收集进入/离开数据、环境传播和各层状态。错误出现在调用栈深处时，使用 `references/root-cause-tracing.md` 追溯到源头；不确定哪个测试造成污染时，可用 `scripts/find-polluter.sh` 二分定位。
2. **降级排查**：如果测试通过但主流程明显不对，先搜索 catch 后假成功、fallback 默认值、条件跳过、mock 泄漏、静默忽略等降级逻辑。找到后先移除或暴露真实错误，再从阶段 1 重新开始。
3. **模式分析**：在同一代码库寻找能正常工作的类似实现；完整阅读参考实现；列出正常路径与异常路径的差异、依赖、配置和隐含假设。不要略读参考实现。
4. **假设验证**：只提出一个具体假设，格式为"我认为 X 是根因，因为 Y"；用最小改动、最小脚本或最小测试验证它。验证失败时撤回该假设并提出新假设，不在失败假设上叠加修复。
5. **修复规模评估**：按 `references/scale-and-red-flags.md` 判断小修或大修。小修进入直接实施；大修整理根因、范围、策略、约束，调用 `implementation-planning`，见其 SKILL.md。
6. **小修实施**：先创建能失败的最小测试或一次性验证脚本；只针对已确认根因做单一修复；不顺手优化、不捆绑重构。涉及等待/超时场景时，使用 `references/condition-based-waiting.md` 的条件轮询原则替代任意 sleep。
7. **大修实施**：计划确认后，调用 `plan-execution`，见其 SKILL.md。计划的最后一个模块必须是回归验证；每个修复模块应带上关联根因、风险点、回退方案。
8. **验证与报告**：运行覆盖根因场景的测试或可复现验证，检查相关功能回归。修复通过后参考 `references/defense-in-depth.md` 判断是否需要在多层增加验证。最后按 `references/troubleshooting-report-template.md` 归档排查报告。

## 校验与门槛

进入下一阶段或判定完成前必须满足：

- [ ] 阶段 1 结束前，没有提出修复方案；已记录可追溯证据，或明确说明无法复现时缺少哪类证据。
- [ ] 阶段 2 结束前，已列出正常参照与异常路径之间的关键差异；没有参照时，已说明搜索范围和替代判断依据。
- [ ] 阶段 3 结束前，根因假设经过最小验证；"可能是 X"不能作为进入阶段 4 的依据。
- [ ] 阶段 4 结束前，已按文件数、模块跨度、预估工时、接口/架构影响、测试影响、前后端影响判定小修或大修。
- [ ] 阶段 5 结束前，已有失败用例、一次性脚本或明确复现步骤证明修复覆盖根因；仅 lint/build/typecheck 不能替代行为验证，除非原问题就是 lint/build/typecheck 失败。
- [ ] 当出现紧急、疲劳、权威压力或"这次可以例外"的心理信号时，已对照 `references/scale-and-red-flags.md`；评审本 skill 抗压执行能力时，使用 `references/pressure-tests.md`。
- [ ] 报告中包含问题描述、根因分析、修复内容、验证结果；没有把 mock、stub、占位数据或样例输出当成真实验证。

## 失败与回退

- 阶段 1 无法复现：保持 `in_progress`，继续收集日志、环境、输入数据和用户可见现象；证据不足且无法继续时标记 `blocked`。
- 阶段 3 假设验证失败：撤回该假设，记录失败证据，回到阶段 1 或阶段 2；不得叠加新修改。
- 小修连续失败 3 次：停止继续试第 4 次，按 `references/scale-and-red-flags.md` 的架构红灯处理，进入大修评估。
- 发现降级逻辑掩盖真实错误：先移除或绕开降级逻辑，让真实错误暴露，再回到阶段 1。
- 大修所需的 `implementation-planning` 或 `plan-execution` 不可用：停在已产出的修复方案概要或计划处，标记 `blocked`，不要把大修拆成多个未经计划的小修。
- 已确认的根因被新证据推翻：撤回对应结论，回到能解释新证据的最早阶段；最终报告必须写明被排除的假设。
- 修复完成但验证命令无法运行：标记 `not_verified`，说明缺少的验证条件和已完成的替代检查。
- 连续 3 次修复失败、需要架构重构、需要跨模块大修、或缺少关键生产/用户输入数据：先说明现有证据和推荐路径，再请求用户确认。

## 证据与完成定义

本 skill 额外要求：

- 根因结论必须带证据链：现象 -> 复现/日志/命令输出 -> 代码路径/数据流 -> 源头原因。
- 修复完成必须同时证明"原问题不再触发"和"相关路径没有明显回归"。
- `done` 只能在报告已归档或报告内容已随最终回复交付后使用；修复了但报告缺失时仍是 `not_verified`。

## 边界声明

本 skill **不做**：

- 不在根因未确认前给修复方案。
- 不用 catch、fallback、默认值、静默忽略掩盖真实错误。
- 不把大修当作多个小修绕过计划。
- 不创建新的需求文档或技术方案文档。
- 不把其他 skill 目录内的文件当作本 skill 必需依赖。
- 不把只通过 mock/stub/占位输出的检查标记为真实验证。
