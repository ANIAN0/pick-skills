# 任务规划细则

## 文档结构

按需创建支撑目录，不预建空文件。

```text
workplace/3/implementation-planning/2026-06-21-order-import.md
workplace/3/implementation-planning/2026-06-21-order-import/
├── tasks/T-001-import-happy-path.md
├── tasks/T-002-duplicate-handling.md
├── evidence/EVD-001-baseline.md
├── research/RT-001-unknown-constraint.md
└── review/REV-001-plan-review.md
```

入口链接每个 `T-*`，每个任务文件链接回入口及对应方案内容。`T-*`、`EVD-*`、`RT-*`、`REV-*` 编号一旦被引用，不得重排或复用；删除、合并或替换时保留历史说明并让新编号递增。

## 缺口分流

不能在任务文档中自行补设计：

- 方案契约缺口返回 `project-design`：真实变更位置、接口字段、状态、失败行为、数据归属、验证定义或技术决策不清。
- 需求语义缺口返回 `project-requirements`：用户目标、验收边界、特别关注点或不做范围不清。
- 执行事实缺口留在规划阶段自修或登记 `RT-*`：代码路径、基础命令、相似模式、依赖顺序或既有失败需要核验。

开放问题会影响任务边界、接口契约、字段、状态、失败行为、依赖顺序或测试阶段交接时，不得创建对应 `T-*` 的详细任务契约。

## 覆盖审计

在支撑材料或规划工作区逐项核对，不把完整矩阵堆进入口：

- `F-*`、验收要求、`D-*`、`C-*`、`V-*` 是否全部进入任务。
- 覆盖完整性：所有追踪项有任务落点。
- 可执行完整性：真实路径、接口契约、依赖、实现步骤、禁止偏离项、最小基础检查和测试阶段交接明确。
- 服务边界、API、数据实体、迁移、配置、页面、状态、错误反馈和运行链路是否有落点。
- UI 需求是否有实现任务；无 UI 时是否明确。
- 阻塞审查发现是否已关闭，调研结论是否已吸收。

入口只展示总数、覆盖完整性、可执行完整性、缺口和处理方式。

## 开发阶段检查策略

开发阶段只规划最小必要检查，目的不是证明功能正确，而是避免明显格式、语法或构建入口错误。

- 必须优先使用项目已有格式、lint、typecheck、编译或最小 smoke 命令。
- 只允许列出基础测试：已有且与本任务直接相邻、运行成本低、不会要求新增持久化测试文件的测试。
- 不要求开发阶段执行复杂功能测试、E2E、浏览器验证、前端交互验证、完整回归或多轮重复测试。
- 不把“跑 10 次测试”当成提高可信度；同一检查只需在关键改动后运行一次，失败时修正后重跑。
- 如果为了临时确认局部逻辑需要草拟测试或脚本，必须标明“临时、不落盘或执行后删除”，不得作为任务产物。

`V-*` 和验收要求只在任务中转写为“测试阶段交接”：说明后续集中测试要覆盖的入口、行为、失败路径和观察证据，不要求执行者在开发阶段完成这些功能测试。

## 任务拆分

任务按最小完整实现切片拆分。一个切片贯穿该行为实际需要的层，完成后代码应达到可被后续集中测试验证的状态。任务太大或包含多个可独立实现的行为时拆分；拆分后只能产生内部结构且无法对应方案变更时合并。

只有真实依赖要求时才提前创建迁移、共享契约、基础设施或行为保持的 prefactor 任务。禁止把同一行为的测试、实现、回归或审查拆成相互独立的横向任务。

入口表格顺序就是默认执行顺序。可并行或可乱序必须在入口明确标注；任何改变风险收敛或关键依赖的重排都必须返回规划阶段。

## T-* 契约

每个 `T-*` 必须包含：

- 追踪和目标：关联 `F/D/C/V`、实现目标、完成后代码应具备的能力。
- 上下文和边界：当前状态、目标状态、相关 `D-*` 摘要、特别关注点、不做范围、禁止捷径；BUGFIX 写根因、风险和回退。
- 文件和契约：实现文件、允许的临时检查文件、上游依赖、本任务提供、下游消费、相邻接口、字段、事件、状态和错误。
- 实施步骤：按技术方案设计列出有序实现步骤，不重新设计，不加入额外行为。
- 最小检查：格式、lint、typecheck、编译或最基础测试命令；说明失败判定。
- 代码审查要点：审查者直接查看代码时如何判断实现是否与方案一致。
- 测试阶段交接：后续集中测试需要覆盖的 `V-*`、用户入口、失败路径、UI 或回归范围。

任务文件不能用“参见入口”“参见其他任务”省略执行所需信息。可以链接方案和证据作为来源，但必须内联当前任务需要的实际契约和约束。

## 执行状态

入口文档是唯一状态面板：

- 只在入口 frontmatter 维护整体 `execution_status` 和 `execution_review`。
- 只在入口任务表维护每个 `T-*` 的执行状态。
- 任务文件不写 `execution_status` frontmatter，不保留 `## 执行记录`，不维护 `pending/in_progress/done/not_verified/blocked`。
- 任务清单更新范围、契约或交接内容时，同步更新入口摘要；状态只改入口，不改任务文件。

## 回退

执行或验收回退并证明规划契约需要修改时，把原入口 `status` 改回 `discussing`，把 `plan_review`、`execution_status` 和 `execution_review` 重置为 `pending`。修订受影响任务契约后，重新完成计划审查和用户确认；不要在任务文件恢复或维护执行状态。
