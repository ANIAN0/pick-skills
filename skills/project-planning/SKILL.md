# 项目规划

这是流程型 skill。目标是把已确认技术方案转成执行者可直接照做的实现任务：按照技术文档的设计，正确且完整地实现，不多、不少、不偏离。复杂功能测试、E2E、前端验证和最终验收不放在任务或开发阶段强制执行，统一交给开发后的测试/验收阶段。

## 触发与边界

**触发**：用户要求把已确认 `project-design` 方案拆成实现任务、任务清单、开发计划或执行契约时使用。

**不触发**：用户仍在澄清需求时，调用 `project-requirements`，见其 SKILL.md；用户仍在设计实现路径、API、数据、UI 实现或验证策略时，调用 `project-design`，见其 SKILL.md；用户已经要求直接实现时，交给 `project-execution`。

**与其他 skill 的关系**：本 skill 可调用 `project-review`，见其 SKILL.md。审查不可用或未通过时，入口不得标记为 `confirmed`。

## 存储与路径契约

- 任务入口只在 `workplace/<版本>/implementation-planning/` 下创建或更新一份；优先使用用户给出的路径，其次复用同一技术方案已有入口，否则按 `YYYY-MM-DD-功能名.md` 命名。
- 一个已确认技术方案当前只能有一份任务入口；发现多份时先选择或合并，不继续新增。
- 新建入口使用 [任务入口模板](assets/planning-entry.md)，新建任务使用 [详细任务模板](assets/task-detail.md)。
- 支撑材料放在入口旁的同名目录中，按需创建，不预建空目录或空文件。
- 支撑材料编号使用类型加递增数字：`EVD-*` 证据汇总、`RT-*` 调研、`REV-*` 审查。

## 阶段与流转

| 状态 | 含义 | 可进入的下一状态 |
|---|---|---|
| `discussing` | 任务仍在调查、切片或确认 | `confirmed` / `blocked` |
| `confirmed` | 任务入口已审查且经用户确认，可进入执行 | `discussing` |
| `blocked` | 缺少继续规划或确认的必要条件 | `discussing` |

切换条件：

- `discussing` -> `confirmed`：已确认技术方案、任务入口、全部 `T-*`、必要支撑材料、独立审查和用户确认全部完成。
- `discussing` -> `blocked`：缺少用户或外部系统才能提供的必要条件，且无法安全假设。
- `confirmed` -> `discussing`：下游证明任务契约需要改变，或上游需求/方案从 `confirmed` 回退。
- `blocked` -> `discussing`：用户、项目文件或外部系统补齐恢复条件。

## 执行步骤

1. 确认入口路径：只在 `workplace/<版本>/implementation-planning/` 下创建或更新与当前技术方案对应的一份任务入口。输出完整路径并说明“如需修改请告知，否则继续”，然后继续执行。
2. 校验输入：只接受 `status: confirmed` 的技术方案入口。读取已确认需求、方案摘要、`D-*`、`C-*`、`V-*`、相关调研和审查报告；缺少确认方案时返回 `project-design`。
3. 建立覆盖审计：提取全部 `F-*`、验收要求、`D-*`、`C-*`、`V-*`、用户特别关注点和不做范围。发现方案或需求缺口时返回责任阶段，不在任务里补设计。
4. 调查执行事实：核验真实代码路径、项目格式命令、最小基础测试入口、相似实现、依赖顺序和既有风险。必要时运行不修改项目状态的基线命令；详细输出放 `EVD-*`。
5. 写入入口和任务：入口作为唯一状态面板，展示范围、任务顺序、依赖、开发检查、风险、审查结论和执行状态。每个 `T-*` 只写自含实现契约，不维护执行状态。
6. 讨论任务切片：首次从方案拆任务时，一次性讨论切片粒度、顺序、依赖、合并/拆分、测试阶段交接和主要风险。相关问题成组提问，不逐项拉长轮次。
7. 自检、独立审查、用户确认：自检通过后调用 `project-review` 审查入口和全部 `T-*`。审查通过后请用户确认入口摘要，确认后把 `status` 改为 `confirmed`，保持入口 `execution_status: pending`。

## 校验与门槛

进入执行阶段前必须满足：

- [ ] 入口路径真实，位于 `workplace/`，且一个技术方案当前只有一份任务入口。
- [ ] 输入技术方案为 `status: confirmed`，任务没有重新设计或扩展方案。
- [ ] 每个 `F/D/C/V` 有明确任务落点，没有额外范围或未处理方案缺口。
- [ ] 每个 `T-*` 文件完整自含，真实路径、接口契约、实现步骤、禁止偏离项、最小基础检查和测试阶段交接明确。
- [ ] 任务没有要求开发阶段创建持久化测试文件、执行复杂功能测试、E2E 或前端验证；这些内容只作为测试阶段交接。
- [ ] 入口任务表包含唯一执行状态列，任务文件 frontmatter 和正文不维护状态。
- [ ] 独立审查通过，用户明确确认入口摘要。

任一项不成立时保持 `status: discussing`，不得交给执行阶段。

## 失败与回退

- `discussing` 下发现方案契约缺口：返回 `project-design`，技术方案入口不得绕过修订。
- `discussing` 下发现需求语义缺口：返回 `project-requirements`。
- `discussing` 下发现执行事实缺口：留在规划阶段自修，或登记 `RT-*` 并调用 `project-research`。
- `confirmed` 后下游证明任务契约需要修改：把原入口 `status` 改回 `discussing`，把 `plan_review`、`execution_status` 和 `execution_review` 重置为 `pending`；受影响任务只改契约内容，不在任务文件维护状态。
- 独立审查不可用或未通过：保持 `discussing`，记录原因和下一步修复条件。

## 提问契约

满足全部条件才问用户：

- 答案会实质改变任务边界、接口契约、实现顺序、风险处理或测试阶段交接。
- 无法从项目、已有文档、历史对话或调研获得答案。
- 错误假设会导致明显返工、范围错误、用户可见问题、验证失效或风险。

提问时放在回复最后的 `## 需要你确认`，后面不再追加总结。能安全假设时，直接写明假设、依据和影响并继续推进。

## 下沉材料

按需读取 [任务规划细则](references/planning-rules.md)：

- 需要创建支撑材料、证据、调研或审查链接时。
- 需要判断覆盖完整性、可执行完整性、任务切片或依赖顺序时。
- 需要编写完整 `T-*` 契约、开发阶段最小检查或测试阶段交接时。
- 执行或验收回退导致计划需要重开时。

## 边界声明

本 skill **不做**：

- 不修改生产代码、测试、配置或数据；只允许安全基线和命令试验。
- 不重新决定需求或方案，发现缺口时返回责任阶段。
- 不把任务拆成“先写测试、再实现、再回归”的横向任务。
- 不要求开发阶段执行复杂功能测试、E2E、浏览器检查或前端验证。
- 不在任务文件维护执行状态、执行结果或验证记录；状态只更新入口文档。
