# 项目规划

创建一份精简、可持续更新的任务清单，让执行者在开发过程中不会忘记修改范围、遗漏必要工作或过早认为任务已经完成。

## 核心原则

- 计划是范围和进度的记忆，不是需求文档、技术方案或代码教程。
- 直接引用已有的问题说明、需求或技术方案，不复制其内容，也不重新设计实现方式。
- 只列为了完整交付这次改动确实需要完成的任务。覆盖必要的代码、配置、数据、当前改动自测和文档改动，但不加入顺手优化、全项目回归或无关工作。
- 任务粒度以便于跟踪完成情况为准。不要细化成函数、代码行或机械操作步骤，也不要为每个文件单独创建任务。
- 一项任务说清要完成的结果即可；只有确实影响执行时才补充涉及范围、依赖或顺序。
- 简单到执行者不可能遗忘范围的一步改动，不主动创建计划。用户明确只要求计划时，仍然只提供清单，不擅自开始实现。

## 工作方式

理解当前问题、改动目标以及已经确定的技术方案。正式需求文档和技术方案文档都是可选输入；当前对话已经足够清楚时直接使用。按需查看项目，只确认任务范围、真实落点和必要依赖，不在规划阶段重新进行完整技术设计。

创建或更新一份 Markdown 任务清单。沿用当前改动的版本和中文工作名称；路径优先遵循用户指定，否则沿用原有规范，写入 `workplace/<版本>/implementation-planning/<工作名称>.md`。没有上游文档时，文件名优先采用简短、明确的中文功能名；已有事项编号时使用“编号-中文功能名”。默认只使用这一份文件，不为每项任务创建详细任务文档，也不创建状态机、编号体系或额外入口。

在清单开头直接链接与这次改动相关且实际存在的需求文档和技术方案；可能有多份时全部明确列出。没有正式文档时，用一句话记录当前改动目标。链接是下游确定文档关系的依据，不能让执行者根据标题或相似文件名猜测。链接失效时先修正链接，不能随意选取同一项目中另一项并行改动的文档。

使用自然、简短的复选清单。每项描述一个可以独立判断是否完成的结果；顺序、依赖、涉及模块或完成说明只有在能防止误解或遗漏时才写。清单应让已经理解方案的执行者快速恢复工作，而不是让不了解方案的人仅靠清单重新推导实现。

创建清单后，对照当前改动目标和技术方案检查是否覆盖完整。重点是有没有漏掉实现这次改动不可缺少的部分，不使用固定覆盖矩阵，也不为了显得完整而增加任务。

执行过程中发现原范围内还有必要工作时，直接补入清单；任务不再需要时删除或说明取消原因。开始、完成或阻塞后及时更新对应项，保持清单反映真实状态，不在其中堆积命令输出、讨论过程或执行日志。

## 完整性审查

任务清单初步完成后，使用两个新的 subagent 检查它是否真正覆盖当前改动：

1. 只把任务清单及其明确链接的需求和技术方案交给第一个 subagent，不提供用户对话或主 agent 的理解。让它提出至少 10 个有价值、能够检验任务覆盖、依赖和完成边界的问题。不能为了满足数量加入同义问题或具体代码写法。
2. 只把相同材料和这些问题交给第二个 subagent。让它完全根据材料逐题回答；无法判断时必须明确写“不确定”，不能自行补全任务或方案。
3. 主 agent 根据完整上下文和项目证据独立判断答案，再与第二个 subagent 的答案比较。如果差异表明必要工作可能遗漏、任务范围错误或依赖关系会导致执行不完整，就修改清单并重新审查。
4. 如果问题触及应由执行者决定的代码细节，或者答案差异不影响修改范围和完成判断，不为了一致而扩写任务清单。

审查问答不写入任务清单；除非用户要求保留，否则不额外创建审查文档。这个审查只检查计划覆盖，不重新审查需求或设计本身。

## 边界

- 不要求先经过需求或设计阶段，也不要求已有正式文档。
- 不决定技术方案；发现会改变整体实现方向的问题时，先继续设计，而不是在任务清单中偷偷补方案。
- 不编写实施步骤、函数设计、伪代码、逐行修改说明或详细测试脚本。
- 不修改代码、配置、测试或数据，不执行任务，也不负责验收。
- 不为一次显而易见的小改动制造额外规划成本。
