# 项目规划

创建一份精简、可持续更新的任务清单，让执行者在开发过程中不会忘记修改范围、遗漏必要工作或过早认为任务已经完成。

## 核心原则

- 计划是范围和进度的记忆，不是需求文档、技术方案或代码教程。
- 直接引用已有的问题说明、已确认需求或已确认技术方案，不复制其内容，也不重新设计实现方式。
- 只列为了完整交付这次改动确实需要完成的任务。每项任务都必须能追溯到已确认的上游结论，或当前项目中完成该结论不可缺少的真实交付项。存在功能迁移基线时，同时覆盖源能力迁入项和目标承载面兼容项；不能只把新功能机制转成任务。覆盖必要的代码、配置、数据、当前改动验证和文档改动，但不加入顺手优化、全项目回归或无关工作。
- 任务粒度以便于跟踪真实完成情况为准。不要细化成函数、代码行、机械操作或单个文件；一项任务包含多个能够独立失败、依赖不同前置条件或需要分别验证的结果时，应当拆分。
- 一项任务说清可独立判断的交付结果即可；只有确实影响执行时才补充来源、完成边界、涉及范围、依赖或顺序。
- 既有测试只有在用户、已确认上游文档或项目明确维护规则将其指定为本次有效基线，或者测试已随本次需求同步更新时，才能作为任务完成依据。不能根据测试文件存在、名称相似或历史上曾通过，推断它仍然有效。
- 简单到执行者不可能遗忘范围的一步改动，不主动创建计划。用户明确只要求计划时，仍然只提供清单，不擅自开始实现。

## 工作方式

理解当前问题、改动目标以及已经确定的技术方案。正式需求文档和技术方案文档都是可选输入；当前对话已经足够清楚时直接使用。如果项目中已经存在与本次改动对应的正式需求或技术方案，先检查其状态、待决定事项和与用户当前表达的一致性：只有用户已经明确认可、状态为“已确认”或项目等价状态的正文才能作为规划输入；仍为草稿、包含会改变交付范围的待决定事项或与用户当前表达冲突时，先回到对应阶段。按需查看项目，只确认任务范围、真实落点和必要依赖，不在规划阶段重新进行完整技术设计。

计划不是技术方案进入执行的强制门禁。当前方案明确且没有实质待决项时，用户要求“开始实施、按此修改、继续开发”可以直接进入原子化执行；不需要为了交接先创建或确认计划。技术方案在计划形成后发生实质变化、出现新的替代或修复方案，或原计划没有直接链接当前采用的方案时，旧计划不再作为执行来源；只有仍需要跨会话跟踪或多人协作时，才按当前方案更新计划。

创建或更新一份 Markdown 任务清单。沿用当前改动的版本和中文工作名称；路径优先遵循用户指定，否则沿用原有规范，写入 `workplace/<版本>/implementation-planning/<工作名称>.md`。没有上游文档时，文件名优先采用简短、明确的中文功能名；已有事项编号时使用“编号-中文功能名”。默认只使用这一份文件，不为每项任务创建详细任务文档，也不创建状态机、编号体系或额外入口。第一次创建时按项目规范标记状态；项目没有约定时标为“草稿”。

在清单开头直接链接与这次改动相关且实际存在的需求文档和技术方案；可能有多份时全部明确列出。没有正式文档时，用一句话记录当前改动目标。链接是下游确定文档关系的依据，不能让执行者根据标题或相似文件名猜测。链接失效时先修正链接，不能随意选取同一项目中另一项并行改动的文档。

使用自然、简短的复选清单。每项描述一个可以独立判断是否完成的结果，并能从上游正文或项目必要事实找到来源；来源容易混淆时直接标注对应章节或依据。顺序、依赖、涉及模块或完成说明只有在能防止误解或遗漏时才写。清单应让已经理解方案的执行者快速恢复工作，而不是让不了解方案的人仅靠清单重新推导实现。

创建清单后，对照当前改动目标、技术方案和已确认迁移账本检查是否覆盖完整。重点检查有没有漏掉实现新能力、保留受影响既有能力和验证组合结果所必需的部分，以及每个任务是否都有来源和可判断的完成边界；不使用固定覆盖矩阵，也不为了显得完整而增加任务。跨层集成或高风险公共契约会决定大量后续工作时，在已确认方案范围内优先安排一个有代表性的端到端结果及其验证，尽早暴露契约偏差，而不是等全部分层工作完成后才首次闭环。

执行过程中发现已确认范围内还有必要工作时，可以补入清单并记录来源；任务不再需要时说明取消原因，不能因实现困难静默删除。新增内容会改变用户行为、技术方向、公共契约、目标承载面或交付范围时，不能直接写成执行任务，必须返回迁移、需求或设计阶段确认。开始、完成或阻塞后及时更新对应项，保持清单反映真实状态，不在其中堆积命令输出、讨论过程或执行日志。

## 完整性审查

任务清单初步完成后，使用两个新的 subagent 检查它是否真正覆盖当前改动：

1. 只把任务清单及其明确链接的需求和技术方案交给第一个 subagent，不提供用户对话或主 agent 的理解。让它搜索任务覆盖、依赖和完成边界；每个候选问题必须指出清单位置、可能遗漏的交付结果及其影响，不能加入同义问题、具体代码写法或没有上游来源的新机制。候选问题只是搜索线索，不是正式遗漏，数量不是完成标准。
2. 把任务清单、明确链接的上游正文和候选问题交给第二个 subagent，允许它按需查看与问题直接相关的代码、配置和项目规则。要求它逐项记录上游依据、项目事实、具体缺失结果、影响和分类；分类至少区分“计划确实遗漏”“上游真实缺口”“已有覆盖”“执行细节”“前提错误或超出范围”。无法查证时明确写“不确定”，不能自行补全任务或方案。
3. 主 agent 根据完整上下文和项目证据复核分类。只有证据表明确有必要交付内容遗漏、任务范围错误或依赖会导致执行不完整时才修改清单；审查者提出的新机制没有已确认上游依据或项目必要事实时必须丢弃。
4. 确认属于上游真实缺口且会改变用户行为、技术方向、公共契约或交付范围时，将计划保持或恢复为草稿并返回对应阶段，不能在任务清单中替上游拍板。问题只触及执行者决定的代码细节，或差异不影响修改范围和完成判断时，不为了一致而扩写任务清单。

审查问答不写入任务清单；除非用户要求保留，否则不额外创建审查文档。这个审查只判断计划覆盖和候选问题是否有依据，不重新设计需求或方案。集中查证和处理一轮中的全部实质问题；修改影响任务覆盖、依赖或完成边界时，只复审修改项及受影响关系，不重新强制生成一批全量问题。

## 完成与交接

规划阶段完成不表示已经证明不存在未知问题。只有上游输入有效、规定的完整性审查已经执行、候选问题均已查证分类、实质遗漏已经处理，并且用户已经审阅和明确认可当前任务范围、顺序与完成边界，才能将计划标记为已确认并交给执行阶段。用户确认后，如果任务范围、依赖或交付结果发生实质变化，重新标记为草稿并确认受影响内容。

## 边界

- 不要求先经过需求或设计阶段，也不要求已有正式文档。
- 不决定技术方案；发现会改变整体实现方向的问题时，先继续设计，而不是在任务清单中偷偷补方案。
- 不编写实施步骤、函数设计、伪代码、逐行修改说明或详细测试脚本。
- 不修改代码、配置、测试或数据，不执行任务，也不负责验收。
- 不为一次显而易见的小改动制造额外规划成本。
