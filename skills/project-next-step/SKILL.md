# 项目下一步

基于真实项目状态、既有候选和用户目标，帮助用户决定现在最值得投入的一项工作。该 Skill 属于流程型：先调查和比较，再由用户确认，最后记录决定并给出后续阶段入口。

## 触发与边界

**触发**：用户询问“项目下一步做什么”“先做哪个”“当前最值得推进什么”，需要比较多个方向，或希望先调查项目再决定优先事项。

**不触发**：下一项工作已经确定，只需要澄清需求、设计方案、拆分任务或执行代码；用户只要求维护已经决定的 Roadmap 内容。

**与其他 Skill 的关系**：

- 关键事实无法通过当前调查可靠确认时，可调用 `project-research`，见其 SKILL.md；不可用时自行完成最小必要调查并明确不确定性。
- 决定确认后，可按事项成熟度调用 `project-requirements`、`project-design` 或 `project-planning`，见各自 SKILL.md；不可用时给出清楚的交接摘要。
- 需要把已确认决定同步到 Roadmap 时，可调用 `project-workspace`，见其 SKILL.md。

## 存储与路径契约

确认后的决策记录默认写入 `workplace/<版本>/decisions/<YYYY-MM-DD>-<简短中文名称>.md`。版本按用户指定、项目当前明确使用的活动版本或现有工作文档确定，不根据版本号大小猜测。无法可靠确定版本时，退化到 `workplace/decisions/<YYYY-MM-DD>-<简短中文名称>.md`，不为写文件虚构版本。

同一决策尚在讨论时不创建多个文件；用户重新打开原决定时更新原文件，并保留“原决定、改变原因、新决定”的简短说明。不同决策使用新文件。路径优先遵循用户或项目已有规范。

决策记录只保存当前判断所需的信息：决策范围、项目证据、候选比较、已选下一步、暂不选择的原因、主要不确定性和建议交接方向。不复制完整调研、需求、设计或任务清单。

## 阶段与流转

| 状态 | 含义 | 可进入的下一状态 |
|---|---|---|
| `discussing` | 正在调查、比较或等待用户取舍 | `confirmed`、`blocked` |
| `confirmed` | 用户已经明确接受某个下一步 | `done`、`not_verified`、`discussing` |
| `not_verified` | 决定已确认，但决策记录未能写入或复核 | `done`、`discussing`、`blocked` |
| `done` | 决策记录已写入并与确认内容一致 | `discussing` |
| `blocked` | 连续无法取得决定所需的关键条件 | `discussing` |

切换条件：

- `discussing` → `confirmed`：用户明确选择或接受首选项；agent 的单方面推荐不算确认。
- `confirmed` → `done`：决策记录写入成功，重新读取后与确认内容一致。
- `confirmed` → `not_verified`：决定已经确认，但保存或复核条件不满足。
- `confirmed` / `done` → `discussing`：新证据、约束变化或用户要求重新选择。
- 任一未完成状态 → `blocked`：达到“失败与回退”定义的持续阻塞条件。

## 执行步骤

1. **定义本次决定**。说明要决定的时间尺度、可支配资源和“下一步”的粒度。默认选择一个可以进入需求、调研、设计、规划或执行阶段的完整事项，不把一条命令当作方向，也不扩张成季度 Roadmap。
2. **建立现状证据**。检查项目目标、当前阶段、正在进行和刚完成的工作、Roadmap 与待办、用户或运行反馈、缺陷与风险、依赖、Git 状态和已有工作文档。区分当前事实、历史结论、用户偏好和推断；能从项目查清的内容不询问用户。
3. **形成候选集**。同时纳入已有事项和调查中新发现的机会，合并重复项并删除已完成项。候选通常保留 3–7 个，应考虑完成在制工作、解除阻塞、降低关键风险、验证高不确定方向、交付用户价值以及暂不启动新工作的可能性；不为覆盖类别机械凑数。
4. **检查可行性**。排除缺少不可绕过前置条件、明显超出当前权限或资源、与目标无关或没有任何事实依据的候选。前置条件本身更紧迫时，把它提升为独立候选，不把不可执行事项排在首位。
5. **统一比较**。用相同维度比较候选：目标影响、紧迫性与延迟代价、证据可信度、投入与见效速度、依赖、风险与可逆性、学习价值、是否符合项目当前阶段。没有真实权重和数据时不计算总分；直接说明关键优势、代价和不确定性。
6. **澄清价值取舍**。只有项目证据无法回答、且不同答案会改变首选项时才询问用户。得到回答后更新全部受影响候选，不只为原推荐寻找支持。
7. **给出建议**。推荐一个首选下一步，说明期望改变、为什么是现在、关键证据、主要风险和进入下一阶段所需的第一个动作；同时保留 1–2 个后续候选，并解释其当前不优先的原因。明确列出仍可能推翻建议的不确定性。
8. **取得确认并记录**。用户未确认时保持 `discussing`，不把推荐写成最终决定。确认后写入决策记录并重新读取复核；保存失败时标记 `not_verified`，不得声称完成。
9. **交接下一阶段**。根据已选事项当前缺口建议进入需求、调研、设计、规划或执行之一。只提供交接入口和必要上下文，不在本 Skill 内继续完成下游工作，也不自动开始执行。

## 校验与门槛

给出推荐前必须满足：

- 决策范围、时间尺度和当前项目目标已经明确；
- 候选同时覆盖已有事项与调查发现，且不存在明显重复、已完成或不可执行项；
- 所有候选按同一组维度比较，事实有来源，未知项明确标注；
- 首选项没有被更紧迫的阻塞、风险或不可绕过依赖否决；
- 至少解释最有竞争力的未选项为什么不是现在；
- 比较方式符合第五步，未让新颖程度、沉没成本或实现难度取代项目价值。

多轮讨论时比较本轮与上一轮的候选覆盖、证据可信度和取舍清晰度。新增证据导致首选项变化，或两个及以上候选的先后关系变化时，重新执行完整候选比较；不能只修改推荐结论。任何候选从“有证据”退化为“无证据”都必须在推荐前补查或明确降级其可信度。

## 失败与回退

- 找不到可靠项目目标或当前状态时，保持 `discussing`，先完成最小事实调查；缺失内容只能由用户提供时再询问。
- 决定依赖一个可调查但尚未确认的关键事实时，暂停排序并先调查；不要用低可信假设制造确定推荐。
- 多个候选的差异本质上是用户价值取舍时，展示冲突和建议，等待用户决定；不要通过任意加权替用户拍板。
- 已确认决定被新证据推翻时回到 `discussing`，保留原决定和改变原因，重新比较后再确认。
- 同一关键阻塞连续三轮仍无法解除时标记 `blocked`，说明缺少的条件及其对决定的影响。

## 提问契约

默认把互不依赖、都会改变候选排序的事项合并为一轮 2–5 个编号问题。每个问题先说明已知证据、需要用户决定的取舍、不同答案会改变什么以及推荐方向。只有当前答案会决定其余问题是否成立，或确实只有一个价值分歧时，才单独问一个问题。

不要询问可以从项目调查得到的事实，不要求用户替 agent 汇总 Roadmap、代码状态或已有文档。问题放在回复末尾，用户回答后统一重算受影响候选。

## 证据与完成定义

推荐必须能够追溯到项目文件、代码与 Git 状态、运行或用户反馈、已有 Roadmap 与工作文档，或用户明确表达的目标和约束。历史文档中的计划不自动等于当前事实；无法验证其现状时降低证据可信度。

完成证据是经过用户确认并重新读取复核的决策记录，其中必须能找到首选项、后续候选、关键依据、不确定性和交接方向。推荐文本或口头确认本身不能替代这份记录。

## 边界声明

本 Skill **不做**：

- 不把选择下一步扩张为完整 Roadmap、季度规划或资源排期；
- 不修改 `ROADMAP.md`，不自动改变已有事项优先级或状态；
- 不编写需求正文、技术方案、实现任务清单或生产代码；
- 不在用户确认前把推荐包装成项目决定，也不自动启动后续工作；
- 不默认新功能比完成在制工作、修复问题或暂不启动更重要。
