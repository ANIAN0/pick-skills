# 项目无人值守

把一句话需求交给一组相互独立的阶段 subagent，持续推进到代码完成、测试通过、验收完成并创建本地 Git 提交。主 agent 只负责编排、核对真实产物、判断回退和处理阻塞，不重新代替各阶段工作。

## 无人值守的含义

- 对能够从用户原话、项目代码、项目规则和可靠证据中判断的事情自主完成，不要求例行确认。
- 不把“无人值守”理解为可以猜测产品决策。缺少会实质改变功能结果的用户选择，且无法从项目中可靠推出时，保留已完成工作并向用户提出最小必要问题。
- 审查问题、行业惯例、subagent 偏好和“通常做法”都不是需求来源。任何新增结论必须能追溯到用户、项目事实或调研证据。
- 只处理当前一句话需求，不顺带重构、清理或提交其他改动。

## 权限

用户明确调用本 skill，即授权在当前项目内为这项需求：

- 创建和修改需求、调研、UI、方案、计划、代码、配置、迁移和当前需求专用测试。
- 运行与当前需求相关的开发、自测、独立测试和验收操作。
- 删除确认由本次工作产生且不应交付的临时文件。
- 精确暂存本次修改，并由 `project-acceptance` 创建一个或多个本地 Git 提交。

这项授权不包含推送、创建 PR、部署、发布、变基、改写历史、修改生产数据、发送外部消息、申请凭据或处理无法确认归属的用户文件。需要这些动作时必须另行获得明确授权。

## 编排原则

一次只运行一个阶段 subagent，并等待它及其内部审查 subagent 全部结束后再进入下一阶段。不要并行运行会读取不同版本产物的阶段，也不要让多个 agent 同时修改工作区。

为每个阶段创建新的 subagent，尽量不给它继承主对话。阶段任务中明确提供：

- 用户最初的一句话原文。
- 项目根目录、当前版本和稳定的中文工作名称。
- 本阶段必须读取的真实文件及直接路径。
- 本阶段允许修改的范围和应使用的 skill。
- 预期产物，以及无法继续时应返回的具体阻塞证据。

阶段之间传递原始文档、代码、差异和测试证据，不传递替代这些材料的对话摘要。subagent 完成后，主 agent 必须亲自读取产物、Git 差异或测试结果，确认文件真实存在且内容符合本阶段职责；不能只相信 subagent 的完成声明。

在阶段委派中要求 subagent 达到本阶段完成条件后立即返回准确产物路径和验证结论，不等待下一条指令，也不顺手执行下游阶段。审查剩余问题已经确认属于下游实现细节或非阻塞偏好时，本阶段应结束，不能为了消除所有“不确定”继续循环。

每个阶段只有一个产物负责人。阶段 subagent 可以调用调研获得证据，但不得同时修改其他阶段正文或提前完成下游工作；主 agent 也不能把多个阶段合并进一次委派。当前阶段未达到完成条件时，只能继续当前阶段、返回上游或明确受阻。

所有阶段沿用同一版本和工作名称。需求、设计和计划使用各自已有目录规范和直接链接，不增加重复的总报告或状态台账。把用户最初的一句话原样保存在需求正文同名二级目录的 `原始需求.md`，作为整条链路不变的来源锚点。

## 开始前

读取项目内适用的 `AGENTS.md`、`CLAUDE.md`、`PROJECT_RULES.md`、`ROADMAP.md` 和相关项目说明，确认项目根目录、当前版本、构建方式与约束。检查 Git 状态和已有暂存、未暂存、未跟踪内容，记录开始前已经存在的修改范围。

从用户原话和项目命名中确定简短、稳定且尽量使用中文的工作名称；已有事项编号时沿用“编号-中文功能名”。优先使用项目当前明确版本和目录规范。项目、版本或目标范围无法可靠确定且选错会污染其他工作时停止，不自行选择。

开始前存在用户修改并不自动阻止流程。只要能够可靠区分当前需求和既有修改，就保留并避开它们；无法区分且存在覆盖、删除或误提交风险时停止并说明具体文件。

## 阶段链路

### 1. 需求

委派 subagent 使用 `project-requirements`。让它先建立 `需求地图.md`，把用户提出的每项功能区分为“仅有功能名、候选行为、已决定、有争议、已排除”，再根据原始一句话和项目中与用户行为直接相关的证据形成简洁需求正文，并完成该 skill 自带的清晰度审查。不能因为无人值守而替用户补造功能规则。委派时明确要求：用户的引用、反问和建议不是确认；SDK 能力、参考项目行为和审查回答中的“不确定”不是目标需求；参数解析、存储失败和框架默认行为等留给设计或执行。本阶段只允许修改需求材料。

主 agent 读取需求地图、需求正文、变更记录和审查材料，逐项检查首期能力是否都有目标、入口与对象、主要操作、反馈和可见结果。任一首期能力仍只有功能名、候选行为或处于有争议状态时，需求保持草稿；先从项目证据中查找，仍不能判断时停止并询问用户。不能因为正文篇幅完整或已经生成技术材料就进入下游。

用户在本阶段或后续阶段质疑需求来源、参考完整性或对象理解时，立即回到需求的质疑修复态，撤回受影响结论及其下游派生，不把质疑改写为新的行为基线。修复只允许调查事实、呈现候选差异和取得必要决定；所有“有争议”条目重新收敛前，不恢复下游阶段。

### 2. 参考功能双基线与必要调研

用户原话、需求或项目材料提到其他项目、模板、旧版本或既有实现时，先逐个判定其角色：行为基线、视觉参考、SDK/框架/平台候选、数据或协议来源、实现证据。只有“行为基线”才委派 subagent 使用 `project-feature-migration`，锁定源和目标工作区，建立源功能与目标承载面双基线，解决映射和契约冲突，并完成风险匹配的完整性审查。其他角色交给限定问题的调研或设计，不能合并进完整迁移账本。

存在行为基线时，迁移基线未确认不得进入依赖该迁移的技术设计；目标承载面调查不能被普通项目调研或设计证据基线替代。迁移 subagent 只修改迁移材料。

迁移调查发现新的用户可见目标能力、差异或冲突时，重新委派需求 subagent 补齐现状基线和需求正文并复审；不能由迁移或设计 subagent替用户决定保留、改变或移除。

根据需求正文和项目现状识别会影响需求或技术方向的真实不确定项。每个调研任务必须是明确问题，委派新的 subagent 使用 `project-research` 调查；可以对紧密相关的少量问题使用有边界的批次。没有需要调研的问题时直接进入下一阶段，不为满足流程制造报告。

调研结论改变用户可见需求时，重新委派需求 subagent 将其作为候选差异处理并复审；只影响技术选择时，把真实调研文件路径交给设计阶段。调研不得用“应采用某参考”“应组合多个参考”替需求阶段作决定；证据仍不足时保留“不确定”，不能把推断升级为事实。

### 3. 可选 UI 说明和原型

需求包含非简单界面、页面流转或关键交互时，委派 subagent 使用 `ui-requirements-doc` 形成 UI 正文。只有原型能够明显降低实现歧义，或用户原话明确需要原型时，才再委派 `html-prototype-generator`；微小样式修改和已有模式足够明确的界面不强制生成原型。

UI 文档和原型必须服从已经确认的需求及项目设计依据，不能利用“设计选择”掩盖产品决策缺失。原型未经过用户确认时只能作为实现沟通材料，不能反向覆盖需求正文。

### 4. 技术设计

委派 subagent 使用 `project-design`。提供需求、已确认迁移基线（如有）、相关调研、UI 材料和项目根目录的直接路径，让它基于现有代码与项目约束确定整体方案、关键文件修改及原因，并完成清晰度审查。

主 agent 检查方案是否引用了实际采用的上游材料，是否处理了调研结论，以及文件边界是否能够指导计划。方案扩大目标承载面时先回到迁移阶段补兼容基线；方案暴露用户可见需求问题时回到需求；需要新证据时回到调研；不要在设计正文里自行补齐上游缺口。

### 5. 任务计划

委派 subagent 使用 `project-planning`。只向它提供原始需求、已确认正文、实际技术方案、相关 UI 或调研材料的直接路径，让它形成用于防止漏改的任务清单并完成覆盖审查。

主 agent 确认清单明确链接真实需求和方案，且覆盖方案中的必要修改、自测准备和交付内容。任务数量应由改动决定，不为流水线形式拆出无意义步骤。

### 6. 执行与自测

委派 subagent 使用 `project-execution`。提供原始需求及需求、方案、计划的准确路径，并明确开始前已有的用户修改。让它完成真实代码、必要的当前需求专用测试和自测，以及该 skill 自带的独立实现审查。

执行阶段不得运行、修改或评价并非当前需求创建或更新的既有测试文件。主 agent 在阶段结束后检查完整差异、计划完成情况和实际自测证据；临时脚本或数据不能冒充正式功能。

### 7. 独立测试与实现审查

委派新的 subagent 使用 `project-review`，把它作为独立测试阶段。提供原始需求、实际需求正文、技术方案、任务清单、完整当前需求差异、相关代码和执行自测证据，但不提供主 agent 的预期结论。

要求它分别检查设计符合性和受影响既有能力回归，独立走通真实调用链并设计、执行与风险相称的验证，列出本轮全部实质问题。既有测试通过只能作为辅助证据，不能替代对当前功能、目标兼容项和技术设计的独立验证。

根据问题根因自动回退：

- 代码写错、漏改、未真实接入或自测无效：回到执行。
- 方案清楚但任务范围遗漏：回到计划，再执行受影响任务。
- 技术方向、文件职责或关键设计错误：回到设计，再更新计划并执行。
- 源功能、目标承载面或双向迁移契约遗漏：回到迁移，再重跑所有受影响下游阶段。
- 问题实际来自需求理解错误：回到需求，并重新运行所有受影响的下游阶段。

回退时把审查问题和证据交给对应阶段，不把审查者建议直接当作正确答案。只重跑受影响的阶段；修复后必须重新执行独立测试。没有新证据、代码或文档变化时，不重复同一轮审查制造循环。

### 8. 最终验收与本地提交

独立测试没有阻塞问题后，委派 subagent 使用 `project-acceptance`。提供原始需求、全部实际采用的文档、实现审查结论、开始前 Git 基线和当前完整工作区状态。

让它梳理本次修改、清理本次临时产物、避开所有用户无关修改，设计逻辑提交批次，并按批次完成最终验收；最后一个批次提交前必须使用全部本次修改做整体用户路径和目标兼容回归。验收发现上游问题时按前述规则回退，受影响批次重新验收后才能提交。

所有批次完成后，主 agent 再检查 Git 状态和提交记录，确认本次应交付内容均已提交、提交范围与验收对象一致，剩余未提交内容只有明确识别的用户无关修改。不要自动推送或部署。

## 阻塞与结束

以下情况不能用猜测、跳过验证或降低标准绕过：

- 缺少会实质改变功能的产品决策。
- 无法区分当前需求与已有用户修改。
- 关键验证依赖缺失的权限、凭据、设备、环境或外部服务。
- 继续需要未授权的生产操作、外部写入或破坏性动作。
- 项目规则、用户要求和真实代码状态存在无法自行消解的冲突。

阻塞时停止会扩大风险的动作，不暂存或提交受影响批次。保留已经形成的文档和安全修改，向用户说明已经完成到哪里、具体证据、唯一需要回答或授权的事项，以及恢复后从哪个阶段继续。

成功结束时只向用户汇总最终功能、关键验证、本地提交哈希、仍存在的非阻塞风险和明确保留的用户无关修改。阶段过程和 subagent 对话留在对应文档或工具记录中，不用冗长流水账重复汇报。
