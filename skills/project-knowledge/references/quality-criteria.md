# 质量与验收

只在迁移、批量更新、健康检查或交付前读取。

## 结构检查

- `_meta/coverage.json` 与当前文件系统重新扫描结果一致；没有漏记、失效条目、未说明的排除或 `pending`。
- 读者入口、Agent 维护说明和 schema 各有唯一权威位置；现有站点没有出现竞争入口。
- 普通概念 frontmatter 可解析，必填字段符合 profile schema，未知字段在更新中保留。
- 目录只包含已存在的稳定类型，索引列出实际页面并解释用途。
- 本地 Markdown 链接有效；移动或替代页面的入链已处理。
- 同一稳定身份只有一个规范页，原始来源、综合结论和历史版本未混为副本。

## 内容检查

- 关键结论有可访问来源，来源的版本、日期和权威范围足以支持结论。
- 当前事实、历史事实、计划、推断、冲突和未知有明确区分。
- `active` 页面没有被更高权威来源推翻；`superseded` 与 `deprecated` 页面说明原因并指向当前结论。
- 页面回答真实检索问题，包含边界和失效条件；无只有标题、目录复述或模板空话的薄页。
- 强关系完整且带语义；导航或弱相关没有制造机械反链。

## 维护检查

- 本次变化已同步规范页、强关系、最近索引和日志。
- 到期 `review_after`、失效来源、孤立关键页和未处理 inbox 已列出或修复。
- 删除只发生在无入链、无审计价值且有更可靠来源的内容；其他旧知识使用生命周期状态处理。
- 原始资料及其版本历史得到保留，迁移没有覆盖未知用户内容。

## Profile 专项

### 个人知识库

- project、reference project、topic、lesson、decision 和 source 的身份没有混用。
- lesson 包含情境、证据、有效行动、结果和适用边界。
- 外部参考项目记录观察版本/日期与不适用条件。
- 完成项目已提炼可复用知识，而不是把整个项目复制或直接归档后失联。

### 项目 Wiki

- 全部源码区域已被发现并按组件分类；未深读区域有与检索目标一致的排除依据，不能因没有正文页而从覆盖统计消失。
- 批量建设前的事实基线覆盖项目定位、系统边界、核心机制、数据/状态、接口/事件、质量/运维及证据缺口。
- 覆盖主要用户价值的关键业务旅程已从真实触发点追到可观察结果，并包含跨组件交互、数据/状态变化、关键分支和失败恢复。
- 架构与工作流页解释运行机制和边界，不把目录树、启动装配、Manager 清单或 PRD 摘要包装成项目理解。
- 需求/能力与实现模块、接口或事件、数据对象和验证入口有证据映射；无法确认的历史取舍、技术债和业务事实保持为推断或缺口。
- 导航按用户任务组织，新读者能在两次导航内找到 quickstart 和主要 reference。
- 步骤有前置条件、预期结果和失败入口；高风险示例经过与风险相称的验证。
- API、CLI、配置、UI 和版本说明与当前发布事实一致。
- 公开层不包含凭据、内部地址、未发布能力或不必要实现细节。
- 现有站点构建、导航目标、链接和代码块渲染通过。

### 产品 Wiki

- 当前 capability、规范 requirement、iteration/decision 和原始 source 三层可互相追溯。
- 每个稳定需求有独立知识库需求页；索引逐项链接规范页和精确来源，不用目录链接、“同上”或总索引代替文件级处置。
- 需求有稳定 ID、业务状态、所属模块/能力、迭代、来源及相关/替代关系。
- 重复 ID、标题冲突和同一需求修订链已显式裁决或记录为缺口，不能把冲突 ID 当作唯一身份。
- 新来源进入后，受影响的当前能力和完整替代链已同步。
- 同一需求的文件修订没有被误建为多个独立需求。

## 检索验收

用 3–5 个来自真实场景的问题测试，不用文件名提示答案。至少包含：

- 一个精确事实查询。
- 一个需要跨页面和关系链综合的问题。
- 一个涉及旧版本、替代项或冲突来源的问题。
- 一个找不到可靠答案的问题，验证 Agent 会报告缺口而不是编造。

个人库应能找出相似项目的历史经验与适用边界；项目 Wiki 应能指导新用户完成关键任务并找到当前契约；产品 Wiki 应能为一个新需求返回相关能力、需求、迭代、决策和来源，并形成可追溯的需求上下文包。

## 独立审查

- 批量任务的 reviewer 未参与建设，收到的是原始路径和目标而不是建设者结论。
- reviewer 已核对覆盖等式、遗漏目录、断链、精确来源、稳定身份冲突、薄页和真实检索问题。
- 修订后阻塞问题数下降且没有新增高严重性回归；审查证据包含问题路径与复验结果。
