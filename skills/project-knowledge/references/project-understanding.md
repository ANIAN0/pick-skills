# 项目理解契约

只在为真实软件项目初始化、迁移或批量刷新知识库/Wiki，或审计项目文档是否符合实现事实时读取。目标不是读完所有代码，而是先建立足以支撑计划文档的**事实基线**。

## 证据证明力

- 目录树只能证明文件分布，不能证明模块职责、业务边界或调用关系。
- `main`、应用装配和依赖注入入口只能证明启动时连接了什么，不能单独证明运行时行为。
- PRD、README 和旧 Wiki 说明预期或历史背景；当前行为仍需由代码、契约测试、配置、运行结果或已发布接口复核。
- 单个类或 Manager 只能证明局部实现；跨模块结论必须沿调用、事件或数据链追踪。
- 技术决策、历史原因和技术债不能从代码形状猜测；必须有 ADR、提交/Issue、注释、测试约束、维护者说明等证据，否则标为推断或缺口。

## 研究顺序

1. 先完成文件系统全量 inventory 和权威文档逐文件处置，再读取项目级说明、构建与依赖清单、启动方式、现有文档、发布记录和测试入口，确定项目边界、可运行组件和版本。不得依赖 `.gitignore` 或已知目录名推断完整范围。
2. 从对外触发点反向定位真实入口：UI 操作、API/CLI、消息、定时任务、Worker 或文件导入；不要只停在进程启动入口。
3. 对每个高频问题选择能代表核心价值的业务旅程，沿“触发 → 接口/路由 → 编排/引擎 → 领域服务 → 数据/状态 → 异步事件或外部系统 → 可观察结果”追到终点，同时记录关键分支、失败和恢复。
4. 交叉读取模型/schema、迁移、配置、权限、队列/事件定义和测试，确认数据身份、状态机、事务边界、并发/重试及前后端契约。
5. 用可执行测试、命令、接口响应、日志或 UI 观察验证高风险结论；无法运行时用两类独立静态证据互证，并明确未运行。
6. 对照需求、旧文档与当前实现，区分“当前已发布”“存在但未接入”“计划中”“历史遗留”和“无法确认”。

先广度发现全部组件、文档类型和候选链路，再对与读者问题直接相关的链路纵向追踪。代码量大不是只做目录摘要的理由；源码可以分类后不深读，但既有文档必须逐文件处置，与目标无关的内容必须说明排除依据。

## 事实基线

开始批量写知识页前，至少形成以下内部工作结果；只把其中长期有效的结论写入知识层：

| 维度 | 必须回答 |
|---|---|
| 项目定位 | 服务哪些角色、解决什么问题、不解决什么 |
| 业务旅程 | 主要角色如何从触发动作得到可观察结果 |
| 系统边界 | 运行组件、外部依赖、前后端/Worker/服务之间如何协作 |
| 核心机制 | 编排器、Agent/规则/任务引擎等如何被驱动，关键分支在哪里 |
| 数据与状态 | 核心实体、身份、状态迁移、持久化和一致性边界 |
| 接口与事件 | 输入输出契约、事件时序、失败、重试和幂等行为 |
| 质量与运维 | 关键测试、配置、观测、真实故障入口与恢复路径 |
| 决策与缺口 | 有证据的取舍、已知债务、冲突和仍无法确认的事实 |

为核心结论维护证据矩阵：`结论 | 类型（事实/推断/缺口） | 直接证据路径与符号/位置 | 互证 | 适用版本 | 将进入的页面`。文件路径必须尽量精确到符号、路由、schema、测试或命令结果；“参考 main.py”或“参考 backend 目录”不够。

## 写入门槛

同时满足以下条件才开始批量生成内容页：

- 每个计划中的核心页面都对应真实读者问题，并在证据矩阵中有支撑；没有证据的页面不为补齐目录而创建。
- 至少已纵向追踪覆盖主要用户价值的关键旅程；涉及多个运行组件时，链路跨过真实组件边界而非停在单个入口。
- 架构、工作流、数据模型和能力结论能解释行为、边界与失败，不只是目录、类名或 Manager 清单。
- 需求/能力已映射到实现模块、接口/事件、数据对象和验证入口；无法映射的内容明确标为计划或缺口。
- 冲突和未知不会被改写成确定语气；公开页只采用达到发布可信度的结论。

未通过时只允许输出研究范围、证据矩阵、已确认事实、缺口和建议的继续调查路径，或修复已经证伪的页面；禁止先生成一套模板页再承诺后补事实。

## 提问边界

先查尽可访问的代码、测试、配置、历史和运行证据。只有业务目标、未落盘决策或访问权限确实掌握在用户手中，并且缺失会实质改变文档结论时才提问；提问应附已确认事实与具体缺口，不把“整体还是某模块需要补深”这类项目理解责任交给用户。
