# 软件项目理解

只在 project profile 摄入源码/工程文档或验证 operational 里程碑时读取。完整 inventory 负责广度；逐来源事务和后续综合负责深度。

## 证据证明力

- 目录树只证明文件分布；启动装配只证明连接关系；单个类只证明局部实现。
- PRD、README 和旧 Wiki 说明预期或历史；当前行为由代码、schema、契约测试、配置、运行结果或发布接口复核。
- 跨组件结论必须沿调用、事件或数据链追踪。技术取舍和债务需要 ADR、提交/Issue、测试约束、注释或维护者说明，否则是推断/缺口。

## Inventory 阶段

从扫描结果生成 repository map：全部一级目录、每个权威根的直接子目录、空目录、忽略项、嵌套仓库、遍历/读取错误和版本/迭代兄弟项。只列“主要目录”或文件总数不合格。

repository map 只用于确定来源边界、队列优先级和候选旅程，不直接生成架构/模块页。优先级按读者问题安排：发布契约与当前文档、外部触发点、schema/模型、编排/领域、事件/队列、测试与运维；优先不等于忽略低优先来源。

## 单来源分析

处理一个工程文件时：

1. 说明该文件实际证明的职责、输入输出、状态和失败行为；
2. 定位解释它所必需的直接调用者、被调用者、schema、配置和测试，但不把这些依赖标记为已摄入；
3. 把可独立成立的结论写为 claims，把跨文件才能成立的结论写为 synthesis/review backlog；
4. 对需求/能力记录可证实的实现模块、接口/事件、数据对象和验证入口，无法映射的保持计划或缺口；
5. 精确 evidence 到符号、路由、schema、测试或命令结果，不使用“参考 main.py/某目录”。

一个源码文件不必产生一个页面。只在它贡献长期稳定概念或修正已有概念时更新 OKF；纯胶水、生成物或无长期价值内容可有证据地处置，不制造目录镜像。

## 跨文件综合

业务旅程、架构、数据模型和核心机制不能由单文件事务直接定稿。相关来源任务完成后，创建显式 synthesis/review 工作项，沿：

```text
外部触发 → 接口/路由 → 编排/引擎 → 领域服务
→ 数据/状态 → 异步事件/外部系统 → 可观察结果 → 失败与恢复
```

综合页的每个结论链接多个已提交来源；仍 pending 的关键环节作为缺口。涉及多个运行组件时，链路必须跨过真实组件边界。

## Operational 门槛

声明某个项目问题范围 operational 前，至少回答项目定位、相关业务旅程、系统边界、核心机制、数据/状态、接口/事件、失败恢复、测试/运维和证据缺口。运行证据优先；无法运行时用两类独立静态证据互证并明确未运行。

未达到门槛时可以查询已验证的局部事实，但必须披露 coverage 和缺口；不能用模板架构页掩盖未处理来源，也不把“请用户选择哪个模块补深”当作项目调查。
