# 项目 Wiki profile

只在建设、刷新、查询或审计面向项目用户、集成方、开发者或运维人员的说明文档时读取。

## 先确定受众与发布边界

为每类主要读者列出要完成的任务和需要查到的权威事实。公开 Wiki 与内部工程知识可以共享证据，但发布边界不同：公开页只包含目标读者需要的信息；源码路径、内部拓扑、未发布能力、凭据和安全细节留在非发布证据层。

现有站点已经有 Markdown 根目录、`nav.json`、侧边栏配置、版本路由或静态生成器时，延续其文件与链接契约。不要强制改造成 OKF，也不要创建与站点导航竞争的第二套 `index.md`。

## 信息架构

按读者任务选用以下知识区，只创建实际需要的部分：

```text
docs/
├── overview/           # 项目定位、能力边界、核心概念
├── quickstart/         # 最短可验证成功路径
├── guides/             # 按用户任务组织的操作指南
├── concepts/           # 稳定原理、模型和术语
├── reference/          # API、CLI、配置、协议等精确契约
├── operations/         # 部署、升级、监控、故障处理
├── faq/                # 高频问题及诊断入口
└── changelog/          # 按发布版本说明新增、变更、废弃与迁移
```

导航从“是什么 → 首次成功 → 常见任务 → 精确参考 → 运维与版本”渐进展开。功能菜单或源码目录只能作为局部映射，不能代替读者任务导航。

内部 coding-agent Wiki 可增加 `architecture/`、`workflows/`、`decisions/`、`testing/` 和按需的 `code/`。逐文件页面只有在能说明职责、边界、关联测试和修改风险时才创建。

## 页面契约

每页明确目标读者、适用版本或更新时间、前置条件和权威来源。页面类型的最低内容：

- **Quickstart**：可执行步骤、预期结果、失败入口和下一步；安全可行时实际执行关键路径。
- **Guide**：目标、前置条件、步骤、验证、回退或故障处理。
- **Reference**：完整字段/参数、约束、默认值、错误行为、兼容性和示例；以当前发布契约为准。
- **Concept**：解释稳定机制和边界，链接相关 guide/reference，不复制操作步骤。
- **Changelog**：明确版本、发布日期、用户可见变化、破坏性变更、迁移和相关页面。

架构、工作流和能力页面从读者可观察行为出发，说明触发点、跨组件协作、数据/状态变化、输出、失败与恢复，再落到实现位置。源码目录和启动装配可以作为定位索引，不能替代这些内容；对外页面不必暴露内部路径，但结论必须由非发布证据层支撑。

一个事实只有一个权威页面；其他页面用链接和必要上下文引用。导航摘要说明页面能解决什么问题，不只重复标题。

## 证据优先级

按文档类型声明权威来源，例如：

- API/协议：已发布 schema、路由与模型、契约测试、实际响应。
- CLI/配置：当前命令帮助、解析代码、默认配置和可重复运行结果。
- UI 操作：当前发布界面、接口行为和验收结果。
- 能力与版本：已发布版本记录、确认需求和验证结果。

设计稿、未来需求和旧版本文档只能解释历史或计划，必须标注，不能覆盖当前发布事实。

## 发布维护

每次发布或用户可见行为变化时执行影响检查：受影响的 overview、quickstart、guide、reference、operations、FAQ、导航和 changelog 是否都已处理。只更新真正受影响的页面；修改 `nav.json` 或侧边栏后检查每个目标存在且可打开。

公开前验证：

- 新读者能从入口在两次导航内找到首次成功路径和主要 reference。
- 示例与当前版本一致，关键步骤有可观察的成功结果。
- 页面没有相互冲突的默认值、鉴权、错误码或版本说明。
- 没有秘密、内部地址、调试数据或未发布能力泄露。
- 站点构建、链接和代码块渲染通过现有验证方式。
