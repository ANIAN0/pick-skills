# 覆盖与审查契约

只在初始化、重建、迁移、批量刷新或覆盖审计时读取。全量分析指“所有项目文件先被发现并处置”，不等于把每个文件写成页面，也不等于同等深读所有源码。

## 全量来源账本

在 `<kb-root>/_meta/coverage.json` 记录项目相对路径。扫描不依赖 `.gitignore`，因为被忽略的历史文档、评论和排障材料仍可能是知识来源；只排除明确的生成目录、依赖缓存、虚拟环境、版本控制数据和当前 Wiki 输出目录，并记录排除规则。

每个发现的文件只能使用一个处置状态：

| 状态 | 含义 | 必填信息 |
|---|---|---|
| `mapped` | 已阅读并贡献到一个或多个规范页 | 精确目标页 |
| `consolidated` | 内容已合并进另一来源链或规范页 | 目标页与合并依据 |
| `superseded` | 来源已被更新版本替代 | 替代来源或目标页 |
| `duplicate` | 与另一来源实质重复 | 规范来源 |
| `excluded` | 与知识目标无关、生成物或不可发布 | 可复核理由 |
| `pending` | 已发现但尚未处置 | 可选的下一步 |

源码可以先按组件、语言和职责完成发现与分类，再对核心链路深读；既有 `docs/`、需求、设计、测试、发布、迁移、原型、排障和旧 Wiki 等文档语料必须逐文件进入上述六类之一。空目录也记录在 scope summary，避免把“没有文件”和“没扫描”混为一谈。

完成等式：

```text
inventory_total
= mapped + consolidated + superseded + duplicate + excluded + pending
```

初建、重建、迁移或声称“完整覆盖”时必须满足 `pending = 0`。目录级 `sources` 只声明来源范围，不能替代文件级处置；来源产生稳定需求、决策、版本或能力时，不能只映射到一个总索引，必须映射到对应规范页或说明合并关系。

## 确定性自检

使用 `scripts/audit_wiki.py`：

1. `inventory` 递归生成或同步 coverage 文件，新发现文件默认 `pending`。
2. Agent 阅读后更新每个文件的处置、目标与理由。
3. `validate` 重新扫描文件系统，检查漏记/失效条目、处置等式、权威根目录状态、目标页存在性、Wiki 本地链接和 frontmatter 来源路径。

任何漏记文件、失效条目、`pending`、不存在目标页、越界链接或断链都是阻塞错误。目录来源、缺少精确映射和未加载 PyYAML 是 warning 或验证缺口；任务要求精确来源时按错误处理。

## 独立审查

初始化、重建、迁移或一次创建/重写 5 个以上正文页时，使用未参与建设的 subagent/reviewer 做 fresh-context 审查。只给它项目根、Wiki 根、检索目标和原始材料；不提供事实基线结论、预期答案或建设者的自评。

Reviewer 至少核对：

- 文件系统与 coverage 账本是否相等，遗漏目录、空目录和排除理由是否真实。
- 每个权威文档是否逐文件处置，`mapped` 目标是否存在且不是用总索引敷衍稳定对象。
- 需求 ID 冲突、版本/状态、替代链和精确来源是否可检索。
- 本地链接、外部源路径、导航目标和 frontmatter 来源是否有效。
- 抽查核心结论能否沿源码/文档回溯，页面是否夸大覆盖、参数或行为。
- 用真实问题执行检索验收，并专门测试一个应报告缺口的问题。

Reviewer 输出问题路径、严重性和证据。建设者修复后重新运行确定性检查；复审相对上一轮若没有减少任何阻塞问题，停止继续堆页面并报告根因。
