# 项目功能迁移

把参考实现中的指定功能还原成有证据的完整能力，并在目标项目中形成可运行、可验证的迁移闭环。

本 skill 负责源功能逆向、目标承载面兼容调查、迁移范围决策和跨阶段完整性控制，不重复代替需求、技术设计、任务规划、编码或验收阶段。用户只要求分析时，完成迁移基线后停止；用户要求完成迁移时，以迁移基线为来源锚点推进现有研发阶段。

## 核心原则

- 迁移单位是用户能完成的目标、业务规则和产生结果的完整链路，不是页面、组件、接口、类或文件。
- 先判断参考功能是否真正解决用户问题、是否适合目标项目、迁移成本和约束是否合理，不能因为用户提供了源码就默认应当照搬。
- 使用双基线调查源项目和目标项目。源功能基线证明要迁入什么；目标承载面兼容基线证明迁移会碰到什么、哪些既有能力不得静默回归。
- 迁移边界由用户目标与实际影响面共同决定。方案若要替换目标页面、主流程、公共组件、协议适配层、状态所有权或数据职责，调查范围必须扩展到这些承载面的全部可达能力，不能继续按迁移主题名称收窄。
- 结合真实运行行为和源码调用链理解功能。页面相似、接口存在、代码复制、构建通过或局部测试通过都不能证明迁移完整。
- 区分必须保留的功能语义与源项目偶然采用的架构、框架和代码组织。保留前者，根据目标项目重新设计后者。
- 每项用户可见差异、核心规则删减或能力排除都必须由用户确认，不能在设计或实现中静默丢失。
- 不声称已经消除所有未知。只在规定调查和审查已经完成、已发现的实质问题均有处置、剩余证据缺口及影响明确时推进。

## 确定迁移任务

先从当前对话、项目材料和工作区查清：

- 源项目及其精确版本、分支、提交或当前工作区状态；
- 目标项目及其当前版本和工作区状态；
- 要迁移的功能入口、主要用户、使用场景和期望迁移粒度；
- 目标项目中将被复用、改写、替换或绕过的承载面，以及这些承载面的用户入口和公共职责；
- 用户要求原样复刻、保持核心语义后适配，还是只迁移明确指定的子集；
- 本次只形成迁移方案，还是继续完成目标项目实现。

能从仓库、运行环境或已有文档查清的内容自行调查。只有不同答案会改变迁移对象、核心行为、目标适配方式或交付范围时才询问用户。默认将互不依赖的事项合并成一轮 2–5 个编号问题，并写明当前证据、差异影响和建议。

如果没有精确版本，以实际读取的提交或工作区状态作为源锚点并记录。后续源项目发生实质变化时，原迁移结论不能自动代表新版本。

## 逆向还原源功能

不要从目录结构或搜索结果直接推导功能。先找到用户真实入口并走通能够运行的参考功能，再沿每个纳入范围的操作向下追踪真实代码。

### 观察用户行为

至少调查与迁移范围直接相关的：

- 入口、导航、列表或选择、详情、编辑和操作反馈；
- 业务对象、版本、草稿、运行项等具体操作粒度；
- 初始、加载、空、成功、失败、只读和无权限等有实际依据的状态；
- 不同角色可以看见和执行什么；
- 操作前提、输入、状态变化、输出、副作用和操作后的可见结果；
- 会改变用户结果的重要分支，而不是穷举理论异常。

可以安全运行源项目时，使用真实页面、接口或其他入口观察行为。无法运行时，明确记录限制，并通过上下游源码、配置和可靠文档交叉验证；不能把未观察到的运行结果写成已证实事实。

### 追踪真实调用链

以一次用户操作或外部触发为单位，从入口追踪到最终效果，再追踪结果如何返回或被用户看见。按实际项目选择相关层级，包括：

- 页面路由、组件状态和客户端调用；
- HTTP、RPC、CLI、事件、定时任务或插件入口；
- 鉴权、校验、业务编排和领域规则；
- 数据读取、写入、事务、缓存、文件或外部服务；
- 异步任务、回调、消息和后续副作用；
- 配置、特性开关、初始化、依赖和部署前提；
- 错误如何转换、传播和呈现。

每条核心链路必须有连续的源位置或运行证据。某一层确实不存在时说明原因；不能看到前端调用和后端接口就假定中间规则、状态与副作用已经理解。

源项目中的测试、示例和文档可以帮助发现行为，但只作为线索或辅助证据。不能仅凭测试名称、断言或文档描述认定当前实现确实如此。

### 区分功能语义与实现偶然性

将调查结果分成：

- **可观察行为**：用户或外部系统能够感知的输入、过程和结果；
- **核心规则**：删除后会使已选场景无法完成或结果含义改变的业务约束；
- **必要支撑能力**：权限、持久化、异步处理、配置等完成核心规则不可缺少的机制；
- **可替换实现**：源项目的框架、文件布局、内部接口形状和其他不必原样迁移的做法；
- **无关能力**：与本次迁移边界没有因果关系的相邻功能。

不要把源项目的所有代码都升级为迁移范围，也不要因为某项能力隐藏在后台就把必要支撑能力误判为无关实现。

界面迁移中要区分视觉皮肤与用户可见语义。颜色、间距和内部组件组织可以按目标项目替换；入口与导航、信息分组、折叠和聚合规则、可操作控件、操作对象、权限表现、状态与结果反馈属于功能语义，除非明确处置，不能以“UI/布局不迁移”为由排除。

## 逆向目标承载面

源功能还原后，不立即进入目标方案。先从目标项目的真实用户入口和运行路径识别迁移实际会影响的承载面。以即将被修改的页面、主流程、公共控制器、协议边界、状态所有权和数据职责为起点，反向枚举其当前支持的可达能力，再沿每项能力追到真实调用链和结果反馈。

目标承载面调查至少记录：

- 入口、导航、展示、详情、操作对象、权限表现和结果反馈；
- 当前用户可以完成的主要操作，以及空、失败、等待、取消、恢复和终态；
- 公共组件或协议支持的实际变体，不能用一个成功样例代表全部受支持类型；
- 项目 README、正式需求、旧方案、现有测试和真实代码之间的契约冲突；
- 迁移改动将保留、替换、绕过或删除的职责及其下游使用者。

只调查与迁移无因果关系的整个目标项目同样不正确。完成标准是：每个将被替换或改变职责的承载面，其全部可达能力都有证据和后续处置；不能看到目标已有相似模块就把目标调查缩减成“可复用能力列表”。

## 建立双向映射

分别记录源功能基线、目标承载面兼容基线和迁移后的期望状态。不能用目标项目的半成品实现替代源基线，也不能用参考项目没有某项能力推断目标既有能力可以删除。

对每项源行为或必要支撑能力明确一种处置：

- **保留**：目标行为和语义保持一致；
- **适配**：保持目标价值，但按已确认差异改变交互、规则或结果；
- **替换**：使用目标项目已有机制实现同一必要能力；
- **排除**：明确不进入本次范围；
- **受阻**：当前缺少决定或证据，不能可靠确定处置。

适配、排除核心规则或用户可见行为时，说明实际影响并取得用户确认。必要支撑能力可以采用不同技术实现，但不能在没有替代链路时排除。

对目标承载面的每项既有能力同样明确“保留、改变、移除或受阻”。保留项必须进入下游设计和验证；改变或移除用户可见能力必须说明影响并取得用户确认；受阻项会阻止迁移基线确认。源能力与目标既有契约冲突时单独记录冲突，不由迁移阶段静默选择一方。

提出目标方案前先检查目标项目是否已有可复用能力。不要机械复制源架构，也不要为了少改代码而把完整能力降级成静态页面、固定数据、孤立接口、mock、临时绕过或无法接入真实流程的外壳。

直接复制或改编源代码、资源、数据或依赖时，检查源许可证、版权说明和项目许可是否允许相应用法，并保留必要归属。无法确认时不要复制；可以在许可和用户要求允许的范围内重新实现已经查明的功能语义。

## 维护迁移基线

使用一份持续更新的 `功能迁移基线.md` 保存迁移特有事实，不另外创建重复的总报告或多套状态台账。

如果当前工作已经有需求正文，把迁移基线放在正文旁的同名二级目录。尚无正文时，先确定稳定工作名称，按项目规范创建对应二级目录；项目没有约定时使用：

`workplace/<版本>/requirements/<工作名称>/功能迁移基线.md`

后续需求正文默认位于：

`workplace/<版本>/requirements/<工作名称>.md`

迁移基线至少包含以下内容，可以根据项目合并章节，但不能省略其信息：

1. **状态与锚点**：草稿或已确认、源和目标项目路径、版本或提交、工作区差异；
2. **目标与边界**：迁移原因、用户场景、迁移粒度、包含和排除范围；
3. **源功能全貌**：用户流程、对象与状态、核心规则、权限和可观察结果；
4. **源调用链与依赖**：每条核心行为的连续代码或运行证据、配置和运行前提；
5. **目标承载面兼容基线**：实际影响面、既有可达能力、公共职责、协议变体、契约冲突和连续证据；
6. **双向映射**：源能力的迁入处置、目标既有能力的兼容处置，以及新旧冲突的待决项；
7. **完整性账本**：跨阶段持续更新的迁移闭环；
8. **证据限制与阻塞**：无法运行、无法读取或尚未确认的内容及其实际影响；
9. **下游链接**：正式需求、方案、计划、实现审查和验收材料的直接路径。

### 完整性账本

完整性账本同时包含“源能力迁入项”和“目标既有能力兼容项”，以一个可独立观察或独立失败的行为、规则或必要支撑能力为一项，不以文件或函数为一项。每项持续记录：

- 稳定且容易理解的行为名称；
- 条目来源及其行为、代码或运行证据；
- 为什么属于核心行为或必要支撑；
- 目标处置和已确认差异；
- 对应需求、设计和任务位置；
- 目标实现位置；
- 与交付行为层级匹配的验证及结果。

初次调查时允许下游位置暂缺，但不能将迁移基线标为已确认，直到所有源能力和受影响目标能力都有明确处置，所有契约冲突均已解决或明确受阻。实现完成时，任何纳入范围的账本项缺少目标落点或真实验证，都必须保持未完成。

迁移基线第一次创建时标为草稿。只有源调查、目标承载面调查和完整性审查已经完成，双向范围与处置决定清楚，实质证据缺口已经处理或明确阻塞影响，并且用户明确认可当前迁移契约后，才能标为已确认并进入下游。含义变化时恢复为草稿并重新确认受影响内容。

## 迁移完整性审查

迁移基线初步稳定后，使用两个新的 subagent 做一次独立审查。这个审查强制扩大搜索面，但候选问题不是事实或正式缺陷。

1. 向第一个 subagent 提供用户原始目标、源和目标项目的精确位置与版本、迁移基线，不提供主 agent 的结论。要求它提出至少 10 个有价值的候选问题，同时搜索源功能遗漏、目标承载面遗漏和双向映射缺口；每项指出可能遗漏的位置、行为和影响，不能加入同义问题或通用最佳实践。
2. 向第二个 subagent 提供相同原始材料和候选问题，允许它查看直接相关的源项目与目标项目代码、配置和运行证据。要求逐项记录源证据、目标事实、具体缺失内容、影响和分类；分类至少区分“源功能调查遗漏”“目标承载面遗漏”“双向映射或契约冲突”“已有覆盖”“下游实现细节”“前提错误或超出范围”。无法证明时明确写不确定。
3. 主 agent 依据源和目标的真实证据复核分类。只有证据支持的源行为、受影响目标能力、必要支撑或映射缺口才能修改迁移基线；审查者建议的新机制、理论风险和个人偏好不能扩展范围。
4. 审查发现用户可见差异或核心规则处置不明确时，集中询问用户。只改局部内容后定向复核受影响链路，不重新强制生成一批全量问题。

“至少 10 个”只约束初次候选搜索，不要求产生固定数量的正式缺陷、用户问题或审查轮次。

## 贯穿研发阶段

用户要求完成迁移时，让实际需要的现有阶段负责各自正式产物，并始终直接引用已确认迁移基线。迁移基线是指定参考实现进入设计的强制输入；正式需求文档和任务计划仍是可选产物，不能因为迁移复杂就自动变成执行门禁：

1. **需求**：存在需要用户决定的目标行为、范围或用户可见偏离时，使用 `project-requirements` 把纳入范围的源行为和目标兼容项转成目标项目用户需求。迁移基线证明参考能力与受影响既有能力，需求正文或用户当前明确决定目标行为。
2. **设计**：使用 `project-design` 把必要能力映射到目标架构、模块、契约和数据链路。不能把“参考源项目”当成技术方案，也不能遗漏账本中的目标兼容项和后台支撑能力。设计若新增会被替换或改变职责的承载面，先恢复迁移基线为草稿，补齐该承载面的兼容调查后再继续。
3. **计划**：需要跨会话跟踪、多人协作或用户明确要求时，使用 `project-planning` 确保每项纳入范围的行为和必要支撑都有任务来源与完成边界。否则已确认技术方案可以直接进入原子化执行；跨层能力仍优先完成一个代表性的真实端到端结果。
4. **执行**：使用 `project-execution` 先打通并验证代表性纵向链路，再扩展其他行为和分支。每完成一项就回写实现和当前验证证据，不能只批量完成同一层。
5. **审查**：使用 `project-review` 同时从“迁移账本到代码”和“代码到真实运行结果”检查完整性，区分实现漏项、计划遗漏、设计错误和迁移契约缺口。
6. **验收**：在目标项目当前运行环境中，按已确认的相同前提比较源行为和目标结果。只有明确确认的适配项允许不同；无法运行的关键路径保持未验证。

正式需求、设计或计划仍为草稿、互相冲突或没有引用正确迁移基线时，不能进入执行。下游发现的信息如果改变迁移范围、核心行为、用户可见差异或处置决定，先把迁移基线恢复为草稿，返回对应上游确认，不能由执行者自行选择。

调用会自动提交的验收流程前必须取得用户对提交行为的明确授权。完成迁移本身不授权自动暂存、提交、推送、部署或修改生产环境。

## 完成迁移

只有同时满足以下条件，才能说明所选功能已经完整迁移：

- 使用的源、目标和迁移基线锚点仍然有效；
- 规定的源调查、目标承载面调查、双向映射和迁移完整性审查已经完成；
- 每项源能力和受影响目标能力都有证据、确认处置、下游落点、目标实现和匹配层级的验证；
- 至少一条代表性真实端到端链路已在目标项目当前实现中闭环；
- 所有会改变核心场景结果的重要分支、角色差异和必要副作用都已按范围验证；
- 验证使用当前工作区和当前运行产物，不依赖 mock、固定返回、旧进程或未经指定为当前有效基线的既有测试；
- 复制的代码或资源已经完成必要的许可与归属检查；
- 阻塞项、未验证项和已确认差异已经如实说明，没有被包装成完成。

完成后简洁报告迁移了哪些完整能力、哪些差异经过确认、每类目标行为由什么真实证据证明，以及仍然存在的阻塞或未验证内容。

## 边界

- 不把与所选功能没有因果关系的整个源项目纳入调查或迁移。
- 不要求目标项目复制源项目的框架、目录、接口形状或内部实现。
- 不替用户决定核心能力删减、用户可见差异或范围扩展。
- 不用文档完整、代码数量、候选问题数量或低层检查代替真实功能闭环。
- 不自动提交、推送、部署、修改生产数据或执行其他未经授权的外部动作。
