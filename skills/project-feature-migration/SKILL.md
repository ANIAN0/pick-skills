# 项目功能迁移

把参考实现中的指定功能还原成有证据的完整能力，并在目标项目中形成可运行、可验证的迁移闭环。

本 skill 负责源功能逆向、目标承载面兼容调查、迁移范围决策和跨阶段完整性控制，不重复代替需求、技术设计、任务规划、编码或验收阶段。用户只要求分析时，完成迁移基线后停止；用户要求完成迁移时，以迁移基线为来源锚点推进现有研发阶段。

本 skill 是迁移基线的唯一产物负责人。它只创建或修改 `功能迁移基线.md` 及迁移审查材料；发现目标产品行为、技术方案或实现任务缺口时，把证据返回对应阶段，不同时修改需求正文、技术方案、计划或生产代码。

`功能迁移基线.md` 即使与需求正文共用同名二级目录，也不属于需求阶段可写的普通二级材料。其他阶段发现它需要改变时，本 skill 在独立阶段重新核实锚点、影响与处置后更新；不能接受另一个阶段已经顺手改写的内容作为已验证迁移结论。

设计、规划、执行或审查阶段报告“新增承载面、参考遗漏或迁移缺口”时，只把报告当作候选证据。另一个阶段不得在同一轮切换到本 skill，恢复状态、扩大限定行为基线或补写处置，再把新内容作为自己的上游依据。只有用户明确要求重新审查或更新迁移基线时，才独立进入本阶段并重新核实源、目标锚点和实际影响。

下游自行新增的组件、页面、状态、协议或后台任务不能反向证明目标承载面必须扩大。先检查它是否具有已确认需求、限定行为基线或目标项目不可绕开的真实来源；没有来源时由下游删除。只有合法方案确实会替换或改变既有公共承载面，且该影响在当前基线中缺失时，才把证据记录为迁移候选。候选仍不能自动晋级为目标采用决定。

## 核心原则

- 迁移单位是用户能完成的目标、业务规则和产生结果的完整链路，不是页面、组件、接口、类或文件。
- 完整性只对用户明确圈定的行为基线成立；完整调查限定能力，不完整搬运参考项目的同名功能面或相邻能力。
- 先判断参考功能是否真正解决用户问题、是否适合目标项目、迁移成本和约束是否合理，不能因为用户提供了源码就默认应当照搬。
- 使用双基线调查源项目和目标项目。源功能基线证明要迁入什么；目标承载面兼容基线证明迁移会碰到什么、哪些既有能力不得静默回归。
- 迁移边界由用户目标与实际影响面共同决定。方案若要替换目标页面、主流程、公共组件、协议适配层、状态所有权或数据职责，调查范围必须扩展到这些承载面的全部可达能力，不能继续按迁移主题名称收窄。
- 结合真实运行行为和源码调用链理解功能。页面相似、接口存在、代码复制、构建通过或局部测试通过都不能证明迁移完整。
- 区分必须保留的功能语义与源项目偶然采用的架构、框架和代码组织。保留前者，根据目标项目重新设计后者。
- 限定行为基线内的每项用户可见差异、核心规则删减或能力排除都必须由用户确认，不能在设计或实现中静默丢失；范围外相邻能力不属于删减。
- 不声称已经消除所有未知。只在规定调查和审查已经完成、已发现的实质问题均有处置、剩余证据缺口及影响明确时推进。

## 确定迁移任务

先写出一条可核对的**限定行为基线**：`源对象 + 被选中的用户能力 + 迁移粒度 + 保真程度`。这条边界必须来自用户明确表达或已确认需求，不能由源项目目录、页面名称、审查结果或 agent 对“完整”的偏好推导。无法写出且不同边界会实质改变产品范围时，先澄清范围；没有行为基线时不启动本 skill 的完整性账本。

先对每个被提到的参考对象做**参考角色判定**：

- **行为基线**：用户要保留、复刻或适配其完整用户行为；只有这种角色进入本 skill 的双基线流程；
- **视觉参考**：只参考布局、样式、信息密度或控件位置；
- **SDK、框架或平台候选**：用于选型和技术可行性判断；
- **数据或协议来源**：目标只需读取、转换或兼容其数据；
- **实现证据**：只用来证明某种机制可行或比较取舍。

同一项目可以承担多个角色，但要分别写清角色对应的具体能力。视觉参考、技术候选、数据来源和实现证据交给需求、调研或设计阶段按各自职责处理，不能因为项目被称为“参考”就自动建立完整迁移账本。角色不明确且不同判断会显著改变调查范围时，先询问用户。

用户问“为什么没参考 X”“是否看过 X 的实现”或用 X 质疑现有文档，只表示 X 需要进入证据完整性调查，不表示用户要求迁移 X、采用 X 的行为或把 X 升级为行为基线。先交给 `project-research` 核实事实；只有用户明确要求保留、复刻或适配 X 的具体用户行为后，才把对应能力纳入本 skill。不得为了修复一次调研遗漏而扩大迁移范围或重写目标产品行为。

“基于通用能力实现”“复用某项目机制”只圈定被点名的能力或职责。例如“基于通用定时任务实现评估”可以把多任务、通用调度与运行交接纳入调查，但不会自动把 quickstart、时区、一次性任务、Artifact、Agent 管理入口或整个 Automations 页面纳入行为基线。只有用户明确要求完整复刻该功能面时，才调查并处置这些相邻行为。

用户明确要求对限定能力“1:1 复刻”“完全还原”或“沿用完整逻辑”时，按完整保留处理该范围，不再逐项询问是否采用源项目已经具备的入口、操作、状态和结果。只纳入该语句直接指向的源项目与能力，不把同轮出现的其他参考对象一并升级为行为基线。先建立完整源基线；只有范围边界、源项目自身冲突、目标项目硬约束、许可限制和明确拟偏离项需要返回用户决定。不能因为调查尚未完成，把未知源行为包装成待用户定义的产品问题。

确认至少存在一项行为基线后，再从当前对话、项目材料和工作区查清：

- 源项目及其精确版本、分支、提交或当前工作区状态；
- 目标项目及其当前版本和工作区状态；
- 要迁移的功能入口、主要用户、使用场景和期望迁移粒度；
- 目标项目中将被复用、改写、替换或绕过的承载面，以及这些承载面的用户入口和公共职责；
- 用户要求原样复刻、保持核心语义后适配，还是只迁移明确指定的子集；
- 本次只形成迁移方案，还是继续完成目标项目实现。

能从仓库、运行环境或已有文档查清的内容自行调查。只有不同答案会改变迁移对象、核心行为、目标适配方式或交付范围时才询问用户。默认将互不依赖的事项合并成一轮 2–5 个编号问题，并写明当前证据、差异影响和建议。

不要根据 agent 偏好的 MVP 粒度自行把同一完整用户流程分期。只有拆出的每一期都能独立形成可用闭环，且有用户优先级、真实依赖、风险或成本证据时，才把分期作为待决定项；源项目已经用一条低成本完整链路承载的相邻操作，默认一起纳入调查和处置。

如果没有精确版本，以实际读取的提交或工作区状态作为源锚点并记录。后续源项目发生实质变化时，原迁移结论不能自动代表新版本。

## 逆向还原行为基线

不要从目录结构或搜索结果直接推导功能。先找到用户真实入口并走通能够运行的参考功能，再沿每个纳入范围的操作向下追踪真实代码。

源功能包含多个触发源、后台或定时流程、Agent/Skill/调度器协作、共享数据或多重生命周期时，先按独立触发源形成来源职责图和流程图。节点使用“执行者 + 动作”，连线区分控制调用、数据读取、数据写入和用户操作；多条流程访问同一数据不表示它们互相触发。没有完成这一步时，不能把若干局部参考行为拼成一个“完整源流程”。

来源流程图只证明参考实现怎样运行。目标产品流程必须来自用户明确决定或已确认需求；将来源节点映射到目标时逐条记录“采用、适配、排除或受阻”，不能因为来源机制已经验证，就把其调度频率、目录、内部编排或相邻能力自动晋级为目标行为。

### 观察用户行为

至少调查与迁移范围直接相关的：

- 入口、导航、列表或选择、详情、编辑和操作反馈；
- 业务对象、版本、草稿、运行项等具体操作粒度；
- 初始、加载、空、成功、失败、只读和无权限等有实际依据的状态；
- 不同角色可以看见和执行什么；
- 操作前提、输入、状态变化、输出、副作用和操作后的可见结果；
- 会改变用户结果的重要分支，而不是穷举理论异常。

可以安全运行源项目时，使用真实页面、接口或其他入口观察行为。无法运行时，明确记录限制，并通过上下游源码、配置和可靠文档交叉验证；不能把未观察到的运行结果写成已证实事实。

### 追踪真实调用链

以一次用户操作或外部触发为单位，从入口追踪到最终效果，再追踪结果如何返回或被用户看见。按实际项目选择相关层级，包括：

- 页面路由、组件状态和客户端调用；
- HTTP、RPC、CLI、事件、定时任务或插件入口；
- 鉴权、校验、业务编排和领域规则；
- 数据读取、写入、事务、缓存、文件或外部服务；
- 异步任务、回调、消息和后续副作用；
- 配置、特性开关、初始化、依赖和部署前提；
- 错误如何转换、传播和呈现。

每条核心链路必须有连续的源位置或运行证据。某一层确实不存在时说明原因；不能看到前端调用和后端接口就假定中间规则、状态与副作用已经理解。

源项目中的测试、示例和文档可以帮助发现行为，但只作为线索或辅助证据。不能仅凭测试名称、断言或文档描述认定当前实现确实如此。源项目具备某项行为也只证明行为基线，不自动决定目标产品要保留它；目标处置仍需来自用户决定或已确认需求。

调查发现限定行为基线之外的相邻能力时，标为“范围外证据”，不要把它加入迁移账本，也不要把未迁入解释成能力删减。只有新证据证明该能力是完成已选场景不可缺少的核心规则或必要支撑时，才将其带回需求阶段判断是否扩大限定行为基线。

### 区分功能语义与实现偶然性

将调查结果分成：

- **可观察行为**：用户或外部系统能够感知的输入、过程和结果；
- **核心规则**：删除后会使已选场景无法完成或结果含义改变的业务约束；
- **必要支撑能力**：权限、持久化、异步处理、配置等完成核心规则不可缺少的机制；
- **可替换实现**：源项目的框架、文件布局、内部接口形状和其他不必原样迁移的做法；
- **无关能力**：与本次迁移边界没有因果关系的相邻功能。

不要把源项目的所有代码都升级为迁移范围，也不要因为某项能力隐藏在后台就把必要支撑能力误判为无关实现。

界面迁移中要区分视觉皮肤与用户可见语义。颜色、间距和内部组件组织可以按目标项目替换；入口与导航、信息分组、折叠和聚合规则、可操作控件、操作对象、权限表现、状态与结果反馈属于功能语义，除非明确处置，不能以“UI/布局不迁移”为由排除。

## 逆向目标承载面

源功能还原后，不立即进入目标方案。先从目标项目的真实用户入口和运行路径识别迁移实际会影响的承载面。以即将被修改的页面、主流程、公共控制器、协议边界、状态所有权和数据职责为起点，反向枚举其当前支持的可达能力，再沿每项能力追到真实调用链和结果反馈。

目标承载面调查至少记录：

- 入口、导航、展示、详情、操作对象、权限表现和结果反馈；
- 当前用户可以完成的主要操作，以及空、失败、等待、取消、恢复和终态；
- 公共组件或协议支持的实际变体，不能用一个成功样例代表全部受支持类型；
- 项目 README、正式需求、旧方案、现有测试和真实代码之间的契约冲突；
- 迁移改动将保留、替换、绕过或删除的职责及其下游使用者。

只调查与迁移无因果关系的整个目标项目同样不正确。完成标准是：每个将被替换或改变职责的承载面，其全部可达能力都有证据和后续处置；不能看到目标已有相似模块就把目标调查缩减成“可复用能力列表”。

## 建立双向映射

分别记录源功能基线、目标承载面兼容基线和迁移后的期望状态。不能用目标项目的半成品实现替代源基线，也不能用参考项目没有某项能力推断目标既有能力可以删除。

对每项源行为或必要支撑能力明确一种处置：

- **保留**：目标行为和语义保持一致；
- **适配**：保持目标价值，但按已确认差异改变交互、规则或结果；
- **替换**：使用目标项目已有机制实现同一必要能力；
- **排除**：明确不进入本次范围；
- **受阻**：当前缺少决定或证据，不能可靠确定处置。

上述处置只适用于限定行为基线内的能力。参考项目中未被选入基线、也不是已选场景必要支撑的相邻能力使用**范围外**分类；范围外不是“排除”，不需要用户逐项确认，也不进入下游完整性账本。

适配、排除核心规则或用户可见行为时，说明实际影响并取得用户确认。必要支撑能力可以采用不同技术实现，但不能在没有替代链路时排除。

每个“保留、适配或替换”条目必须同时具备两类来源：证明源行为存在的源证据，以及证明目标要采用它的用户决定或已确认需求。只有源证据、审查建议、安全理由或实现便利时，不得把条目标成目标处置。

对目标承载面的每项既有能力同样明确“保留、改变、移除或受阻”。保留项必须进入下游设计和验证；改变或移除用户可见能力必须说明影响并取得用户确认；受阻项会阻止迁移基线确认。源能力与目标既有契约冲突时单独记录冲突，不由迁移阶段静默选择一方。

提出目标方案前先检查目标项目是否已有可复用能力。不要机械复制源架构，也不要为了少改代码而把完整能力降级成静态页面、固定数据、孤立接口、mock、临时绕过或无法接入真实流程的外壳。

直接复制或改编源代码、资源、数据或依赖时，检查源许可证、版权说明和项目许可是否允许相应用法，并保留必要归属。无法确认时不要复制；可以在许可和用户要求允许的范围内重新实现已经查明的功能语义。

## 维护迁移基线

使用一份持续更新的 `功能迁移基线.md` 保存迁移特有事实，不另外创建重复的总报告或多套状态台账。

如果当前工作已经有需求正文，把迁移基线放在正文旁的同名二级目录。尚无正文时，先确定稳定工作名称，按项目规范创建对应二级目录；项目没有约定时使用：

`workplace/<版本>/requirements/<工作名称>/功能迁移基线.md`

后续需求正文默认位于：

`workplace/<版本>/requirements/<工作名称>.md`

迁移基线至少包含以下内容，可以根据项目合并章节，但不能省略其信息：

1. **状态与锚点**：草稿或已确认、源和目标项目路径、版本或提交、工作区差异；
2. **目标与边界**：迁移原因、用户场景、迁移粒度、包含和排除范围；
3. **源功能全貌**：用户流程、对象与状态、核心规则、权限和可观察结果；复杂功能同时包含按独立触发源划分的职责图、流程图和必要状态图；
4. **源调用链与依赖**：每条核心行为的连续代码或运行证据、配置和运行前提；
5. **目标承载面兼容基线**：实际影响面、既有可达能力、公共职责、协议变体、契约冲突和连续证据；
6. **双向映射**：源能力的迁入处置、目标既有能力的兼容处置，以及新旧冲突的待决项；
7. **完整性账本**：跨阶段持续更新的迁移闭环；
8. **证据限制与阻塞**：无法运行、无法读取或尚未确认的内容及其实际影响；
9. **下游链接**：正式需求、方案、计划、实现审查和验收材料的直接路径。

### 完整性账本

完整性账本同时包含“源能力迁入项”和“目标既有能力兼容项”，以一个可独立观察或独立失败的行为、规则或必要支撑能力为一项，不以文件或函数为一项。每项持续记录：

- 稳定且容易理解的行为名称；
- 条目来源及其行为、代码或运行证据；
- 为什么属于核心行为或必要支撑；
- 目标处置和已确认差异；
- 对应需求、设计和任务位置；
- 目标实现位置；
- 与交付行为层级匹配的验证及结果。

初次调查时允许下游位置暂缺，但不能将迁移基线标为已确认，直到限定行为基线内的所有源能力和受影响目标能力都有明确处置、每个目标处置都有决定来源、所有契约冲突均已解决或明确受阻。实现完成时，任何纳入范围的账本项缺少目标落点或真实验证，都必须保持未完成。

迁移基线第一次创建时标为草稿。只有源调查、目标承载面调查和完整性审查已经完成，双向范围与处置决定清楚，实质证据缺口已经处理或明确阻塞影响，并且当前候选版本呈现后用户又明确认可该迁移契约，才能标为已确认并进入下游。含义变化时立即恢复为草稿；“修改”“修正”“继续”“列出决定”或指出错误不构成对修改后版本的确认，同一回合实质改写的基线不得由 agent 自行标记为已确认。

用户认可位于迁移完整性自检之后，不能用来发现源行为遗漏、目标兼容遗漏或映射冲突。向用户提交确认前，主 agent 必须先完成当前锚点下的源调查、目标调查、双向映射和规定审查，修复能够自行处理的发现，并按修改影响完成复核。改变范围、参考角色、完整用户流程或多个账本项时，旧审查结论失效；不得以“只差用户审阅”跳过重新审查。

## 迁移完整性审查

迁移基线初步稳定后，按范围和风险做独立审查。跨项目、跨公共承载面或主 agent 无法可靠覆盖时，使用新的 subagent 盲查；局部、证据充分的迁移可以由主 agent 完成。审查者只接收用户原始目标、限定行为基线、源和目标锚点及迁移基线，不接收预期结论。

审查先验证限定行为基线没有被迁移文档自行扩大，再逐项寻找并分类“源功能调查遗漏”“独立流程被错误合并或职责颠倒”“目标承载面遗漏”“双向映射或契约冲突”“范围外相邻能力”“已有覆盖”“下游实现细节”“前提错误或超出范围”，但不规定候选问题数量、审查者数量或固定轮次。每个候选问题必须指向具体行为、位置和可能影响；无法证明时标为不确定。源项目存在某项能力本身不能证明迁移遗漏。

主 agent 依据真实证据复核分类。只有证据支持的源行为、受影响目标能力、必要支撑或映射缺口才能修改迁移基线；审查者建议的新机制、理论风险和个人偏好不能扩展范围。审查发现用户可见差异或核心规则处置不明确时，记录具体差异和受影响账本项并停止对应处置，等待用户明确要求进入需求阶段；只改局部内容后定向复核受影响链路。

完成标准不是生成多少问题，而是限定行为基线没有膨胀，每项纳入的源行为、每项受影响目标能力和每个新旧契约冲突都有证据、目标决定来源、处置或明确阻塞；范围外能力没有被审查自动晋级为目标需求。

## 贯穿研发阶段

用户要求完成迁移时，让实际需要的现有阶段负责各自正式产物，并始终直接引用已确认迁移基线。迁移基线是指定参考实现进入设计的强制输入；正式需求文档和任务计划仍是可选产物，不能因为迁移复杂就自动变成执行门禁：

1. **需求**：存在需要用户决定的目标行为、范围或用户可见偏离时，使用 `project-requirements` 把纳入范围的源行为和目标兼容项转成目标项目用户需求。迁移基线只能证明参考能力与受影响既有能力，不能把源行为直接晋级为目标需求；需求正文或用户当前明确决定目标行为。
2. **设计**：使用 `project-design` 把必要能力映射到目标架构、模块、契约和数据链路。不能把“参考源项目”当成技术方案，也不能遗漏账本中的目标兼容项和后台支撑能力。设计若发现合法方案会影响基线未覆盖的承载面，停止受影响设计并报告证据；不得由设计阶段直接恢复或修改迁移基线。
3. **计划**：需要跨会话跟踪、多人协作或用户明确要求时，使用 `project-planning` 确保每项纳入范围的行为和必要支撑都有任务来源与完成边界。否则已确认技术方案可以直接进入原子化执行；跨层能力仍优先完成一个代表性的真实端到端结果。
4. **执行**：使用 `project-execution` 先打通并验证代表性纵向链路，再扩展其他行为和分支。每完成一项就回写实现和当前验证证据，不能只批量完成同一层。
5. **审查**：使用 `project-review` 同时从“迁移账本到代码”和“代码到真实运行结果”检查完整性，区分实现漏项、计划遗漏、设计错误和迁移契约缺口。
6. **验收**：在目标项目当前运行环境中，按已确认的相同前提比较源行为和目标结果。只有明确确认的适配项允许不同；无法运行的关键路径保持未验证。

正式需求、设计或计划仍为草稿、互相冲突或没有引用正确迁移基线时，不能进入执行。下游发现的信息如果可能改变迁移范围、核心行为、用户可见差异或处置决定，停止受影响工作并形成包含证据和影响的候选报告；只有用户明确要求进入迁移阶段后，才由本 skill 决定是否恢复基线为草稿并更新，不能由执行者自行选择或改写状态。

调用会自动提交的验收流程前必须取得用户对提交行为的明确授权。完成迁移本身不授权自动暂存、提交、推送、部署或修改生产环境。

## 完成迁移

只有同时满足以下条件，才能说明所选功能已经完整迁移：

- 使用的源、目标和迁移基线锚点仍然有效；
- 限定行为基线仍能直接追溯到用户表达或已确认需求，没有因调查或审查自动扩大；
- 规定的源调查、目标承载面调查、双向映射和迁移完整性审查已经完成；
- 限定行为基线内的每项源能力和受影响目标能力都有证据、确认处置、下游落点、目标实现和匹配层级的验证；
- 至少一条代表性真实端到端链路已在目标项目当前实现中闭环；
- 所有会改变核心场景结果的重要分支、角色差异和必要副作用都已按范围验证；
- 验证使用当前工作区和当前运行产物，不依赖 mock、固定返回、旧进程或未经指定为当前有效基线的既有测试；
- 复制的代码或资源已经完成必要的许可与归属检查；
- 阻塞项、未验证项和已确认差异已经如实说明，没有被包装成完成。

交付前核对基线文件、审查记录、变更记录和最终回复对草稿/已确认状态给出同一答案；任何已确认状态都必须有候选版本呈现后的真实用户依据。

完成后简洁报告迁移了哪些完整能力、哪些差异经过确认、每类目标行为由什么真实证据证明，以及仍然存在的阻塞或未验证内容。

## 边界

- 不把与所选功能没有因果关系的整个源项目纳入调查或迁移。
- 不要求目标项目复制源项目的框架、目录、接口形状或内部实现。
- 不替用户决定核心能力删减、用户可见差异或范围扩展。
- 不用文档完整、代码数量、候选问题数量或低层检查代替真实功能闭环。
- 不自动提交、推送、部署、修改生产数据或执行其他未经授权的外部动作。
